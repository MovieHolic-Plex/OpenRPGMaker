01무엇이 망가져 있었나

전부 실측이다. 짐작으로 적은 줄은 없다.

#구멍근거지금
1채팅 턴은 완료 시점에 1행만 남는다 — 새로고침·크래시로 끝나지 않은 턴은 흔적이 없다 aiChatPanel.ts 의 recordAiActivity({channel:"chat"}) 호출이 단 하나, 그것도 finally 턴 시작에 pending 행을 먼저 쓴다. 같은 log_id 로 upsert 되므로 행은 늘지 않는다
2그 1행도 조용히 잘린다 — audit 200칸·툴 80개 13:23:48 「니 추천대로」 행: audit 정확히 200, 첫 칸이 이미 턴 중간의 tools:escalated(사람 발언·플래너 결정이 사라졌다). 툴은 114회 중 67개 칸수 상한을 바이트 예산(audit 384KB / 툴 128KB)으로 교체. 잘리면 양 끝을 남기고 truncated 로 몇 칸인지 말한다
3프론트 액션은 0건 uiEvents 필드는 타입에 있었지만 chat 채널에서 항상 비었다 — 채우는 코드가 없었고, 아무 테스트도 그걸 잡지 못했다 src/ai/uiEventLog.ts — 위임 리스너 1개 + 300건 링버퍼. 의미 액션 13종은 결과 수치까지 싣는다
4늦게 정착한 턴은 아예 안 남는다 ownsTurn(true) 가 false 면 대화만 저장하고 return — 활동 로그를 건너뛴다 orphaned: true + stoppedReason 으로 남긴다. 소유권이 끊긴 사실 자체가 진단이다
5워크트리 19/53 은 어디에도 안 남는다 .env.local 없음 → Supabase 미설정. 표본의 output/ai-activity/ 도 0개. localStorage 100건이 전부 둘 다 죽었으면 콘솔 경고 1회 + 하네스에 「기록 로컬 전용 — 300건 링버퍼」 배지
6남아도 SQL 로 못 찾는다 전부 payload_json 안. "이벤트 툴을 부른 턴" 을 알려면 169KB payload 를 받아 grep 해야 했다(실제로 그렇게 찾았다) 평탄 색인 6종을 payload 최상위에 함께 만들고 GIN 마이그레이션 파일을 뒀다
7하네스 토큰 배지가 아직 정규식 긁기 aiHarnessModal.ts 의 /출력 토큰 ~(\d+)/ — 게이지는 구조 집계로 옮겼는데 배지만 남아 있었다 SessionUsageTotals 로 교체. 사용량을 안 준 호출은 「사용량 미보고 N회」 로 따로 센다

02어떻게 모으나 — 위임 리스너 1개

버튼마다 호출을 심는 방식은 이미 실패했다. 그게 3번 구멍을 만든 실패 모드다.

document 의 capture 단계에서 click·change 를 한 번 듣고, 이벤트가 AI 표면 안에서 났을 때만 기록한다. 앞으로 추가되는 버튼도 자동으로 들어온다 — 다음 사람이 계측을 잊어도 «눌렸다» 는 사실은 남는다. 대신 결과 수치가 필요한 액션(압축이 얼마를 줄였나, 되감기가 스냅샷 몇 개를 되돌렸나)은 그 자리에서 명시 호출을 둔다.

위임 수집이 잡는 것

무엇을 눌렀는지. click:<testid>, change:<testid> + 표면·라벨·비활성 여부.

버튼을 새로 달아도 계측을 따로 심을 필요가 없다.

명시 호출 13종이 더 싣는 것

그래서 어떻게 됐는지. 압축 전/후 토큰, 되돌린 스냅샷 수, 버린 대화 칸 수, 도크 from→to, 중단 시점 툴 수…

거절도 남긴다 — 「눌렀는데 안 바뀌었다」를 사후에 가르는 유일한 증거다.

실측 중에 실제로 잡힌 «반쪽 기록»
진단 스펙 첫 실행에서 되감기 버튼에 click:ai-turn-rewind 만 있고 의미 이벤트가 없었다. rewindToTurn 이 turnBusy 면 기록 앞에서 조기 반환했기 때문이다. 무엇이 바뀌었는지가 없는 기록은 이 기능의 가치가 0 이므로, 거절 경로도 disabled: true + reason 으로 남기게 고쳤다. 두 번째 실행에서 turn-rewind {reason:"turn-busy"} 가 나왔다.

03기록 행이 무엇을 담나

턴 구간만 담는다

세션 audit 은 턴을 넘어 누적된다. 세션 전체를 넣고 뒤에서 자르면 긴 턴의 머리가 날아간다 — 2번 구멍이 정확히 그 모양이었다. 턴 시작에 session.getAuditEntries().length 를 표식으로 잡아 그 지점부터 잘라 담는다. (계획서에는 기존 turnEntries 가 이미 턴 구간이라고 적혀 있었지만, 실제로는 auditHistory + 세션 누적 전체였다. 읽고 고쳤다.)

예산을 넘으면 양 끝을 남긴다

색인은 «절단 전» 전체에서 만든다

이름 목록은 중복 제거된 짧은 배열이라 비용이 거의 없는데, 절단된 행에서 만들면 가운데로 버린 툴·액션은 조회로 아예 못 찾는다. payload 를 못 찾는 게 이 작업이 고치려는 구멍이라 색인·커밋 id·진단은 전부 절단 전 입력에서 뽑는다. 툴 120개 턴 테스트가 이걸 잠근다 — 행에 남은 호출은 일부지만 index.toolNames 는 120개 전부다.

-- 색인 적격 형태(컬럼 단위 포함 연산자 → GIN 을 탄다)
GET /rest/v1/ai_activity_logs?payload_json=cs.{"index":{"toolNames":["set_event"]}}
GET /rest/v1/ai_activity_logs?channel=eq.ui&payload_json=cs.{"index":{"uiActions":["turn-rewind"]}}

-- 보기 좋은 하위 경로 형태는 같은 행을 주지만 색인을 못 탄다(15,000행 seq scan)
-- payload_json->index->toolNames=cs.["set_event"]   ← 쓰지 말 것

색인 6종: toolNames · failedToolNames · uiActions · commitIds · mapIds · userTexts. userTexts 는 기계 footer([컨텍스트] 맵: …)를 뗀 사람 문장만 담는다 — 붙이면 모든 행이 같은 맵 이름으로 시작해 검색축이 죽는다. commitIds 는 상태줄 텍스트를 긁는 한 군데를 남겨 기록 시점에 구조화한다(조회하는 사람이 매번 긁지 않게).

06남은 것

  • 마이그레이션은 적용하지 않았다. 공유 Supabase 스키마라 파일만 뒀다 (supabase/migrations/20260830000000_ai_activity_payload_index.sql). CREATE INDEX CONCURRENTLY 는 트랜잭션 밖에서 실행해야 한다는 주석을 파일에 남겼다. channel 에 CHECK 제약이 없어 "ui" 채널 추가에는 스키마 변경이 필요 없다.
  • 맵 캔버스·타일 팔레트는 범위 밖. 드래그 같은 연속 입력이 섞이면 로그량이 수십 배가 되고 별도 샘플링 설계가 필요하다.
  • 「제안 승인/거절」 액션은 없다. 승인 카드는 설계상 제거됐고(쓰기는 그대로 적용하고 복구는 되돌리기다), 남은 게이트는 DOM 어포던스가 없는 콘솔·E2E 훅이라 누를 버튼 자체가 없다. 그 경로의 결과는 턴 행의 toolCalls 에 남는다.
  • 「니 추천대로」의 근본 원인은 별개 PR. 플래너에 대화 기록을 넣는 수정(workPlan.ts)은 이 작업에서 손대지 않았다. 이번 것은 «무슨 일이 있었는지 보이게» 하는 작업이다.
  • maps 미러가 커밋마다 갱신되지 않는 문제도 그대로 뒀다 — 별개 결함이다.
