2. 원인과 수정

A. 매 프레임 전체 맵 탐색 — 가장 큰 원인

  • updateNpcSchedules 가 프레임마다 주민 전원의 목표 경로를 다시 등록했다. 100ms 주기로 묶고(tickNpcSchedules), 이미 같은 목표로 걷는 중이면 재등록을 건너뛰고, 실패한 경로는 10틱 백오프를 둔다. 백오프 상태는 WeakMap 에 두었다 — 세션 상태에 넣으면 세이브 파일로 흘러간다.
  • 시간표가 바뀌면 renderTiles 로 맵 전체 GameObject(1만~2.1만개, 25.1ms)를 파괴하고 다시 만들었다. 갱신이 필요한 것은 이벤트 계층뿐이라 refreshRuntimeEntities 를 새로 두고 그쪽을 부른다.
  • 도달 불가한 표적을 추격하는 NPC 가 매 프레임 A* 전체 탐색을 반복했다(실측 174ms/프레임/NPC). chasePathBlocked 로 표시해 재탐색 주기를 기다리게 한다. 경로가 소진돼서 빈 경우는 표시가 없으므로 예전처럼 즉시 재탐색한다 — 추격 반응성은 그대로다.

B. A* 자료구조

배열을 우선순위 큐로 쓰며 while 반복마다 sort()(O(n log n))를 돌리고 개선된 노드를 findIndex()(O(n))로 훑었다. 문자열 키 "x,y" 도 반복마다 새로 만들었다. 이진 최소힙 + 정수 키(y*width+x) + 지연 삭제로 바꿨다.

뽑는 순서가 같은 이유: 비교자 f → h → order 의 order 는 키마다 유일하므로 open 안에서 전순서다. 즉 정렬 후 shift 와 힙 pop 이 같은 노드를 뽑는다. decrease-key 는 지연 삭제로 대체했다 — 개선 노드는 g 가 반드시 더 작아 f 도 작으므로 낡은 항목보다 먼저 나오고, 낡은 항목은 pop 시점에 nodes 최신본과 다르다는 것으로 걸러진다.

맵 경계 396칸을 후보로 각각 A* 를 돌리던 최근접 탐색(150ms/프레임)은 너비 우선 1회 (nearestReachableCandidate)로 바꿨다. 한 칸 비용이 1 이므로 BFS 깊이가 곧 최단 거리다. 동률 규칙(candidates 배열에서 앞선 것)까지 예전 안정 정렬과 같고, accept 판정은 실제로 닿은 후보에만 돌려 396칸 전수 검사를 없앴다.

B2. 도달 불가는 아예 탐색하지 않는다 — 통행 성분 색인

재탐색 스로틀은 빈도만 막았다. 단발 비용은 여전히 6.7ms 였고, 갇힌 NPC 30명이면 500ms 마다 200ms 를 쓴다. 4방향 통행 그래프의 연결 성분을 색인해 도달 불가를 탐색 없이 판정한다.

정확한 판정인 근거 — canMove 는 대칭이다: 
canMove(a→b) = a.<dir>      && b.<opposite>
canMove(b→a) = b.<opposite> && a.<dir>     ← 같은 논리곱

그래서 인접 통행 관계는 무향 그래프이고, 유니온-파인드 연결 성분은 findChasePath 의 도달 가능성과 정확히 일치한다. 근사가 아니라 같은 답이다. 이 정리는 인접 쌍 300여 개로 테스트에서 직접 확인한다.

비용을 어디에 두었는지가 이 수정의 핵심이다.

  • 미리 만들지 않는다. A* 가 실제로 빈 경로를 낸 뒤 — 이미 6.7ms 를 쓴 뒤 — 에만 색인을 만든다(2.9ms). 도달 불가가 없는 맵은 값을 치르지 않는다.
  • 도달 가능 질의는 지문을 타지 않는다. 라벨 두 번 읽기로 끝난다. 낙관적으로 낸 "도달 가능" 은 틀려도 호출부가 A* 를 돌려 스스로 바로잡기 때문에 검증할 필요가 없다.
  • 결과를 바꾸는 답에만 검증을 붙인다. 낡은 색인이 낼 수 있는 위험한 오답은 "도달 불가" 하나다 — 그러면 호출부가 탐색을 건너뛰어, 벽이 열렸는데 추격을 포기한다. 그 답을 낼 때만 지문(25µs)을 확인하고 낡았으면 그 자리에서 다시 만든다.
  • 판정기를 질의당 한 번 만들어 돌려 쓴다. 후보마다 검증하면 경계 100칸 질의가 100 × 25µs = 2.5ms 로 되돌아간다(실측하고 고쳤다).

낡은 색인 대책이 두 겹이다. 런타임에서 타일이 바뀌는 유일한 지점 (applyMapOverrides)은 lowerTiles[i] 를 제자리에서 고쳐 배열 identity 로는 잡히지 않는다. 그 지점에서 명시적으로 버리고, 그와 별개로 지문 (FNV-1a, 셀당 배열 읽기 2회)이 무효화 누락을 구조적으로 막는다. 무효화 한 곳을 빠뜨려도 조용한 게임 버그가 되지 않는다.

안 덮는 것: 발자국이 1×1 보다 큰 이동. canMoveFootprint 는 이동 방향의 선행 모서리만 보므로 폭 2 이상에서 대칭이 깨진다(오른쪽으로 갈 때는 오른쪽 열, 왼쪽으로 갈 때는 왼쪽 열). pass 가 있으면 색인을 쓰지도 만들지도 않으며, 그걸 테스트로 고정했다.

C. 이벤트 뷰 질의

runtimeEventViewsForMap(...).find/some 이 질의마다 모든 맵을 훑어 전체 배열과 Set 3종을 새로 만들었다. NPC 한 명이 한 걸음 옮길 때 대각 판정으로 최대 3회 불린다. 지연 순회 forEachRuntimeEventView 하나로 모으고, 찾기 질의는 첫 일치에서 멈춘다. 다른 맵 순회는 실제로 옮겨진 이벤트가 있을 때만 한다 — 맵이 하나뿐인 프로젝트는 값을 치르지 않는다.

D. 화면 밖 타일 컬링

Phaser Container 와 root display list 에는 프러스텀 컬링이 없다. cull() 호출부는 TilemapLayer{WebGL,Canvas}Renderer 뿐이고 이 프로젝트는 Tilemap 을 쓰지 않는다. 그래서 320×240 화면에 1만~2.1만개 타일이 매 프레임 전부 드로우된다. 카메라 창 밖 타일의 visible 을 끄는 playSceneTileCulling.ts 를 추가했다.

청크 컨테이너를 쓰지 않은 이유: Container 자식은 컨테이너 안에서만 depth 정렬된다. tileLayer 안에서는 농지·설치물 오버레이와 root y-sort 가구가 depth 로 서로 끼어들기 때문에 청킹하면 그리는 순서가 바뀐다. 개별 visible 토글은 depth 규칙을 건드리지 않는다.

E. 그 외

  • runtimeDom — QA 상태 JSON 미러가 프레임마다 textContent 를 다시 썼다. 노드를 캐시하고 직렬화 결과가 같으면 쓰지 않는다. .runtime-state-json 에 content-visibility: hidden 을 걸어 레이아웃 비용을 없앴다 — 1×1 박스는 남아 Playwright toBeVisible() 과 textContent 가 그대로 동작한다.
  • tileToolbar — store.subscribe 가 칸을 칠할 때마다 툴바 전체를 다시 그렸고 거기에 projectLint(141~1206ms)가 딸려 왔다. 120ms 트레일링 디바운스.
  • mapOverlayTiles — tileStackAt/topTileInStack 이 읽는 중에 clearTileStack 을 불러 작성된 스택을 지웠다. 렌더 경로가 살아 있는 store 맵을 넘기므로 한 번 그리면 작성된 lowerTileStacks/upperTileStacks 가 undo·자동저장 밖에서 조용히 사라졌다. 읽기를 순수하게 만들었다.

3. 브라우저 증거

jsdom 테스트는 픽셀을 만들지 않으므로 컬링이 화면을 갉아먹어도 통과한다. 실제 캔버스를 찍어 확인했다.

왜 페이지 안 getImageData 가 아닌가: WebGL 캔버스는 preserveDrawingBuffer 없이 합성 뒤 버퍼가 비므로 drawImage → getImageData 가 전부 투명 검정으로 읽힌다(실측 어두운 비율 1.0). Playwright 스크린샷 PNG 를 pngjs 로 디코딩해 측정한다. 캔버스는 레터박스(좌우 검은 띠)로 감싸여 있어 전체를 재면 정상 화면도 15% 넘게 검으므로, 지도 내용이 확실한 가운데 60%만 본다. 임계값 2%.

컬링이 보이는 그림을 바꾸지 않는다 통과

60×60 체커보드 맵(TILE.GRASS / TILE.PATH). 한 칸이라도 빠지면 눈에 보인다. 카메라가 타일 경계를 여러 번 넘도록 오른쪽 8칸 + 아래 6칸 걷고, 다시 되돌아온다.

시간표를 100ms 로 묶어도 주민이 실제로 걸어간다 통과

20×20 최소 맵, 주민 1명을 (2,2) 에 두고 시간표 목표를 (12,9) 로 준다. tickNpcSchedules → registerAutonomousMover → refreshRuntimeEntities 경로만 태운다.
