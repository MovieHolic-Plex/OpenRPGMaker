02같은 단어, 반대 규약 — 두 발자국 체계

이 저장소에는 이미 “발자국” 이 있었다. 농장 건물·집 장식을 놓는 SpatialFootprint 다. 그쪽은 (x,y) 가 좌상단이고, 캐릭터는 발이 땅에 닿아야 하므로 (x,y) 가 하단 행의 칸이다. 이름을 다르게 둔 이유가 이것이다.

03짝수 폭만 중심선이 칸 경계로 간다

발자국의 왼쪽 끝은 left = x − ⌊(width−1)/2⌋ 다. 홀수 폭에서는 앵커 칸 중앙이 그대로 중심선이라 characterSpriteX 와 값이 같고, 짝수 폭에서만 두 칸 경계로 간다. 그래서 footprintSpriteX 가 따로 필요하다.

이 계약을 지키는 테스트가 없었다.
기존 통행 테스트는 전부 홀수 폭(3) 이었다. 홀짝이 갈리는 곳은 왼쪽 모서리 하나뿐이고 (폭 2 는 left = x, 폭 3 은 x−1), 오른쪽은 둘 다 x+1 이라 우향 이동으로는 구분이 안 된다. left 를 x − ⌊width/2⌋ 로 잡는 흔한 오구현을 넣어 확인해 보니 기존 8개 테스트가 전부 통과했다 — 1x1 전수 스윕과 3x3 선행모서리 테스트까지 포함해서. 짝수 폭 좌향 이동 테스트를 추가해 막았다 (eb530e1c).

04히트테스트를 점에서 사각으로 올렸다

기존 코드는 event.x === x && event.y === y 로 이벤트를 찾았다. 발자국이 커지면 질문이 “점이 이벤트 좌표와 같은가” 에서 “두 사각이 겹치는가” 로 바뀐다. 원본을 사각 질의로 바꾸고 점 질의를 얇은 래퍼로 남겨서, 기존 호출부 30여 곳을 하나도 고치지 않았다.

승격 대상을 세는 과정에서 계획이 다섯 곳이라고 한 것이 실제로는 일곱 곳이었다. 그중 facingPrompt 는 1차에 포함시켰다 — 승격하지 않으면 2x2 골렘을 네 칸 어디서나 말은 걸 수 있는데 “조사” 프롬프트는 앵커를 볼 때만 떠서, Z 는 먹지만 UI 는 침묵하는 상태가 된다. 나머지 하나 (findGiftTargetEvent, 시나리오 테스트 하네스) 는 사용자 노출면이 없어 2차로 넘겼다.

05비용은 면적이 아니라 한 줄이다

발자국 전체를 매 걸음 훑으면 면적에 비례해 비싸진다. 실제로 새로 밟는 칸은 진행 방향의 선행 모서리 한 줄뿐이다.

06워프 착지 — 안 맞으면 밀어낸다

3x3 이 딱 안 맞는 목적지로 워프하면 벽에 박힌다. 체비쇼프 거리 순으로 나선 탐색해 가장 가까운 유효 칸으로 밀어낸다. 링 안에서는 모든 칸이 등거리라 방출 순서 자체가 계약이고, 그래서 테스트로 못박았다.

1x1 은 검사하지 않고 그대로 착지시킨다.
일부러 그렇게 뒀다. 기존 transfer 는 통행 불가 칸에도 강제 착지하고 컷신 배치가 실제로 그걸 쓴다. 여기에 검사를 걸면 기존 게임이 깨진다. 이 함수는 아직 아무도 호출하지 않는다 — 배선은 2차다.

07브라우저 증명 — 사람이 아니라 시나리오가 걸었다

계획서는 완료 기준 4(막히고 네 방향에서 말이 걸린다)를 사람이 --headed 로 직접 걸어보는 것으로 검증하게 했다. 런타임 QA 시나리오로 자동화했고, 하네스를 커밋해 재현 가능하게 남겼다. 골렘은 30x30 맵 앵커 (15,18), 배율 2, 발자국 (15,17) (16,17) (15,18) (16,18).

판별력이 있는 프로브와 없는 프로브

08반 타일 차이는 눈이 아니라 숫자로 잡았다

0.5 타일은 스크린샷으로 판정할 수 없다. 렌더된 스프라이트의 월드 좌표를 직접 읽었다 (TILE_SIZE = 16).

1x1 NPC 5개:  x = 232, 232, 168, 296, 328   → 전부  x mod 16 == 8   (타일 중앙)
골렘 2x2:     x = 256                        →       x mod 16 == 0   (타일 경계)

footprintSpriteX(15, {width:2,height:2}) = (15 + 1) × 16 = 256   ← 실제 값
characterSpriteX(15)                      = 15 × 16 + 8   = 248   ← 1x1 이었다면
차이 = 8px = 정확히 반 타일

골렘만 유일하게 경계에 있고, 나머지는 예외 없이 칸 중앙이다. y = 304 = characterSpriteY(18) 이고 원점이 setOrigin(0.5, 1) 이라 스프라이트는 발밑에서 위로 자란다 — 발이 땅에 파묻히지 않는다.

스프라이트 박스와 발자국은 일부러 다르다.
골렘의 그림은 3x4 칸을 덮고 발자국은 2x2 다. 발자국은 충돌 개념이고 배율은 렌더 개념이라 스펙에서 독립으로 뒀다. 24x32 를 2배한 48x64 라 뭉개져 보이는 것도 정상이고, 스펙의 후속 과제로 적혀 있다.

09회귀 게이트를 통계에서 인과로 바꿨다

공유 머신에서 npm test 전체는 실패 파일이 85–99 개로 흔들렸다. 기준선이 88 개니까 ±11 의 잡음 안에서는 진짜 회귀를 구분할 수 없다. 그래서 변경 지점의 호출자에서 역산했다.

  • 바뀐 함수 다섯 개의 src/ 호출자를 grep — playSceneMovement.ts, 시나리오 테스트 하네스 testing/sceneTestRunner.ts(테스트 25개가 그 뒤에 있다), sealReachability.ts
  • 그 경로를 덮는 스위트를 모으고, 기준선에서 초록인 것만 남겼다 — 하나라도 빨개지면 무조건 우리 탓이 된다
  • 결과 28 파일 / 318 테스트, 15초. 6분짜리 전체 스위트보다 빠르고, 통계가 아니라 인과라서 결정적이다

타입체크도 이진 게이트가 아니었다. 전체 npm run typecheck 는 이 브랜치에 기존 에러 574개가 있다. 총계는 기준선과 정확히 같고, 이 계획이 만진 20개 .ts 파일의 에러는 0 이다. typecheck:app 은 tsconfig.app.json 이 test 를 제외하므로 테스트 파일을 한 번도 검사하지 않는다 — 두 게이트를 같이 봐야 하는 이유다.

11내가 틀렸던 것

판별력 있는 프로브를 셋이라고 했는데 둘이었다.
footprintBounds(15,18,{2,2}) 의 앵커는 발자국의 좌하단 칸이다. 그래서 아래쪽 프로브 (15,19) → (15,18) 은 왼쪽과 똑같이 앵커를 겨냥하고, 판별력이 없다. 구현자가 값을 조용히 바꾸지 않고 보고한 뒤 변형 둘을 추가했다.
헛통과 테스트를 스스로 지시했다.
이 계획에서 “이름은 검증인데 실제로 아무것도 못 잡는 테스트” 가 네 번 나왔다. 함수를 자기 자신과 비교한 56좌표 스윕, 순수 함수를 두 번 불러 결정성을 주장한 테스트, 입력이 애초에 먹지 않는 headless 에서 “안 움직였다” 를 단정한 것, 그리고 마감 리뷰가 잡은 네 번째 — 발자국을 인자로 받지도 않으면서 “발자국 높이와 무관하다” 를 주장한 내 테스트(§12). 처음 둘은 계획서 결함이었지만 나머지 둘은 내가 그 함정을 감시하던 중에 내가 쓴 것이다. 교훈은 “계획서를 잘 읽자” 가 아니라, “아무 일도 없었다” 형태의 단정에는 무언가 일어날 수 있었음을 증명하는 대조군이 반드시 필요하다 는 것이다.
주석에 줄번호를 인용했다가 그 주석 때문에 밀렸다.
경계를 표시하는 주석 초안이 :805 :811 식으로 줄번호를 인용했는데, 주석 세 줄을 넣는 순간 인용된 번호가 전부 +3 밀렸다. 함수 이름으로 바꿨다. 계획서의 줄번호가 이미 한 번 밀렸던 것과 같은 종류의 실수다.

12마감 리뷰가 잡은 것 — 이 브랜치가 새로 만든 결함 하나

브랜치 전체를 두 리뷰 에이전트에 독립으로 걸었다. 이미 판정된 것을 재발견으로 올리지 말라고 지시했고, 실제로 새로 나온 것은 하나다 — 그리고 그건 이 브랜치가 열었다.

사각으로 찾은 이벤트를 앵커 점으로 돌려세우고 있었다.
히트테스트는 §04 에서 사각으로 올라갔는데, 그 결과를 소비하는 directionTowardPlayer 의 방향 계산은 앵커 델타 그대로였다. 골렘 앵커 (15,18), 발자국 (15,17)(16,17)(15,18)(16,18) 에서 플레이어가 (16,19) 에서 (16,18) 을 조사하면 델타가 (1,1) 이 되고, facingForDelta 는 |dx| ≥ |dy| 에서 가로를 우선하므로 "right" 가 나온다 — 플레이어가 정남향에 있는데 골렘이 옆을 본다.

승격 전에는 (16,18) 이 빈 칸이라 이 경로에 닿을 수조차 없었다. 그리고 커밋된 하네스의 down-alt 프로브가 정확히 이 입력을 지나가는데, 시나리오가 방향을 단정하지 않아 초록으로 통과했다. 2차로 넘기지 않고 여기서 고쳤다(§10 판정 23) — 플레이어 위치를 발자국 사각에 클램프해(nearestCellInRect) 최근접 칸에서 델타를 뽑는다. 1x1 에서는 사각이 그 칸 자신이라 클램프가 항등이다.

이미 내린 판정을 뒤집는 것이기도 하다. 태스크 4 리뷰는 이 줄을 보고 "directionTowardPlayer 는 앵커를 원하는 것이 맞다" 로 기록했다. 어느 이벤트인가 를 고르는 데는 앵커가 맞고, 어느 방향인가 에는 틀리다. 짝수 폭·다행 발자국에서 앵커는 최근접 칸이 아니다.

같이 닫은 것

  • 비정규 발자국의 fail-open — 폭 0 이 들어오면 footprintBounds 가 left > right 인 역사각을 만들고, 파생 셀 루프가 0회 돌아 통행 검사가 실행되지 않은 채 통과했다. 실측으로 canMove 는 벽에서 false 인데 폭 0 을 넘긴 canMoveFootprint 는 true 였다. 호출부마다 가드를 넣는 대신 파생의 뿌리인 footprintBounds 에서 축을 1로 굳혔다 — 통행 판정은 열리는 쪽보다 닫히는 쪽으로 실패해야 한다
  • footprintCells 이름 충돌 — spatialPlacements.ts 도 같은 이름을 export 하는데 앵커 규약이 반대다. 스펙 §1 은 normalizeFootprint 라는 이름을 모듈 사설 동명 함수 때문에 거부했었다. export 대 export 는 그보다 강한 사례라 characterFootprintCells 로 바꿨다
  • "검증" 이라는 이름의 빈 테스트 하나가 내 테스트에도 있었다 — "Y 는 발자국 높이와 무관하다" 가 발자국을 인자로 받지도 않고 있었다. 높이를 실제로 바꿔가며 단정하도록 고쳤다. §11 이 말한 그 패턴이다
  • QA 대조군 주석 — "구조적으로 배제한다" 고 적혀 있었지만 evaluateExpect 는 x/y 스칼라 동등만 지원해서 "움직였다" 를 표현할 수 없다. 공유 하네스를 고치는 대신 문구를 사실대로 고치고 2차 항목으로 남겼다. 대조군의 끝 좌표를 하드코딩하는 안은 기각했다 — 이동이 시간 기반이라 (15,21) 은 타이밍 산물이고, 그걸 단정하면 깜빡이는 테스트가 된다
변이 검증 중에 내가 그 금지를 어겼다.
각 수정이 실제로 결함을 잡는지 확인하려고 변이를 넣고 git checkout -- <file> 로 되돌렸는데, 그건 HEAD 로 되돌리는 명령이라 아직 커밋하지 않은 수정 두 파일이 통째로 날아갔다. 이 브랜치의 판정 7·14 가 정확히 이걸 금지하고 14 는 대체 기법(Edit 으로 되돌리기)까지 적어 뒀는데, 그걸 쓴 사람이 어겼다. 재적용하고 4스위트 69테스트를 다시 초록으로 확인했다. 변이 결과 자체는 유효하다 — safeAxis 를 지우면 4개, 앵커 델타로 되돌리면 3개가 실패한다. 기록하는 이유는 이게 이 브랜치에서 세 번째이고, 같은 명령을 형제 워크트리에 썼다면 다른 세션의 미커밋 작업이 복구 불가로 사라졌을 것이기 때문이다. 금지는 규칙이 아니라 반사로 있어야 한다: 변이 전에 커밋하거나, Edit 으로 넣고 Edit 으로 뺀다.

132차로 넘긴 것

1차는 “발자국을 가진 이벤트” 까지다. “발자국을 가지고 움직이는” 것과 “발자국을 저작하는” 것은 2차다.

  • 이벤트 편집창의 크기·배율 입력 UI, 맵 위 발자국 외곽선, 겹침 경고 배지 — 지금 EventPage.footprint 를 쓰는 편집 UI·AI 경로·툴이 하나도 없다. src/editor/ 의 footprint 는 전부 좌상단 기준의 다른 체계다. 즉 다중 타일 이벤트는 JSON 직접 편집으로만 만들 수 있다
  • 움직이는 이벤트 스프라이트의 발자국 중앙 정렬 — footprintSpriteX 는 renderEvents 의 최초 배치에만 걸려 있고, 스프라이트를 다시 놓는 updateAutonomousNPCs·updateChaseNpc·updateActiveNpcMove· applyKnockback·startWindup·stepDash 는 전부 타일 중앙으로 되돌린다. 일괄 치환은 오답이다 — 전투 파일 13개 호출 중 스프라이트 재배치는 5개뿐이고 데미지 숫자·파티클·텔레그래프·스윙 아크는 타일 중앙이 맞다. canMoveFootprint 전환과 같은 작업 묶음이다
  • 플레이어 발자국 (기본값 + 세션 필드 + 세이브 화이트리스트 3곳 + 왕복 테스트)
  • resolveFootprintLanding 을 transfer 경로에 배선, 필드 스폰 발자국, 팔로워 배율
  • NPC 자율이동·추격 경로탐색의 canMoveFootprint 전환
  • 발자국이 겹칠 때의 우선순위 규칙 — 지금은 .find 의 배열 순서가 사실상의 규칙이다. 스펙은 겹쳐 놓는 것을 허용하는데 어느 쪽이 잡히는지는 정의돼 있지 않다
  • handleAction 의 lastActionTargetKey 가 이벤트 단위에서 타일 단위로 격하됐다 — 다중 타일 이벤트가 제자리 회전만으로 재발동할 수 있다
  • sceneTestRunner.ts 의 findGiftTargetEvent 점 비교 승격
  • 저작 시점 lint 가 틀린 조언을 낸다 — projectLint.ts 는 앵커 칸의 통행성과 앵커의 4방 이웃만 봐서 벽을 파고든 2x2 가 무경고로 통과하고, 중복 검사 키가 ${event.x},${event.y} 라 겹친 2x2 둘을 못 잡는다
  • QA 하네스에 이동 단정 수단이 없다 — evaluateExpect 가 x/y 를 스칼라 동등으로만 비교해서 대조군의 “움직였다” 를 표현할 수 없다. 부등 비교를 넣으면 닫히는데 다른 시나리오가 공유하는 파일이라 1차에서 손대지 않았다(§12)
  • 에디터·내장 플레이어의 클릭 히트테스트 — 2x2 의 비앵커 칸을 클릭하면 선택이 아니라 그 위에 새 이벤트가 생긴다. 마감 리뷰가 센 것으로 약 25곳
