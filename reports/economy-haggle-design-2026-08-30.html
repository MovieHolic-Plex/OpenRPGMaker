02 · 조사

네 원형, 고른 건 하나

재미의 단위가 다르다. 시세 시뮬이 아니라 한 손님과의 제안이 한 판인 쪽을 골랐다.

A · 정적 가격

Stardew Valley

시장이 없다. Pierre 매입가는 시즌·작물 고정. 재미는 시간·타일·에너지 대비 이윤. 배송 상자는 하루 정산. rpg-zzu는 이 층을 이미 갖고 있다 (DAY_TRANSITION_STAGES 9단, dayTransition.ts:23).

B · 채택 · 손님 단위 흥정

Recettear / Potionomics / Moonlighter

플레이어가 가격을 부른다. 실패하면 손님이 산다. Wikipedia: ineffectively bargaining will cause the buyer to leave without purchasing anything. 기존 applyHaggleDiscount는 확정 ≤15% 할인이라 최적 전략이 「항상 흥정」이다. 그래서 버린다.

C · 지역 스프레드

대항해시대 · 수호전 교역소 · Mount & Blade

같은 물건의 가격이 장소마다 다르다. 무역로·재고가 가격을 민다. 맵·지역 경제 저작이 먼저 필요하고, 초보 작가가 돈복사 루프를 만들기 쉽다.

D · 공급자·점유율

대항해시대 온라인 · 왕국 경영

플레이어가 시장 점유를 움직인다. 제작기 규모에 비해 피드백 주기가 길고, NPC 에이전트 경제와 붙으면 프레임 예산을 먹는다.

돈복사 방어는 밸런스가 아니라 구조다. sell < buy, 상인 골드 유한, 그 거래를 이용한 가격은 그 거래가 움직인다, 인덱스 클램프 + 평균회귀, 결정론으로 세이브 스컴 무효.

03 · 흥정 코어

임계값. 주사위 없음.

DOM 없음, RNG 없음. src/project/haggle.ts 한 파일. 같은 입력은 세이브/로드 왕복 뒤에도 같은 판결.

export type HaggleRole = "playerBuys" | "playerSells";
export type HaggleMood = "open" | "wary" | "cold";

export type HaggleSetup = {
  readonly role: HaggleRole;
  readonly reference: number;   // 구매=정가, 판매=되팔기가
  readonly reserve: number;     // 상대 한계선 (숨김)
  readonly patience: number;    // 남은 제안 횟수
  readonly insultRatio: number; // 넘으면 즉시 결렬
};

export type HaggleVerdict =
  | { readonly kind: "accept";  readonly price: number }
  | { readonly kind: "counter"; readonly price: number; readonly patience: number; readonly mood: HaggleMood }
  | { readonly kind: "broken";  readonly reason: "insulted" | "exhausted" };

// playerBuys : offer >= reserve → accept
// playerSells: offer <= reserve → accept
// reserve = hash(itemId, merchantKey, dayKey, attemptIndex) 로 지터
// reserve(n+1) = reserve(n) + role_sign × drift × aggression(n)
// aggression(n) = |offer(n) − reference| / reference
// mood는 수락을 막지 않는다. 다음 예비선을 플레이어에게 불리하게 민다.

기분으로 수락을 막으면 「1G씩 찔러 보기」가 최적이다. 예비선이 공격성에 비례해 달아나게 해서 그 전략을 죽인다. 확률 롤은 세이브 스컴을 최적 전략으로 만든다.

저작ShopHaggleConfig { patience?: 1..5 기본 3; insultRatio?: 0.4..0.9 기본 0.6; maxDiscount?: 0..0.4 기본 0.25; skillId?; reactionSetId? }. 맨 boolean haggleEnabled: true 는 기본값. 목업 v3 「흥정 허용」 슬롯이 펼쳐진다.
뷰ShopView = "menu" | "items" | "haggle" (현재 playSceneShopDom.ts:36 은 menu|items 뿐)
거래handleShopTransaction(..., agreedPrice) — 지금은 item.price / sellPrice(item) 고정 (playSceneShop.ts:334, :348)
세션shopHaggleState?: Record<string, { patience: number; drift: number; broken?: boolean }> — sanitizeEconomyRecord 패턴 (economyValues.ts:26, saveSlots.ts:302)

07 · 단계

P0는 방향과 무관하다

AskUserQuestion에서 공통 전제로 박은 것. 흥정을 골라도 가격 함수부터 한 줄로 모은다.

P0 · 잇기

죽은 장부를 가격에 연결

resolvePrice() 단일화. loyalty 할인 · dynamic markup · restock를 읽게. shopPawnTickets / shopLastRestockDayKey는 구현하거나 삭제. 어중간한 sanitize-only 필드를 남기지 않는다. 편집기에 목업 v3 토글 슬롯을 실제 필드로.

P1 · 흥정

코어 + 상점 뷰 + 5 테스트

haggle.ts 순수 코어. 상점 haggle 뷰. 저작 토글 4숫자. 불변식 1–5. 기존 applyHaggleDiscount는 삭제 또는 코어로 대체 — 확정 15% 할인으로 남기면 안 된다.

P2 · 가게 주인

역할만 뒤집힌 같은 코어

kind: "shopkeeper", 손님 큐, 선반, 평판. Recettear 본편. 코어가 양방향에서 증명된 뒤에만. 손님 AI 경제·초 단위 시세는 넣지 않는다.

08 · 안 하는 것

구조로 막는 세 가지

NPC 에이전트 경제 — updateNpcSchedules 프레임마다 A*가 예산을 태운 전례가 있다. 상점 흥정은 대화 한 판이다.
초 단위 시세 — 읽을 수 없다. 하루 경계 9단 트랜잭션이 이미 있다.
통화량 인플레 — 재미가 없고 작가가 원인을 못 본다. inflationFactor 필드는 선언만 있고, P0에서 삭제 후보.
