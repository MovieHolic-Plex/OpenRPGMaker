## 화풍 기준은 후보 칩셋의 묶음으로 (2026-10-23)

**문제:** `review` 의 화풍 반쪽은 칩셋과 상관없이 늘 버들항 기준 그림(`style-refs/<종류>`)과 견줬다. 그래서 jp_city·마법 학교 계단처럼 그 칩셋에서는 정상인 윤곽·명암 방식이 「근흑 윤곽·명암 단계 부족」으로 떨어졌다(#3270 jp 실내 계단 13, #3264 마법 학교 계단 6). 그림의 결함이 아니라 관문의 빈틈이다.

**바꾼 것:**
- 칩셋 묶음 `harness-data/object-gate/style-refs/sets/<칩셋>/<종류>/<이름>.png` + `manifest.json` 을 `tools/build_style_ref_sets.py` 가 **그 칩셋 번들에 이미 실린 그림**(키트·바닥/벽 타일 그룹)에서 만든다. 지금 묶음: `jp_city` · `wizarding_world` · `atlas_biome_interior` · `joseon_baram` · `modern_city`(별칭 `modern3`). 계단 키트는 기준으로 고르지 않는다. 별칭은 `sets/aliases.json`.
- 후보의 칩셋 = 묶음 항목 `chipset`(또는 `review --chipset`), 없으면 라벨 앞머리(첫 `/`·공백 앞, 예: `jp_city/interior/…`, `wizarding_world stairs …`).
- 그 칩셋 묶음에 같은 화풍 종류가 있으면 그것과 견준다. 판정자 문구는 「이 칩셋 출하본이 이 후보의 기준이다 — 지시문의 Beodeul 을 이 기준 그림으로 읽어라」를 덧붙인다.
- 묶음이 없거나(`beodeul_dungeon` 은 아직 번들 시트가 없다), 칩셋을 모르거나, 그 묶음에 그 종류가 없으면 **버들항 묶음으로 떨어진다**. 영수증에 이유가 남는다.
- **영수증** `style.refSet = { id, chipset, fallback, reason?, hash }` — 어느 묶음으로 판정했는지. 이 필드가 없는 옛 영수증은 버들항으로 판정한 것이다. 버들항이 아닌 묶음으로 판정해야 하는 그림은 옛 버들항 영수증을 재사용하지 않고 다시 판정한다.
- **바꾸지 않은 것:** 임계값·판정자·표 수·3/4 지시문·화풍 지시문·보정 프로필. 프로필 해시(`gateProfile`)는 버들항 묶음 매니페스트에만 묶여 그대로 `4d8774b517f41638` 이다. `calibrate` 는 늘 버들항 묶음으로 돈다. 칩셋 묶음의 화풍 답 캐시 키에는 묶음 해시가 섞인다.
- **버들항 판정 불변 확인:** 버들항 묶음 경로는 문구·기준 그림·답 캐시 키가 바이트까지 예전과 같다. 기존 영수증 695장(버들항·대체)의 기준 그림 목록이 새 코드와 모두 같았다. 버들항 문구로 받아 둔 답 캐시가 있는 jp 계단 12장을 `--chipset beodeul_city --offline` 으로 다시 셌더니 예전 영수증과 판정이 모두 같았다(PASS 2 · FAIL 10).
- 2026-10-14 결정(「모든 칩셋의 품질 기준 = 버들항」, 아래 v9 절 끝)은 이 절로 대체된다. Opus 최종 판정(`final.mts`)은 v8 부터 같은 칩셋 앵커를 따로 쓰고 있어 바꾸지 않았다.
- 새 칩셋 묶음을 더하려면 `build_style_ref_sets.py` 의 `SETS` 에 출하 키트·타일 그룹을 넣고 다시 돌린다. 프로필은 바뀌지 않는다.
- 새 단계 플래그: `review --chipset <칩셋>` · `--no-write`(영수증을 쓰지 않음) · `--offline`(답 캐시만 사용) · `preview --chipset`(비교판 묶음 확인).

## 공방 「한 번에 만들기」 단계 `workshop` (2026-10-23)

편집기 공방의 「한 번에 만들기」 물건은 칩셋에 굽기 전에 이 관문을 지난다. 사람에게 관문을 보이지 않는다(사용자 규칙) — 결과만 「넣음/못 그림」.
- 입구: `bun src/harnesses/object-gate/node/judge.mts workshop --png <후보> --kind <종류> --name <이름> --label workshop/<…> [--chipset <칩셋>]`.
  호스트(동반 서비스 `scripts/lib/workshopGate.mjs`, `POST /v1/workshop/gate` → `GET ?jobId=`)가 사용자 컴퓨터의 Claude Code 로그인으로 띄운다. 판정자는 프로필 그대로(Sonnet 5.5 high ×4, 3/4 + 화풍).
- 판정 = 영수증 `verdict` 그대로. **PASS → 넣음. REFER → 같은 판정자 새 호출 한 번(`referCheck`, 적대적 — pass 이고 `sure` 일 때만 통과)이 정한다. FAIL → 판정 근거(`fix`: 이유 + 3/4·화풍 판정자 근거)로 한 번 다시 그리고, 그래도 아니면 「못 그림」.**
  임계값·표 수·판정자·프로필은 바꾸지 않았다. 프로필이 미보정이라 이 영수증은 「보정된 관문 통과」가 아니다 — 굽기 기록(`spec.gate`)에 판정·해시·프로필을 그대로 남긴다.
- 영수증은 저장소가 아니라 `~/.cache/oprn/workshop-gate/receipts/<sha2>/<sha>-<kind>.json`(`OPRN_WORKSHOP_GATE_RECEIPTS`)에 쓴다. 같은 화소·같은 프로필이면 다시 부르지 않는다.
- 속도: 한 판 안에서 눈 판정(eye) 답을 화소 해시·회차·종류로 나눠 쓴다(`shareEyeAnswers` — 보정과 같은 뜻) → 호출 20 → 11. 실측 한 장 18~32초(REFER 검사 포함).

- 입력(한 호출): 3/4 안내 그림 · 실제 위반/정상 쌍 · 이 호출의 화풍 종류별 버들항 기준 그림(1배 + 확대) · 후보마다 번호판(1배 + 최대 8배, 1화소 격자·4행마다 밝은 선). **한 호출 6장**, 같은 화풍 종류끼리, 같은 해시는 한 호출에 한 번.
- **3표 만장일치:** 표마다 다른 묶음 섞기로 따로 부른다. 세 표가 모두 pass 일 때만 pass. 앞 표가 fail 이면 뒤 표는 부르지 않는다(비용). 규칙 v2(한 표)는 같은 위반 그림이 판마다 통과·불합격으로 뒤집혔다.
- 규칙이 답을 다시 확인한다(`decideFinal`): kind_ok · 3/4 pass · 화풍 pass · 혐의 0 · sure — 하나라도 아니면 fail.
- 답 캐시 `~/.cache/opus-gate/answers/<프로필>/<해시>-<종류>-<화풍종류>-v<표>.json`(저장소 밖, 중단 후 같은 명령으로 이어 감).

### 저장소 위치 — 개별 저장소 `MovieHolic-Plex/object-gate` (2026-10-20 분리)

위 네 경로의 공유 정본은 비공개 저장소 `MovieHolic-Plex/object-gate`(로컬 체크아웃 기본 `~/z-project/object-gate`, 다른 곳이면 `--repo`·`OBJECT_GATE_REPO`)다.
`git filter-repo` 로 네 경로의 이력(72커밋, 파일 9,183개)을 그대로 옮겼고, 분리 시점 트리 해시가 이 저장소 `a9a8b5456` 과 네 경로 모두 같다.
object-gen·char-gen·스토어가 같은 관문·같은 영수증을 쓰려고 뗐다.

이 저장소는 **같은 경로에 바이트 그대로 사본**을 둔다(vendored). 그래서 `npm run harness -- object-gate …`, 굽기 스크립트의 `require_pass`,
스토어 관문(`scripts/store/agentStore.mts`), `serve-holds`(18323), `gate_kinds.enforce` 등 호출자는 하나도 바뀌지 않았다.

| 할 일 | 명령 |
|---|---|
| 두 쪽이 같은지 | `npm run object-gate:sync -- status` (같으면 exit 0, 차이 1, 충돌 2) |
| 여기서 병합된 관문 변경을 올리기 | `npm run object-gate:sync -- export --push` — 항상 `origin/main` 을 내보낸다(미병합 커밋은 안 나간다) |
| 그 저장소에서 바뀐 것 들이기 | `npm run object-gate:sync -- import` → 커밋 → PR → 병합 → `export` |

- 경로마다 3-way 다. 기준은 그 저장소의 `.monorepo-sync`(마지막으로 내보낸 이 저장소 `origin/main` 커밋). 한쪽만 바뀐 것만 옮기고, 양쪽이 다르게 바뀌면 멈춘다.
- 스크립트는 git blob 을 그대로 옮긴다. 영수증·승인·보류 결정은 그림 화소 해시·서명에 묶여 있으니 손으로 고치지 않는다.
- 보류 승인 서명 키(`~/.config/oprn/object-gate-hold.key`)는 두 저장소 어디에도 넣지 않는다.
- 판정(`review`·`calibrate`)은 아직 이 저장소 안에서만 돈다. 판정기가 `src/assets/bundled`·`_core/manifest`·재검수용 `tiledata` 를 import 하기 때문이다.
  다른 도구는 그 저장소 체크아웃에서 `OBJECT_GATE_DATA=<체크아웃>/harness-data/object-gate` 로 영수증을 읽고, Python 은 `<체크아웃>/src/harnesses/_core` 를 `sys.path` 에 넣어 `require_pass` 를 쓴다.
- 왜 사본인가: 네 경로가 흩어져 있어 서브모듈 하나로 덮을 수 없고(심링크+서브모듈이면 `wt create`·기존 워크트리 수십 개가 초기화 전까지 깨진다), 판정기가 이 저장소 모듈을 import 해서 npm/pip 패키지로 떼려면 판정기를 고쳐야 한다(프로필 해시·진행 중 보정과 충돌). 영수증을 커밋하는 PR 흐름(#3107 등)도 그대로 둔다.

## 2026-10-14 개편 — 한 번에 3/4 + 버들항 화풍

한 번의 판정(규칙 v4)이 A 3/4 시점 · B 버들항 화풍 둘을 함께 정한다. 둘 다 통과해야 통과이고, 영수증은 두 판정(`view34`·`style`)과 보조 지표(`metrics`)를 그림 해시·프로필 해시에 묶는다.

- **화풍 비교:** 판정자는 같은 종류의 버들항 기준 그림(`harness-data/object-gate/style-refs/`, `beodeulCityTileset.json` 키트·타일 묶음에서 뽑음)을 같은 배율(2배)로 후보 옆에 놓은 판(`preview` 가 `.board.png` 로 저장)을 본다.
  보는 것: 명암 단계(버들항 약 5~6), 윤곽색(이웃 재질의 어두운 색이지 거의 검정이 아님), 질감 점·결, 칸당 정보량, 평면 채움. 테마마다 잠긴 팔레트는 그대로 두고 구조·명암만 본다 — 버들항 색을 요구하지 않는다. 화풍 반쪽은 동률이면 탈락(≥ 절반 fail).
- **숫자 지표는 보조:** 칸당 고유색 중앙값(버들항 10, p90 약 44)·어두운 5% 밝기·거의 검정 윤곽 비율. 통과 근거가 아니다.
- **429:** 계정 한도 429 는 표로 세지 않고 `Resets in` 만큼 기다려 다시 부른다. 병렬 호출은 최대 4.
- **프로필 해시** = 규칙 상수 + 화풍 기준 매니페스트 해시 + view34-guide 해시. 답 캐시 키(프롬프트 해시)는 규칙 숫자를 빼므로 임계값만 바꾸면 `calibrate --offline` 으로 모델 없이 다시 계산한다.

object-gate 는 **지도 위에 놓이는 3/4 기물·건물·지형 조각**의 관문이다. 종류는 부르는 쪽이 정하고 판정자가 과반이 아니라 **4번 중 3번 이상**이 「종류가 맞다」고 해야 면제 종류(`flat`·`terrain`·`organic`·`debris`·`wall_mounted`)가 통과한다(2:2 는 refer). 면제는 시점 규칙을 건너뛸 뿐 화풍 반쪽은 그대로다.
- 전투 이펙트·초상·얼굴·트레이너/몬스터 전투 도트·월드맵 아이콘·RM2000 캐릭터 칩(Actor1 프레임)은 지도 기물이 아니므로 3/4 규칙의 대상이 아니다. 각자의 **사람이 고르는 하네스**(`charset-actor`·`monster-collect-species`·`worldmap-icons`·`pixel-fx-animation`)가 정본 관문이고, 거기서 사람이 고른 현재 그림 해시만 굽는다. 이 그림을 `flat`/`other` 로 억지로 object-gate 에 넣어 통과시키지 말 것(면제 종류 판정이 종류 불일치로 막는다).
- 같은 그림이 **지도 기물로 번들·공용·스토어에 구워지는 순간** object-gate 영수증이 필요하다(예: 트레이너 NPC 가 아니라 맵에 놓이는 입상·소품).
- 사람 확인 필요(refer)는 어떤 자동 출구도 통과시키지 않는다. 그림을 더 분명하게 고치거나, 사람이 고르는 하네스 경로·공방 로컬 「그래도 넣기」를 거친다.

  - 서명 대상에 `delegatedBy`·`evidence` 는 위임 기록에서만 들어간다 — 사람 기록의 서명 문자열은 그대로라 기존 기록이 유효하다. `schema` 이름도 그대로다.
  - 출구 효력은 사람 허용과 같다: TS `humanDecision`·Python `human_decision` 이 서명 확인, 그림 해시·종류 일치, 비어 있지 않은 `delegatedBy`·`evidence` 를 요구한다. 거절 위에 올라서지 못하고, Opus 최종 판정이 있는 그림에는 사람 허용과 똑같이 효력이 없다. 검토 화면은 「허용됨(위임)」과 위임자를 보여 준다.
  - **소급 기록은 고치지 않는다.** 2026-10-21 이전에 감독자가 위임받아 검토 API 로 넣은 허용(beodeul-dark-grass-r9 묶음, inaka-handpixel-r14 묶음, astra-centre-mart-kits 묶음 등)은 `by: "human"` 으로 남아 있다. **`note` 에 「delegated by user to supervisor 2026-10-21」 가 들어 있는 기록은 사람 클릭이 아니라 위임이다.** 감사할 때는 이 문구로 가려라(서명이 걸려 있어 `by` 를 사후에 고칠 수 없다).
  - **정정 단계(2026-10-22):** `object-gate redelegate-holds --sha a,b --delegated-by X --evidence <영수증>` 은 `note`/`decidedBy` 에 이미 「delegated by user」가 적힌 `by:"human"` 허용만 `by:"delegated"` 로 바꿔 다시 서명한다(노트에 정정 사유 덧붙임). 버들항 성벽 그림 6장(r4 다섯·r5 하나)을 이것으로 옮겼다. 다른 소급 기록은 아직 그대로다.
  - **물러남(superseded):** `object-gate supersede-holds --sha … --by <새 그림 해시|설명> [--at ISO]` 는 허용 기록에 `supersededBy`·`supersededAt` 을 서명해 넣는다. 물러난 허용은 TS·Python 출구에서 효력이 없고(거절은 거절 그대로), 대기열에서 빠지며 `/api/decide` 가 거절한다. 화면은 「물러남(다시 그림: …)」. 그림을 다시 그려 해시가 바뀌면 옛 허용을 이것으로 표시한다.
- 손으로 쓴 기록이나 고친 기록은 서명이 맞지 않아 없는 것과 같다. 키가 없는 다른 기계에서는 모든 승인이 무효다. 굽기는 이 박스에서 한다.

**서버 확인 사항:**
- 다른 하네스 고르기 화면과 같이 세션 쿠키와 CSRF 머리글이 맞아야 하고, Origin 이 같은 출처여야 한다.
- 요청한 해시의 보류 영수증이 있어야 하고, 그 영수증이 현재 프로필이어야 한다.
- **해시 확인:** review 가 보류 영수증과 함께 저장한 그림(`held-images/<해시>.png`)을 서버가 다시 재서 요청 해시와 같아야 한다. 화면에 보인 그림이 곧 결정이 묶이는 그림이다.
- 그림 저장이 생기기 전에 만든 옛 보류는 같은 그림으로 review 를 다시 돌리면 캐시 영수증이라도 그림이 저장된다(모델 호출은 없다).

**출구 규칙**(TS `objectGateRefusal` 의 `hold` 입력 = Python `refusal`):
- 영수증이 refer 이고, 서명이 맞는 기록이 decision allow 이며, 해시·프로필·종류가 영수증과 같을 때만 모든 출구에서 통과한다.
- 거절 기록이나 무효 기록이면 지금처럼 보류(차단)다.
- 프로필이 보정되지 않았으면 허용이 있어도 막힌다. 승인은 프로필 효력을 만들지 않는다.
- 그림이 한 화소라도 바뀌거나 프로필이 바뀌면 영수증·기록이 맞지 않아 다시 결정해야 한다.
- 세 노드 출구(`check`, 시트 칸 관문 `cells.ts`, Python `require_pass`)가 같은 규칙을 쓴다.

**감독·에이전트·MCP 도구는 결정하지 않는다.** 서버를 띄우고 주소를 사람에게 주는 것까지만 한다. 기록 파일을 쓰거나, 세션을 흉내 내 POST 하거나, 키를 읽어 서명하는 것은 규칙 위반이다.
