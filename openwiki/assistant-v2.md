# 조수 v2 — AI 는 정하고, 함수가 짓고, 다른 눈이 본다 (2026-10-23, 기본 꺼짐)

v1 조수는 모델이 칸 좌표·타일 번호·평면 문자열을 직접 쓰고 도구 400여 개 중에서 고른다. 실패의 대부분이
「모델이 좌표를 지어냄」(벽 속 NPC, 벽으로 걸어가는 컷신, 휑한 방)과 「다 됐다는 거짓 보고」였다.
v2 는 같은 실행기 위에서 역할을 나눈다.

| 단계 | 누가 | 무엇 |
|---|---|---|
| 1 해석 | 모델 | 요청 → 타입 있는 명세 하나(`src/ai/v2/types.ts` PlaceSpec·PersonSpec·EventSpec·ObjectSpec). 좌표 없음, 자리는 낱말. |
| 2 짓기 | 결정론 빌더 | 명세 → v1 결정론 도구 호출(`src/ai/v2/builders/*`, `people.ts`, `events.ts`, `drawObject.ts`). |
| 3 보기 | 코드 | 1배 그림 + 기계 검사(`checks.ts`: 도달·출입 착지·계단·NPC 도달·맨바닥·빈 칸). |
| 4 비평 | 다른 호출 | 요청 원문 + 1배 그림만 보는 독립 비평가(`critic.ts`, v1 `featureCriticPrompt` 루브릭 축 1·2·6). major 를 칸 좌표로. |
| 5 고치기 | 모델 → 빌더 | `edit_place` 패치(구역·주인공 물건 near·크기·variant·dressing)로 같은 빌더를 다시. 맵당 1바퀴(6차 속도 — 3바퀴는 바퀴마다 다시 짓기+비평 20~35초). |
| 6 보고 | 모델 | 「다 됐다」는 비평 major 0 + 기계 검사 통과일 때만. `missingArt` 는 그대로 보고. |

## 다양성 — 같은 요청이 같은 맵이 되지 않게 (2026-10-23)

`make_place` 가 처음 지을 때 명세에 무작위 `salt` 를 넣고, 고치기(`edit_place`)는 기록된 명세의 salt 를 물려받는다(모델은 쓰지 않는다).
빌더는 요청이 정하지 않은 결정만 salt 로 고른다: 마을(씨앗·땅 모양 terraces·숲 종류·맵 크기), 일본 거리·집(씨앗), 실내(배치 variant·씨앗 — 견본·장소 견본 고르기는 2026-10-29 부터 모델 설계로 대체, 아래 「방은 모델이 설계한다」),
던전(종류가 없는 「던전」은 종류도). 던전 짓기 도구 쪽은 덩이 배치에 퍼짐 세 갈래(뭉침·구불·넓게)와 1층 입구 계단/문을 씨앗으로 고른다(`layouts.ts` `layoutBlobOnce`, `dungeonTools.ts`).
여전히 고정인 것: 역전 상점가(지역 문법 station_plaza 가 씨앗을 안 탄다)·일본 집 예제 구성·컷신 무대 자리. 눈가림 「같아 보임」 점수와 빌더 표본은 보고서(`~/claude-viz/assistant-v2-report.html`) 다양성 절.
빌더 증명에서 같은 명세를 다른 salt 로: `SALT=<n> CHECKS=1 bun scripts/qa/assistant-v2/builders.mts <out> <case>`.

## 방은 모델이 설계한다 — 견본을 깔지 않는다 (2026-10-29 맵 같음 감사)

감사(`~/claude-viz/map-sameness-1029.html`, 묶음 vm1~vm8): 여관 1층 23개 중 13개가 같은 16×14 선술집 홀(「여관」 낱말 → 장소 견본 tavern, 뒤집기·손님 자리 네 판),
방탈출 방 23개 중 16개가 같은 나무 서재(손 견본 통째 이식), flash 방탈출 vm6·7·8 은 모두 끝맺음 자동 짓기의 9×10 거실 견본에서 시작했다(vm8 은 모델이 지은 방을 버리고 시작을 옮겼다).
원칙: 방은 모델이 설계하고, 함수는 조화·검사만 하고 고친 것을 알린다. 견본은 `room_parts` 의 참고 배치·그림으로만 보인다.

- 모든 손 도트 실내 짓기 길이 설계를 거친다: `make_place`(설계 없으면 장소마다 한 번 되돌려 보냄 → 그래도 없으면), `edit_place`(설계 없는 구역·더한 구역), `make_game`, 끝맺음 장소 자동 짓기(`buildPlaces`), 위층(`floor:2` 구역).
  설계가 빈 구역은 짓기 직전 `designMissingRooms`(`src/ai/v2/designRooms.ts`)가 **같은 모델**(`env.sideChat`)에게 room_parts 재료(기물 이름표·바닥/벽면·깔개·모양 안내·견본 요약 둘·모양 예 하나)와
  이 게임에 이미 선 방 목록(«이것과 다르게»)을 주고 JSON 설계를 받는다. 두 번 못 받으면 예전 길(함수 배치)로 짓고 경고 「모델 설계 없음」을 남긴다. keep(원래 방 지키기) 구역은 묻지 않는다.
- 되돌려 보내기는 빌더와 같은 칩셋 판정(`interiorTilesetOf`)으로 «손 도트 실내로 지어지나»를 본다 — `style:"modern"` 이어도 주인공 물건 때문에 v5 로 짓는 방(vm8 flash 방탈출)이 견본 서재로 섰다.
- 위층: 설계가 있는 위층 구역은 설계대로 짓고(객실 견본 둘 + 복도 대신), 빈 바닥 메우기(fillBare)를 하지 않는다. 내려가는 계단통은 넓은 설계 방(바닥 24칸 이상)에 서고, 모두 좁을 때만 계단참 복도를 붙인다.
- 끝맺음 단계 `adopt-model-places`(order 25, 자동 짓기 앞): 청사진 장소 이름이 모델이 지은 맵 이름과 어긋나면(모델이 맵 이름을 바꿨다) ① 이름이 겹치는 맵 ② 시작 맵 ③ 남은 장소·후보가 하나씩뿐일 때 그 맵을
  그 장소로 잇는다(실내/바깥이 이름 낱말과 맞을 때만). vm8 flash 방탈출 재구성 재생: 모델 방 「escape_room」을 장소로 이어 자동 짓기 없이 엔딩까지(자동 플레이 성공).
- 예시 그림(2026-10-30 사용자 지시): 옛 서재 사람 견본 `authored-study-*` 는 반복의 원천이라 `room_parts` 참고에서 뺐고(`pickReferences`), 견본을 지어 찍던 그림 대신
  사용자가 실내 기준으로 고른 assistant-rooms-2 방 10장(`public/assets/room-ideas/`, 목록·갈래·한 줄 설명 `src/ai/v2/roomIdeas.ts`)을 **구성 아이디어**(동선·초점·가구 묶음, 베끼지 않음)로 싣는다.
  용도 낱말로 둘을 고른다(객실·위층 → bed, 여관·홀 → hall, 서재·도서 → study, 그 밖·방탈출 → other). 실행기가 `env.readPublicAsset` 으로 읽고, 못 읽으면 글만 간다.
- 그림은 **한 장으로 합쳐** 싣는다(`env.combinePictures`, 기본 `roomPartsPictures:"one"`; `OPRN_ROOM_PARTS_PICTURES=one|each|none` 은 A/B 시험용). 모양 예시 6장 + 그림 2장을 따로 실은 결과(글 1.3만 자 + 그림 8장)
  뒤 Gemini 계열이 짓지 못한 판이 늘었다(서재 3d, 인계 `suite/ledger/handoff-study.md`). 설계 따로 묻기(`designMissingRooms`)도 아이디어 그림을 한 장으로 싣는다.
- 글도 가볍게(`roomPartsText` 기본 slim): 기물 40줄·모양 예 하나(나머지는 그림), 더 필요하면 `query` 로 다시 묻는다(약 6.8천 자, 예전 1.2~1.3만 자). `OPRN_ROOM_PARTS_TEXT=full` 은 A/B 용.
  A/B(2026-10-30, 서재 요청 실제 입력창): gemini-3.8-flash 는 proxy8318 에서 그림을 못 보는 길이라(그림 자리가 글 한 줄로 바뀐다) 그림 수는 원인이 될 수 없었고,
  1.2만 자 글에서 8판 중 2판이 «I'm having a hard time…»으로 멈췄다(slim 3/3 지음). Opus 5.5 medium 은 글·그림 크기와 상관없이 6/6 지었다. 이후 실조수 시험 모델은 Opus 5.5 medium·gpt-6.1-terra 둘(사용자 지시, Argon·flash 제외).
- 씨앗은 모델에게 보이지 않는다: `hints.seed`·`edit_place.patch.seed` 를 스키마·카드에서 뺐고, 그래도 오면 `dropModelSeed`(`modelSeed.ts`)가 버린다. 처음 짓는 명세의 `hints.variant:0` 도 «안 정함»으로 읽는다
  (terra 가 스키마를 다 채워 seed 0/1 을 보내 빌더가 무작위 씨앗을 껐다). 씨앗은 salt·variety(프로젝트 열쇠 + 요청)에서 나온다.

## 게임 요소 — 퀘스트·아이템·전투·파티·스위치 (2026-10-24)

v2 동사는 장소·사람·연출만 다뤘다. 그래서 「심부름 퀘스트」「상점에 새 무기」「보스 전투 뒤 감사」를 옮길 길이 없었다.
`src/ai/v2/game.ts` 는 요청에 게임 낱말(`GAME_WORDS`: 퀘스트·아이템·상점·전투·파티·스위치·여관·낮/밤 …)이 있을 때만 v1 결정론 도구 30개를 그대로 싣는다.
도구는 `V2_GAME_TOOLS`: 읽기 → DB(upsert_item·enemy·troop·actor…) → 붙이기(place_npc·upsert_event·set_shop_stock·place_chest·set_encounter_table·create_quest·configure_time_system·set_npc_schedule).
그와 함께 `GAME_CARD` 를 지시에 싣는다. 맵 요청의 첫 턴은 가볍게 남는다.
연출 비트에는 `tint`(밤·저녁·새벽·세피아·clear — 컷신 뒤에도 남는다)·`camera`(자리·사람으로 옮겨 보여 주고 back 으로 복귀)·`look`(shadow·ghost·normal)·`vanish` 가 더해졌다.
v1 의 `script_cutscene` 비트로 옮긴다(`events.ts`).
비교 사례 40개는 `harness-data/space-craft/seed.json` 의 `game` 분류다(id `g-*`, 시작은 모두 같은 마을 + 촌장·대장장이).
출하 플레이어에서 이벤트마다 세 번 말 걸기·선택·전투·상점을 자동으로 해 본 뒤 상태 변화와 대사로 눈가림 채점한다. 결과는 보고서 「게임 요소 비교」 절에 있다.
못 하는 것: 이미 있는 마을에 강·다리 같은 지형 덧그리기(맵을 새로 짓지 않으면 못 한다).
음악 낱말(음악·배경음·브금·BGM·팡파르·사운드트랙·OST)이 있으면 `FALLEN_TIERS` 음악 단이 `recommend_bgm`·`store_find_music`·`store_install`·`set_game_audio`·`get_database_records` 를 싣는다.
맵·시스템 음악 연결이 바뀌었으면 마감 검사가 「playAudio 이벤트」를 더 요구하지 않는다(`gameChecks.ts` `audioBindingsChanged`). 기본은 조수가 묻지 않고 스토어 곡을 넣어 잇고, 걸지 않았으면 마감 검사가 `set_game_audio`(필요하면 `store_find_music` → `store_install`)를 요구한다. 사용자가 「먼저 묻기」를 켰을 때만 음악 카드가 질문으로 세져 관문이 재촉하지 않는다. 스토어 음악 길은 `openwiki/asset-store.md` 「조수가 스토어 음악을 찾아 넣는다」.

## 새 플레이어 길잡이 — 목표 줄·보이는 이야기 이벤트 (2026-10-26, J90~J96)

사람 판정자가 엔딩에 못 닿는 게임이 자동 플레이로는 통과했다(연애 j90: 투명 「집 현관」, 장난감 가게 j90: 오프닝이 옮긴 인형).

  「현재 목표」 줄을 바꾼다(자리는 런타임이 주인공·인물·HUD 를 피해 고른다 — `runtime-pre-edit-routing.md` 「목표 안내창 자리」). 목표 줄은 상태라 불러오기·장면 재생성 뒤에도 남는다(`zoneFeedback.lastObjective`).
  이야기·연애 기본 HUD 와 `set_field_hud{off:true}` 는 목표 줄을 켜 둔다.
- 출하 막음(`shipChecks.shipBlockers`): `critical-invisible`(엔딩·이정표 이벤트가 투명이고 반짝임·작은 물건이 없음 — 건물 벽면 한 칸은 안 셈),
  `objective-missing`(목표 줄 없음·시작 목표 없음·이정표 뒤 목표 안 바뀜), `romance-gap`(연애 완료 검사 = 호감 변수 미연결 등을 경고가 아니라 막음).
- 자동 플레이(`qa/gameCheck/autoPlay`)는 컷신 `moveEvent` 가 옮긴 인물 칸으로 걸어간다(`sceneTestRunner.applyMoveEventForRunner`, 결과 `movedEvents`,
  저장 지점에서 이어 도는 판도 `initialEventPositions` 로 같은 자리).

벤치 68판의 동굴 26/28 이 「덩이 + 가운데 호수 + 아래 가운데 입구」 한 공식이었다(19장은 방 구성까지 입구·호수·보물·보스 4방). 모델은 type·theme·size 낱말만 넘기고 `layoutBlob` 이 방 수(small=3)·입구 자리(아래 가운데)·역할(가장 깊은 = 보스, 막다른 = 보물, small 이면 호수 1)을 정했고, terra 는 `hints.seed` 를 0·1·2 로 채워 씨앗 고르기까지 꺼졌다. 사용자 원칙: **맵·방은 모델이 설계하고 함수는 조화·검사만**(방 설계 `zones[].design` 과 같은 길).

- 형식: `make_place` 의 `spec.dungeonDesign`(여러 층은 `spec.floorDesigns`) — `src/editor/dungeonKit/designLayout.ts` `DungeonDesign`. `entrance`(north·east·south·west — 들어오는 길 쪽, 기본 없음), `rooms[{id, role(entrance·boss·treasure·lake·camp·shrine·forge·hall·grotto), size(small~huge 또는 w·h), shape(blob·cavern·long·shaft·ring·twin), dir, at(n·se·center… 또는 "x,y" 0~1), water(none·pool·lake·stream), features(stalagmites·crystals·mushrooms·bones·pillars·boulders·camp)}]`, `links[{from,to,kind(winding·straight·narrow·wide)}]` 또는 `connections`(linear·branch·loop·hub, 적은 순서로). 스키마에 enum·범위 없음, `normalize*` 가 한·영 낱말을 너그럽게 읽는다. `author_dungeon` 도 같은 `design`·`floorDesigns` 인자를 받는다(설계 하나 + 여러 층이면 마지막 층에만, 「고침:」으로 알림).
- 누가 정하나: **모델** = 방 수·역할·크기·모양·자리·물·특징·길·입구 쪽. **함수**(`layoutDesignedBlob`) = 겹치는 방 밀기(4칸 넘게 민 방만 알림), 이은 방 사이가 8칸 넘게 비면 판을 당기기(자리 순서 유지), 이어지지 않은 방을 가장 가까운 방과 잇기, 입구·보스 없음·여럿 고치기, 보스 방·고리·입구 최소 크기, 작은 방 호수 → 웅덩이, 테마에 없는 액체(용암↔물·액체 없는 테마) 바꾸기, 모르는 모양·특징 빼기. 고친 것은 모두 warnings 「고침: …」 줄. 방을 더하거나 고르지 않는다. 벽 두께·다리·도달은 원래대로 마스크 `settle` 이 맞춘다.
- 불규칙 문법(cave·volcano·ice·forest·swamp·otherworld)은 설계 자리 그대로 판다(`layouts.ts` `layoutBlob` 첫 줄에서 갈린다). 입구 방은 계단 걸 평평한 북벽 심(7×)을 지키고 다른 방으로 가는 길은 옆구리로 나간다. 숲·늪은 설계한 입구 쪽 맵 끝으로 출구 길(`compose.ts` trailExit, `layout.entranceSide`). 방+통로 문법(catacomb·castle·temple·mine·sewer·pyramid·tower)은 `designToRooms` 가 rooms(kind·크기·from = 입구 쪽 이웃·dir = 두 방 at 비교)로 옮기고, 나무 밖 길이 있으면 `layout:"loop"`. 미궁은 설계를 쓰지 않는다(알림).
- 특징은 방 꾸미기 뒤 `dress.ts` `dressDesignFeatures` 가 덩이로만 더한다(낱개 흩기 없음 — 트인 바닥 외톨이 기물 규칙). 놓을 자리·그림이 없으면 「고침: 방 X 의 특징 … 빠졌다」.
- 재료: v2 동사 `dungeon_parts({theme})`(`src/ai/v2/dungeonParts.ts`) — 모양·역할·물·특징·연결 어휘, 뼈대가 서로 다른 예시 넷(`DUNGEON_DESIGN_EXAMPLES`: 남쪽 입구 갈래·서쪽 입구 물줄기 사슬·동쪽 입구 호수 고리·북쪽 입구 허브 — **게임(projectKey/제목)마다 순서를 돌린다** `rotatedExamples`, 모델이 모두 첫 예시에 기대어 «남쪽 입구·북쪽 보스»로 짰다)와 첫 예시를 사본에서 `author_dungeon` 으로 지은 1배 그림 하나(테마별 캐시).
- 참고 그림(2026-10-30 사용자 지시): `DUNGEON_REFERENCE_PICTURES` = 사람이 조각을 고른 버들항 던전 렌더 다섯(`tiledata/beodeul-variants/{sea-cave,volcano-cave,castle-catacombs,aqueduct-sewer,temple-ruins}/render-1x.png`, mapvqa `refs/anchors.json` 의 던전 기준과 같은 그림). 테마에 맞는 것 먼저 둘을 그림으로, 다섯 모두 구성 한 줄(구역 순서·볼거리·가지·고리)로 준다. 「그대로 베끼지 말고 구성 아이디어만 — 검수는 이 그림과 거의 같은 맵을 반복으로 친다」고 적는다. 그림 파일은 저장소에만 있어 없으면 글만. 지문(`suite/dungeon-design-fp.py`)은 맵마다 참고 그림과의 축소 그림 상관을 재고 ≥0.92 면 반복에 더한다.
- 그림·글 크기: Gemini(argon·flash)가 큰 전맵 그림 넷을 받은 바로 다음 차례에 제공자 오류·글로 적은 tool_call 을 자주 냈다(2026-10-29 6판 중 4판; 실내 안내 동사도 글 1.3만 자+그림 8장에서 같은 회귀). 그래서 **그림 한 장**(참고 둘 + 첫 예시를 지은 그림을 반 크기 280px 높이로 나란히, `sideBySide` pngjs)과 **짧은 글**(어휘 한 덩이 `vocab`, 예시 설계 둘 + 나머지 한 줄, 참고 그림 구성 한 줄씩 — 약 3.3천 자).
- 설계 없이 온 던전·동굴 `make_place`(이번 실행에서 지은 맵 `mapId` 다시 짓기 제외)는 장소 이름마다 한 번 되돌려 보낸다(`session.dungeonBounced`, 「아직 짓지 않았다(실패 아님)」 + parts). 다시 없이 오면 예전 함수 배치. 설계한 층의 `next` 는 `edit_place({patch:{mapId, set:{dungeonDesign: 고친 설계 전체}}})` 를 이른다.
- 되돌려 보내기 앞 손질 `screenDungeonSpec`(`dungeonParts.ts`): ① 프로젝트에 없는 `mapId` 는 버리고 새 맵(2026-10-29 실조수 첫 판: argon «map_cave_1»·flash «cave_dungeon» 을 지어내 `author_dungeon` 이 «맵이 없습니다»로 실패) ② 방 둘 미만 설계(`{rooms:[]}` 빈 껍데기)는 설계 없음 ③ 예시를 그대로 옮긴 설계(방 id 절반 이상, 또는 역할@자리 70% 이상 같음 — flash 가 branch-north 를 그대로 옮겼다)는 장소마다 한 번 되돌려 보내고, 두 번째는 그대로 짓고 「설계가 예시 … 와 거의 같다」를 알린다.
- 씨앗: `hints.seed`·`edit_place` 의 `seed` 를 모델 스키마에서 뺐고, `make_place`·`applyPatch` 가 들어온 `hints.seed` 를 버린다. 던전 씨앗은 `spec.variety`(프로젝트 열쇠 + 요청문)와 이름의 해시 — 같은 게임·같은 요청이면 같은 층, 다른 게임이면 다르다.
- **입구 쪽은 들어오는 길에서(2026-10-30, 맨 요청 남쪽 입구 13/16)**: `dungeonParts.arrivalEntrance` — `make_game` 은 자식 던전의 `place.side`(부모에서 본 방향)의 반대 쪽을 입구로 정하고, `make_place` 는 설계가 입구 쪽·입구 방 자리를 모두 비웠을 때만 `spec.exits` 하나를 쓴다(terra 는 스키마 칸을 다 채우며 exits 에 습관으로 south 를 넣는다). 설계가 다른 쪽을 적었으면 세계 배치가 이기고 「고침: 입구를 X 대신 Y」로 알린다(입구 방 `at` 은 지워 쪽을 따르게). 정보가 없으면 모델이 정하되, 쏠림 원인을 뺐다: 어휘의 입구 낱말 순서를 게임마다 돌리고(`sideOrder`, 늘 south 가 먼저 적혀 있었다), 스키마의 「south(기본)」, 참고 그림 구성 줄의 「남쪽 입구 계단실」「서남 입구」「남동 해변」 같은 절대 방위를 뺐다. `dungeon_parts`·되돌려 보내기는 `context` 로 이 게임의 바깥 장소 출구(「그 출구로 오는 굴이면 입구는 …」)를 준다.
- **바깥 문은 하나, 세계 방향 가장자리 길 칸(2026-10-30 dd1030 opus 「마을+동굴 둘」: 동쪽 동굴 문이 마을 북쪽 끝 (19,0)·가운데 굴 입구 (30,19) 둘, 북쪽 동굴 문은 북동쪽 높은 단)**: 원인은 둘 — `author_dungeon` 기본 출구(`attachDefaultExit`)가 시작점 가까운 갱구 자리를 골랐고, 다시 짓기(edit_place)는 옛 문 자리에 `create_transfer_pair` 로 다시 이으면서 짓기 자체도 기본 출구를 또 달았다. 이제 `make_place`(지금 맵이 이번에 지은 마을·거리)·`make_game`(부모가 마을·거리)은 짓기 전에 `dungeonGates.gateFor` 로 던전이 놓인 쪽(`place.side`, 없으면 설계 입구 쪽의 반대 — 입구 서 → 던전은 동쪽)의 바깥 맵 가장자리 길 칸(없으면 길에 가장 가까운 걸어 닿는 칸, 같으면 가장자리 가운데)을 `spec.gate` 로 정하고 빌더가 `author_dungeon entrance` 로 바로 잇는다(가장자리 길 칸엔 갱구를 찍지 않는다). 다시 짓기는 옛 문 칸을 `entrance` 로 넘겨 짓기가 한 번만 잇는다. 그 뒤 `finishPlace`·make_game 이 `settleDungeonGates` 로 바깥 마을·거리 → 던전 문을 맵마다 하나, 그 가장자리로 정리한다(옛 문 양쪽·월드 그래프 연결을 걷고 `link_world_entrance` 하나, 「고침:」 한 줄). 그 쪽 맨 끝에 걸어 닿는 칸이 없으면(dd1030g terra 강가 마을: 서쪽이 강, 마을 빌더가 서쪽 길을 안 냄) 그 쪽에 가장 가까운 줄의 닿는 칸을 쓴다(「끝에서 N칸 — 길이 끝까지 닿지 않는다」). 월드맵 장소 입구·실내는 건드리지 않는다. 남은 것: 정리로 걷힌 옛 문 자리에 앞서 찍힌 갱구 그림은 그대로 남는다(짓기 전에 자리를 정하는 새 경로에선 생기지 않는다).
- terra 맨 요청 남쪽 입구 쏠림(dd1030 남 9/10)은 안내 문구로 바뀌지 않았다 — 그대로 두고 기록만 한다(세계 배치가 있으면 위 규칙이 입구 쪽을 정한다).
- **같은 게임 안 「다르게」·십자 공식(2026-10-30 terra 같은 요청 3판이 모두 s·center·e·w·n 5방)**: 예시 순서 돌리기(`rotatedExamples`)는 terra 에 효과가 없었다(projectKey 는 판마다 달랐는데 같은 십자). 그래서 ① `screenDungeonSpec` 이 `crossFormula`(방 넷 이상, 자리가 모두 나침반 낱말, 가운데 + 네 끝 중 셋 이상)를 장소마다 한 번 되돌려 보내며 "x,y" 자리·치우친 긴 굴·갈래·높이를 요구하고(`cross:<이름>`), 두 번째는 짓고 알린다. ② `dungeon_parts`·되돌려 보내기 `context` 에 이 게임에서 이미 지은 굴의 설계 한 줄(`designLine`: 입구·방 수·역할@자리/모양/단)을 보여 「방 수·입구 쪽·자리·모양을 다르게」를 요구한다.
- **높이(단·계단)**: 방마다 `level` 0·1·2(옛 `levels` 맵도 읽음). 입구 방이 0 이 아니면 모두 그만큼 내린다(고침). `compose.ts` 가 방 칸에서 다중 출발 BFS 로 바닥 단을 정하고 `reliefPlan.planDungeonRelief` 가 단이 다른 경계마다 곧은 계단 자리(아랫 참·계단 dl+1칸·윗 참, 폭 1~3, 남북 오름 우선)를 찾는다. 못 잇는 방은 한 단 내리고 알린다. 계단 칸은 꾸미기 전에 막아 두었다가 도달 검사 2 앞에서 푼다. 결과는 `map.relief`(스타일 `dungeonReliefStyle`: 숲 grass-steps·늪 peat-steps·얼음 snow-steps·피라미드 sand-steps·나머지 새 `cave-steps` — 칩셋 동굴 바위 색, `rampArt.json` 은 `build-village-stair-art.mts`). 남북 계단 칸의 아래 층 타일은 마을과 같은 버들항 돌계단 조각(`bd-capital-quay-steps-*` 폭 1~2, `bd-mpart-stairs` 폭 3+)으로 칠한다(`dungeonTools.paintReliefStairTiles`) — 동서 계단 조각은 칩셋에 없어 비탈로 그리고 「고침:」으로 알린다(그림 없음). 공허 액체·탑 고리 던전은 높이를 쓰지 않는다.
- **미궁도 설계를 따른다**: `designMaze.layoutDesignedMaze` — 노드 격자 안에 설계한 방을 자리·크기대로 블록으로 두고(겹치면 가까운 빈 자리로 옮기고 알림) 입구 쪽 바깥에 입구 방, 그 사이를 무작위 DFS 갈림길로 잇는다. 보스·보물은 막다른 끝, 지나가는 방은 이은 수만큼 문. 못 닿는 방은 문을 더하거나 빼고 알린다. 예전 `layoutMaze` 는 설계를 버렸다.
- 빌더 hints: 스키마 칸을 0·빈 값으로 다 채우는 terra 의 `hints.layout`(마을 자리 객체)이 author_dungeon `layout`(배치 가족 낱말)으로 넘어가 인자 검증에 걸렸다(dd1030 terra 같은 요청 3판 모두 실패) — 빈 값·객체 hints 는 안 준 것으로 읽는다.
- 빌더 경고: `builders/dungeon.ts` 가 `author_dungeon` 결과의 `diff.warnings` 를 읽지 않아 「고침:」 줄이 모델에게 한 번도 가지 않았다(지문의 고침 수 늘 0) — 고쳤다.
- 시험: `bun scripts/qa/assistant-v2/dungeonDesign.mts <out> [theme…]`(예시 넷 + 설계 없음, 모델 없음). 실조수 판 검사 `bun scripts/qa/assistant-v2/dungeonLiveCheck.mts <판>…`(막힘·자동 플레이·던전 맵 도달(시작/이동 칸에서 이벤트 모두 닿는가)·열린 바닥 한가운데 외톨이 막힌 칸 수, `DLC_NOPLAY=1` 이면 자동 플레이 생략). 실조수 `suite/dungeon-live.sh <arm> <prompt> <batch>`(같은 요청 same1~3 + demon·crystal·goblin·volcano·forest), 지문은 `suite/dungeon-design-fp.py <batch> <out>` — mapvqa 렌더·거의 같음 규칙 + 구조 사인(방 수·방 종류·입구 쪽, 방 이름과 무관해서 mapvqa 「방 구성」 표지가 모델이 지은 이름으로 다양해 보이는 착시를 막는다). 결과 페이지 `~/claude-viz/dungeon-design-1029.html`.

## 씬 벤치 1회차 수리 (2026-10-30 sc-1030a terra · sc-1030s-b1~b4 opus)

장면 하나 요청(보스 방·엔딩·강가 마을 잇기)을 판정자가 플레이한 결과에서 빌더·런타임 결함을 고쳤다. 판 저장본(project.sqlite)이 지워져 있어

끝맺음 자동 단계와 출구·이동 칸 마감은 **단계 하나 = 파일 하나** 목록이다. 수리 작업자 여럿이 같은 파일(옛 `finishAutoBuild.ts`·`verbs.ts clearLanes`)을 고쳐 체리픽이 부딪히던 것을 없앤 구조 변경이며 동작은 같다(`finishReplay --trace` 로 vm5~vm7 판 대조).

- **끝맺음**: `src/ai/v2/finish/stages/<id>.ts` 가 `export const stage: FinishStage = { id, phase, order, run(ctx) }` 하나를 낸다. 목록은 `finish/stages/index.ts`(한 줄에 `export { stage as <이름> } from "./<id>"` 하나). 실행기 `finish/index.ts runFinishAutoBuild` 가 묶음 순서 `blueprint`(청사진이 있을 때 — 한 일은 `ctx.done`, 조수에게 줄 「[자동으로 지음]」 글) → `assembly`(게임 전체 요청일 때 — 한 일은 `ctx.assembled`, 묶음 끝에 `v2.assembly` 기록 + 체크포인트 `blueprint_assembly`) → `reload`(맨 끝 — 저장 → 다시 읽기 관문 `reload-check`, order 900) 로, 묶음 안은 `order` 오름차순으로 돈다. 옛 입구 `finishAutoBuild.ts` 는 다시 내보내기만 한다.
- **출구·이동 칸 마감**(`session.clearLanes`, 끝맺음 단계 `lanes`): `src/ai/v2/lanes/stages/<id>.ts` 가 `LaneStage = { id, scope, order, run(ctx, mapId) }`. `scope:"project"` 단계(빈 시작 맵 치우기·방탈출 봉인·추리 세우기·상점·시작 돈·고아 맵·은신처·얼굴 자리)를 먼저, 이어 맵마다 `scope:"map"` 단계(실내 출구 → … → 막힌 길 표지 → 굴 입구 앉히기 → 보물상자 → 잠긴 집 문 → 이동 칸 비우기 → 대상 앞 → 사람 흩기 → 닿지 못하는 이벤트 → 이동 칸 기록)를 돈다. 한 일은 `ctx.notes`, 맵 이름은 `mapLabel(env, mapId)`, 맵 하나 안에서 단계끼리 넘길 값은 `ctx.map`(맵마다 새로).
- **더하는 법**: (1) 새 파일 `stages/<id>.ts` — 단계 하나, 실패가 끝맺음을 깨면 안 되면 그 안에서 `try/catch`; 기록 키가 필요하면 `env.emit({ type:"execution_status", name:"v2.…" })`. (2) `stages/index.ts` 에 한 줄. (3) `order` 는 앞뒤 단계 사이 빈 번호(10 간격, 꽉 차면 소수 `135` 도 된다). 같은 묶음 안 `order`·`id` 가 겹치면 모듈을 읽을 때 던진다 — 순서가 import 줄 순서에 기대지 않는다. 다른 단계 파일·실행기는 고치지 않는다.
- **동작이 같은지 보기**: `bun scripts/qa/assistant-v2/finishReplay.mts <판> --trace --followup "<후속>" [--snapshot <json>]` — `--trace` 는 `Math.random`·`Date.now` 를 고정하고 `rec.trace`(emit 이름·ok·요약, 체크포인트 이름)·`rec.projectHash` 를 남긴다. 구조만 바꾸는 변경은 두 커밋의 출력(`after`·`trace`·`notes`·`reload`·프로젝트 해시)이 같아야 한다.

## 구조 — v1 실행기를 그대로 쓴다

`runAssistantV2` 는 v1 `runPiAgent` 를 부르되 `options.v2` 갈고리(`src/ai/v2/env.ts`)를 준다:

- `toolNames: ["__assistant_v2__"]` + `initialToolNames: []` → 레지스트리 도구 0개 노출. 대신 v2 동사 8개(`verbs.ts`):
  `make_place · edit_place · add_people · add_event · draw_object · place_object · inspect · ask_user`.
- 동사 인자 중 감싸는 칸 하나(`make_place` 의 spec, `add_people` 의 people 등)는 `src/ai/v2/flatWrapper.ts` 가 최상위로 펴 보여 주고 실행 직전에 다시 감싼다. 예전에 감싸 보낸 호출도 통과한다. 목록과 최상위 칸이 같이 오면, 필수 칸이 찬 최상위는 한 명 더로 붙이고, 한 명짜리 목록의 빈 칸은 채우며, 필수 칸이 빈 찌꺼기는 목록 전체를 거절하지 않고 버린다. 객체 칸은 최상위 값으로 빈 자리를 채우고, 이미 감싼 값이 있으면 그 값을 남긴다.
- 동사는 `wrapTool` 을 거친다 → 체크포인트·실시간 시공 재생(constructionLogs)·맵 소유권·맵별 대기열·사용량 집계·로컬 CLI 엔진이 v1 과 같다.
  동사 안에서 `env.checkpoint` 로 **첫 짓기를 비평 전에** 편집기에 싣는다(사용자는 비평을 기다리지 않는다).
- `options.v2` 가 있으면 v1 의 낱말별 지시(regex system prompt)·몬스터/오프닝 제작·완료 검사·배치 품질 권고·특징 확인표가 꺼진다. 없으면 v1 은 한 줄도 달라지지 않는다.
- 시스템 지시(`prompt.ts`) = 역할·고리·규칙 + 지식 카드 7장(실내·마을·던전·일본 도시·사람·사건·없는 물건, 각 ≤900자) + 지금 프로젝트 맵 목록. 약 5천 자.
- 비평가는 `env.sideChat`(= v1 `eventAssistChat`, 같은 모델) — 사용량은 `stats.review` 로 따로 모인다.
- 끝맺음 관문(`v2FinishGate`): 고칠 수 있는 major·기계 실패가 남은 장소가 있으면 한 바퀴 더 돌게 한다.
- 빈 자리표시 시작 맵(`isPlaceholderMap`)을 `edit_place` 로 「고치려」 하면서 구역(`addZones`)을 주면, 고칠 장소가 없으니 그 패치로 그 맵 자리에 실내를 `make_place` 로 짓는다(2026-10-29 방 과제: 10개 중 4개가 edit_place(map_blank_start) 실패 한 번으로 빈 맵인 채 끝났다).
- 고치기가 더 나쁘면 되돌린다: `edit_place` 뒤 (기계 실패 + 비평 major) 수가 앞보다 늘면 앞 프로젝트로 되돌리고 `reverted:true` 를 돌려준다(바퀴는 쓴 것으로 센다).
- 마을·던전·거리 빌더는 소품 하나하나·`dressing` 을 받지 않는다 — 그런 패치는 바퀴를 쓰지 않고 거절한다(같은 맵이 또 나와 바퀴만 쓰던 것).
- 실패한 동사·예외도 `guard` 가 tool_end 에 ok:false·이유로 싣는다.
