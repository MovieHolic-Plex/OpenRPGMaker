# 배틀러 idle 애니메이션 플레이북

새 배틀러에 idle 애니메이션을 **추가하는 절차**다. 왜 그렇게 설계됐는지(런타임 계약·CSS·폴백)는
`openwiki/runtime-battle.md` 의 배틀러 idle 절에 있다. 이 쪽은 "어떻게 새로 만드는가"만 다룬다.

세 티어가 이미 돌아간다: 적 몬스터(슬라임·박쥐·골렘), 정면 액터(hero-01~06), 후면 액터(hero-01~04).
카탈로그는 `src/assets/battlerIdleAnimations.ts`, 계약은 `test/battlerIdleAnimation.test.ts` 와
`test/battlerBackIdleAnimation.test.ts`.

## 런타임 코드는 건드릴 일이 거의 없다

후면 티어를 붙일 때 **런타임 변경이 0줄이었다.** 경로는 이미 `applyIdleAnimationToImage` 로
배선돼 있었고, 없던 것은 **에셋과 카탈로그 항목**뿐이었다. 새 배틀러를 붙일 때 먼저
`battlerIdleAnimation(resourceId)` 가 이미 그 리소스를 찾는지 확인하라. 찾는다면 작업은
"그림을 만들어 카탈로그에 등록"으로 끝난다.

시트가 없는 배틀러는 정적 이미지로 폴백한다. 스트립이 404 면 `data-battler-anim` 을 걷어
정적 `src` 로 되돌아간다 — 배경만 보이는 구조라 그냥 두면 빈 상자가 된다.

## 순서

### 1. 표시 상자를 먼저 실측한다 (셀 종횡비가 여기서 나온다)

**정사각 셀을 기본값으로 쓰지 마라.** 재생 CSS 는 가로를 상자폭에 묶고 세로를 `auto` 로 둔다.
칸 종횡비가 상자와 다르면 칸 높이가 상자를 넘어 **머리·발이 잘린다.**

실측 예: 포켓몬 스킨의 아군 뒷모습 상자는 `145px × 140px` 로 가로가 더 넓다. 그래서 셀을
`290 × 280`(상자의 2배, 필드 zoom ~2× 에서 1:1)으로 굽는다. 브라우저 실측으로 렌더된 칸
높이 210.0px 가 상자 높이 210.0px 와 같은지 Playwright 가 확인한다.

상자 크기는 `src/styles/runtime/battle-skins/_battlers.css` 에서 찾고, **믿지 말고 브라우저에서
재라** — 스킨별 `width !important` 와 필드 zoom 이 곱해진다.

### 2. 클립을 만든다 (프롬프트에 긍정 제약까지 넣는다)

`image_to_video` 로 정적 원본에서 짧은 idle 클립을 만들고 프레임을 키잉한다.

**"없어야 할 것" 금지만으로는 부족하다.** 영상 모델은 클립이 진행되며 드리프트하는데, 그
형태가 매번 다르다. hero-04 는 세 번 갈렸다:

| 시도 | 프롬프트 잠금 | 드리프트 |
|---|---|---|
| v1 | (없음) | 갈색 두건 망토가 자라 녹색 튜닉을 덮었다 |
| v2 | 망토·후드 금지 | 탠 가죽 하네스가 **녹아 없어지고** 튜닉이 치마처럼 길어졌다 |
| v3 | 하네스 명시 | 옷은 지켰지만 **고개를 돌려 얼굴을 보였다** |

그래서 프롬프트에 **"있어야 할 것이 매 프레임 보인다"**까지 적어야 한다: "탠 하네스가 상체에
계속 보인다", "튜닉은 허리에서 끝난다", "뒷머리만 보인다 — 얼굴·귀 금지".

원본을 **직접 보고** 의상을 적어라. 드리프트된 프레임을 원본으로 착각해 "brown tunic" 이라고
적은 재생성은 더 나빠졌다(편차 0.133).

### 3. 창을 탐색한다 (눈으로 고르지 마라)

```bash
node scripts/asset-gen/select-battler-idle-window.mjs \
  --frames /tmp/back-anim/keyed/hero-04-v3 \
  --reference public/assets/generated/battle-skins/sprites/hero-04-back.png \
  --cell 290 --cell-height 280 --frame-count 8 --verify 6
```

네 계약으로 창을 걸러 통과 픽을 여유 순으로 출력하고, 상위 N개는 **실제 패커로 패킹해
재채점**한다. 근사만 믿으면 리샘플링 차이로 값이 어긋난다(실측: 근사 0.087 대 실제 0.125).

루프가 안 닫히면 `--pingpong-only`. 출력의 `--pick` 을 그대로 4단에 넘긴다.

**통과 창이 없으면 임계값을 낮추지 말고 2단으로 돌아가라.** 그건 클립이 계약을 만족하지
못한다는 뜻이다.

### 4. 패킹한다

```bash
node scripts/asset-gen/pack-battler-idle-strip.mjs \
  --frames <키드 프레임 디렉터리> \
  --reference <정적 원본 png> \
  --out public/assets/generated/.../idle/<slug>.png \
  --cell 290 --cell-height 280 \
  --pick "96,98,100,102,104,102,100,98"
```

`--pick` 은 **중복 인덱스를 그대로 받는다** — 핑퐁이 추가 코드 없이 되는 이유다.

절차 생성(영상 없이) 티어는 `scripts/asset-gen/gen-battler-idle-strips.mjs`.

### 5. 카탈로그에 등록한다

`src/assets/battlerIdleAnimations.ts`. 프레임 간격은 **창의 실측 간격**으로 맞춘다:
`stride ÷ 24fps`. 선택기가 계산해서 출력한다.

### 6. 검증한다

```bash
npx vitest run test/battlerBackIdleAnimation.test.ts test/battlerIdleAnimation.test.ts
npx playwright test --config playwright.runtime.config.ts battler-idle-animation
```

Playwright 는 브라우저에서 **실제로 받은 스트립 파일**의 자연 크기로 잘림을 판정한다 —
카탈로그 상수를 되풀이하지 않으므로 패커가 기하를 바꾸면 새 값으로 다시 판정된다.
**모든 슬러그를 돌려라.** 하나만 보면 나머지 스트립이 무검증으로 남는다.

## 네 계약 — 넷 다 상대값이다

정본은 `scripts/asset-gen/battlerIdleMetrics.mjs` 의 `CONTRACT` 다. 테스트와 선택기가 **같은
파일을 import** 한다. 지표를 테스트 안에만 두면 도구가 다른 산식으로 점수를 내고, 그게 실제로
리뷰에서 두 번 잡힌 "집계가 다른 숫자"의 원인이었다.

| 계약 | 상한 | 왜 상대값인가 |
|---|---|---|
| 전신 색 | 0.15 | 절대 편차는 **지분 작은 성분이 사라지는 것**을 놓친다. hero-04 는 갈색 망토가 녹색 튜닉을 덮었는데 녹색이 피사체의 8% 라 절대 0.035 로 통과했다(상대 0.42) |
| 모션 | 인접 **모든** 쌍 ≥ 2% | `max` 로 재면 8칸 중 한 쌍만 움직여도 통과한다. 초기 hero-01 패킹은 최대 1.9%·최소 0.01% 로 사실상 정지 화면이었고, `steps()` 는 같은 그림 위에서도 배경 위치를 옮기므로 런타임 검사로도 안 잡힌다 |
| 루프 이음매 | 평소 최대 걸음 × 1.5 | 절대 상한은 진폭 큰 모션을 부당하게 떨어뜨린다. hero-03 은 이음매 9.6% 지만 평소 걸음이 14.8% 라 눈에 안 띈다 |
| 머리 영역 | 1.0 | 전신 지표는 **고개 돌림·머리 장식 이물을 못 잡는다** — 머리가 피사체의 일부라 전신 0.125 로 통과한다. 같은 버킷을 피사체 상단 30% 에만 걸면 1.941 |

### 상한은 불량 쪽에서 정한다

실린 값에 맞춰 상한을 정하면 그건 계약이 아니라 현재 자산의 기술서다. **알려진 불량과의
거리**로 정하고, 여유를 **두 방향으로 따로** 적어라.

머리 계약 예: 불량 1.941 은 상한 1.0 의 1.94배 **위**(`1.941/1.0`), 실린 최악 0.665 는 상한의
1.50배 **아래**(`1.0/0.665`). 한 숫자로 뭉치면 산식이 틀린다.

### 머리 계약은 얼굴 검출기가 아니다

고개를 돌리면 잡히는 이유는 **머리카락 지분이 무너져서**다(얼굴 구간을 패킹하면 2.452, 주도
버킷 `green`). 머리색·살색 대비가 약한 배틀러에서는 덜 두드러질 수 있다. 실린 자산에서 이
계약이 실제로 잡아낸 것은 머리띠에 생긴 **밝은 녹색 이물**이었다.

머리 영역 비율(상단 30%)은 임의가 아니다 — 창을 바꿔 재보면 **20~35% 에서만** 정상·불량이
갈린다(15% 는 정상 hero-01 이 탈락, 40% 는 불량이 통과).

## 함정 목록

- **집계를 섞지 마라.** 두 가지를 각각 지켜야 한다.
  1. 실측은 **전 칸 worst** 로 적는다. 칸 0 만 보면 실린 값이 실제보다 좋아 보인다 —
     hero-04 는 색 칸 0 = 0.069 대 worst = 0.092, 머리 칸 0 = 0.528 대 worst = 0.665.
  2. vitest 가 처음 보고하는 값은 **첫 위반 칸**이지 worst 가 아니다 — 옛 결함본 머리는
     첫 위반 칸 1.398(칸 1) 대 worst 1.941(칸 4). 실패 메시지의 첫 숫자를 그대로 옮기면 어긋난다.

  **지표를 가로질러 짝지으면 안 된다.** 색 상한은 0.15, 머리 상한은 1.0 이라 스케일이 다르다 —
  "0.092 대 0.665" 처럼 붙여 쓰면 색 계약을 깬 것처럼 읽힌다(이 문서가 실제로 그렇게 틀렸다).
- **정사각 셀 금지.** 1단 참조.
- **루프가 안 닫히면 핑퐁으로 감는다.** 충실한 구간이 짧아 그 안에 호흡 한 주기가 안 들어가면
  **어떤 연속 창도** 이음매 계약을 통과하지 못한다(hero-04 최선 1.68). 서로 다른 5칸을
  `[a,b,c,d,e,d,c,b]` 로 되짚으면 이음매가 정의상 한 걸음이 된다.
- **계약을 새로 만들면 음성 픽스처로 래칫을 걸어라.** 실린 칸만 검사하면 상한을 올려도 초록이라
  계약이 무엇을 떨어뜨리는지 CI 가 증명하지 못한다. 결함 스트립을 `test/fixtures/battler-idle/`
  에 남기고, **상한은 공유 상수 하나**를 양성·음성이 같이 보게 하고, 픽스처의 실측값을
  `toBeCloseTo` 로 고정하라. 셋 중 하나라도 빠지면 우회로가 생긴다:
  - 상수를 흩어 두면 → 양성만 올려서 빠져나간다
  - 실측을 안 박으면 → 픽스처를 약한 그림으로 바꿔치기해서 빠져나간다
- **자기 도구도 검증하라.** 이 플레이북의 선택기는 처음 만들 때 두 프레임을 폭 2배 이미지에
  붙이면서 행 스트라이드를 어긋나게 해 **모든 창이 모션 만점**으로 보였다. 사전 필터가
  아무것도 걸러내지 않는데 실제 패커에서 0.00% 가 나오면 그 신호다.

## 실린 자산의 실측값

`--verify` 로 재채점한 전 칸 worst(2026-08-31, 후면 티어):

| | hero-01 | hero-02 | hero-03 | hero-04 |
|---|---|---|---|---|
| 색 (≤0.15) | 0.071 | 0.075 | 0.080 | 0.092 |
| 머리 (≤1.0) | 0.526 | 0.167 | 0.337 | 0.665 |
| 모션 최소 (≥2%) | 3.58% | 4.09% | 12.20% | 2.36% |
| 이음매비 (≤1.5) | 1.17 | 0.25 | 0.65 | 0.71 |

**hero-04 의 모션 여유가 얇다**(하한의 1.18배). 선택기를 그 클립에 돌리면 같은 구간에서
모션 6.40% 인 창(`96,98,100,102,104` 핑퐁)을 찾아낸다 — 실린 픽은 최적이 아니다. 다만
그 창은 stride 2 라 간격이 83ms 로 빨라지므로(실린 것은 208ms) 호흡 속도가 달라진다.
다음에 hero-04 를 재패킹할 일이 있으면 이 트레이드오프를 같이 보라.
