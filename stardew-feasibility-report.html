결론부터 말하면 — "농사 + 계절 + 마을 + NPC + 상점"이라는 스타듀밸리의 뼈대는 이 에디터에 이미 내장되어 있습니다. 다만 스타듀밸리 특유의 실시간 조작감(낚시, 액션 전투)과 관계 시스템의 깊이(호감도 UI, 결혼)는 엔진 구조가 막고 있습니다.

✅

그대로 구현 가능 — 네이티브 지원

프롬프트 한 줄이 전용 AI 도구 또는 런타임 기능으로 직결되는 영역. 우회 없이 "진짜" 기능으로 동작합니다.

농사 풀사이클 — 밭갈기 → 심기 → 물주기 → 수확 핵심

스타듀밸리의 심장인 농사 루프가 런타임에 그대로 구현되어 있습니다. 괭이(hoe)로 경작 → 씨앗 심기 → 물뿌리개(wateringCan)로 물주기 → 성장 단계 경과 → 수확, 그리고 물을 안 주면 시드는(dead) 로직까지 존재합니다. 도구는 아이템 장착 개념으로 해결됩니다. "농장 맵에 밭 구역 지정하고, 파십·딸기·옥수수 작물 추가해줘. 물 안 주면 시들게."
근거: src/player/farming.ts (tilled/planted/watered/harvested/dead) · src/project/farmModel.ts (FARM_TOOLS = hoe/wateringCan/axe/pickaxe) · src/project/toolActions.ts

계절 작물 데이터베이스 네이티브

작물 레코드에 계절(seasons), 씨앗 아이템, 수확 아이템, 성장 단계가 스키마로 존재. 작물 전용 스프라이트 에셋도 번들. "봄 작물이랑 여름 작물 구분해서 DB에 넣어줘"
근거: define_crop 도구 · CropRecord.seasons (farmModel.ts) · assets/farming/crops/

시간 시스템 + 수면으로 하루 넘기기 네이티브

아침/낮/저녁/밤(timePhase)과 계절(season)이 이벤트 페이지 조건으로 직접 걸 수 있는 일급 개념. 침대에서 자면 아침으로 넘어가는 것도 전용 커맨드. "하루가 흐르는 시간 시스템 설정하고, 자면 아침 되게 해줘"
근거: configure_time_system · advanceTime / sleepUntilMorning · timePhase/season 페이지 조건 (types/events.ts) · playSceneTime.ts

주민 NPC + 시간대별 스케줄 네이티브

주민 생성 전용 도구와 스케줄 필드, npcActivity 페이지 조건이 있어 "낮엔 상점, 밤엔 집"이 조건 분기 없이 표현 가능. "주민 10명 만들고 각자 아침/저녁 위치 다르게 해줘"
근거: make_villager · eventSchedule.ts · npcActivity 조건 · list_npc_graphics

상점 + 계절 재고 + 상인 소지금 네이티브

상점 커맨드에 아이템별 계절 재고 레이어(stock[].seasons), 가격 오버라이드, 상인 매입 한도(merchantGold)까지 구현됨. "피에르 잡화점"이 그대로 표현됩니다. "씨앗 파는 잡화점 만들고, 봄 씨앗은 봄에만 팔게 해줘"
근거: shop 커맨드 · resolveShopStock · shop-stock-layers UI · merchantGold (commandBodyCommerce.ts)

광산 채광 + 턴제 전투 네이티브

곡괭이(pickaxe)의 "mine" 액션이 도구 시스템에 내장. 인카운터 테이블/필드 스폰으로 광산 몬스터 배치, 전투는 RM2k3식 턴제로 완비. "광산 맵에 광석 노드랑 몬스터 배치해줘"
근거: toolActions.ts (pickaxe → mine) · set_encounter_table / make_hunting_ground · src/battle/

멀티맵 월드 (마을↔농장↔광산) 네이티브

맵 그래프를 먼저 설계(plan_world)하고 빈 맵 생성(build_world) 후 워프 연결(link_maps)하는 선언적 워크플로가 전용 도구로 존재. "마을에서 농장으로, 농장에서 광산으로 이동 연결해줘"
근거: src/editor/tools/worldGraphTools.ts (plan_world / build_world / link_maps / lint_world)

날씨·조명 무드 + 컷신 + 계절 축제 네이티브

비/눈 날씨(setWeather), 맵 단위 조명 무드(set_scene_mood), 선언적 컷신 컴파일러(script_cutscene) 조합으로 오프닝·축제 연출 가능. season 조건으로 "봄 달걀 축제" 같은 계절 이벤트도 직결. "할아버지한테 농장 물려받는 오프닝 컷신 만들어줘"
근거: setWeather / set_scene_mood (lightingTools.ts) · script_cutscene (src/editor/cutscene/)
🟡

조합하면 가능 — 하지만 '우회'

전용 모델이 없어서 변수·분기·이벤트를 수동으로 엮어야 하는 영역. "된다"와 "제대로 된다"는 다릅니다.

호감도 / 선물 우회

주민마다 변수 1개를 할당하고, 선물 이벤트에서 변수를 올리고, 대사 분기를 변수 조건으로 거는 식으로 동작은 합니다.
한계: 하트 게이지 UI 없음, 주민 10명 = 변수 10개 수동 관리, 선물 "주는" 전용 인터랙션(아이템 들고 말걸기)이 없어 대화 선택지로 흉내.
코드에 'affinity/호감도' 검색 시 배틀 상성(type affinity)만 존재 — NPC 관계 모델 부재

결혼 우회

호감도 변수 임계값 도달 → 프러포즈 이벤트 → 결혼 후 동거 배치를 이벤트 페이지 분기로 구성 가능.
한계: "배우자"라는 게임 상태가 없어서 모든 후처리(아침 대사 교체, 집 배치)를 이벤트로 일일이 유지보수.
전용 상태 모델 없음 — 변수+스위치 조합 필요

출하함 (밤 정산) 우회

출하함 상점에 "팔기"로 넣고 판매액을 변수에 누적, 침대 수면 이벤트 진입 시 변수만큼 골드 지급 후 초기화 — 논리적으로 조립 가능.
한계: 상점 판매가 곧바로 골드 지급되는 구조라 "다음날 정산" 연출을 만들려면 전용 변수 회계를 저작자가 직접 설계해야 함.
코드에 shipping/출하 런타임 부재 (AI 프롬프트 예시에만 등장)

가축 사육 (닭·소) 우회

놀랍게도 닭·소 스프라이트 에셋은 번들되어 있습니다. NPC 이벤트로 배치하고 "매일 알/우유 수거"를 일일 리셋 이벤트로 흉내 가능.
한계: 에셋만 있고 가축 데이터 모델(먹이, 친밀도, 산출물 주기)이 없음. 작물 모델(farmModel)에 해당하는 livestock 모델 부재.
근거: assets/farming/animals/ 존재 vs farmModel.ts = 작물 전용

요리 / 제작 / 스킬 레벨 우회

선택지(choices) + 변수 + 아이템 증감으로 "재료 2개 → 요리 1개" 레시피는 구현 가능. 스킬 경험치도 변수로.
한계: 레시피 10개면 선택지 분기 10개 — 데이터 주도 테이블이 아니라 이벤트 하드코딩이 됨.
crafting/cooking 시스템 부재 — choices/variable 커맨드 조합

문답식 낚시 우회

"낚싯대를 던졌다… (wait) …입질이 왔다! → 성공/실패 랜덤 변수 → 물고기 획득" 수준의 텍스트 게임은 가능.
한계: 이건 낚시 '연출'이지 낚시 '게임'이 아님. 진짜 미니게임은 아래 ❌ 참조.
wait + 변수 랜덤 + choices 조합
❌

구현 불가 — 엔진 구조가 막는 영역

노력의 문제가 아니라 런타임 아키텍처의 문제. 엔진을 고치지 않는 한 프롬프트로는 안 됩니다.

실시간 낚시 미니게임 (게이지 타이밍 조작) 불가

스타듀 낚시의 핵심 — 물고기 아이콘을 따라 바를 실시간으로 움직이는 조작 — 은 실시간 입력 폴핑 + 연속 상태 갱신 루프가 필요합니다.
왜 안 되나: 이벤트 인터프리터는 커맨드를 위에서 아래로 순차 실행하는 RM2k3식 구조(src/player/interpreter.ts). 매 프레임 입력을 읽어 UI를 갱신하는 미니게임 프레임워크 자체가 없습니다.
src/player/interpreter.ts — 순차 커맨드 실행기, 실시간 입력 루프 부재

실시간 액션 전투 불가

광산에서 검을 휘둘러 슬라임을 때리는 스타듀식 전투는 불가. 이 엔진의 전투는 화면 전환형 턴제 하나뿐입니다.
왜 안 되나: src/battle/ 전체가 턴 상태기계. 필드 위 실시간 피격 판정(히트박스) 시스템이 없습니다. 추격 AI(make_chase_scene, A*)는 있으나 닿으면 killPlayer/배틀 진입이 전부.
src/battle/ (turn flow) · make_chase_scene = 접촉 트리거까지만

연속 실시간 시계 ("10분 = 7초") 불가

스타듀의 시계는 초 단위로 흐르지만, 이 엔진의 시간은 아침/낮/저녁/밤의 이산 단계(timePhase)입니다.
왜 안 되나: TimePhase가 타입 레벨에서 이산 열거로 정의(types/events.ts). 분 단위 연속 시간축과 그에 종속된 HUD 시계가 없습니다.
types/events.ts — { kind: "timePhase"; phase: TimePhase }

자유 HUD — 하트 게이지 / 스태미나 바 / 달력 위젯 불가

관계 시스템을 우회로 만들어도 보여줄 화면이 없습니다.
왜 안 되나: 플레이어 UI는 대화창·메뉴·숫자 입력으로 고정. 변수 값을 게이지 바로 렌더링하는 저작 수단이 없습니다(그림 표시 picture는 정적 오버레이 수준).
src/player/runtimeDom.ts · dialogueNumberInput.ts — 고정 UI 세트

멀티플레이어 / 협동 플레이 불가

스타듀 1.6식 4인 코-op은 처음부터 설계 밖.
왜 안 되나: 런타임이 단일 PlaySession(로컬 상태) 전제. 네트워크 동기화 레이어가 없고, Supabase는 프로젝트 저장용이지 세션 공유용이 아닙니다.
PlaySession = 싱글 세션 · supabaseProjectSync = 프로젝트 동기화 전용

유저 스크립트 / 모드로 우회 탈출 불가

"그럼 스크립트로 직접 짜면 되지 않나?" — 안 됩니다.
왜 안 되나: 프로젝트 데이터는 선언적 JSON이고 런타임에 임의 코드 실행 경로(eval, 스크립트 커맨드)가 없습니다. RM2k3의 "커맨드 조합" 철학을 그대로 계승 — 못 하는 건 엔진 패치가 유일한 길.
openwiki/runtime-and-data.md — authored JSON ↔ interpreter 구조

판정을 가르는 단 하나의 기준

이 분류는 전부 런타임 아키텍처에서 나옵니다. RPG ZZU는 RM2k3 계보의 "선언적 JSON 프로젝트 + 순차 커맨드 인터프리터 + 턴/메뉴 UI" 엔진입니다. 이 프레임 안에서 표현 가능한 것(✅), 조합으로 억지로 엮이는 것(🟡), 프레임 밖이라 손댈 수 없는 것(❌)이 자연스럽게 갈립니다.

✅ 쪽이 강한 이유농사·계절·시간·도구는 스타듀밸리 요청을 예상하고 엔진에 모델로 심어둔 영역 — farmModel, toolActions, timeSystem이 그 증거.
🟡 쪽의 본질전부 "관계·자원 회계" 문제. 변수+분기로 상태는 만들 수 있지만 데이터 주도 테이블이 아니라 이벤트 하드코딩이라 규모가 커질수록 물너짐.
❌ 쪽의 본질전부 "실시간성" 문제. 매 프레임 입력/갱신, 연속 시간, 히트박스 — 인터프리터 밖의 게임 루프가 필요한 것들.
제품적 시사점스타듀 수요를 노린다면 🟡의 반복 패턴 — 호감도·출하 정산·가축 모델 — 을 전용 도구로 승격하는 게 투자 대비 효과가 가장 큽니다. ❌는 엔진 로드맵 문제.
