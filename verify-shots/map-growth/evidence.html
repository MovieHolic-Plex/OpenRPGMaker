「맵 고쳐줘」 요청이 맵 크기를 바꾸지 않던 결함 — 네 지점 수정

resize_map 도구는 처음부터 있었고 core 로 상시 노출돼 있었다. 그런데도 수정 요청은 맵 크기를 한 번도 바꾸지 않았다 — 네 계층이 같은 방향으로 막고 있었기 때문이다. 아래 before/after 는 수정 전후 코드를 실제로 실행해 받은 문자열이다.

1. buildSpec — 기존 맵 확장 선언

before
에셋 '확장 마을' 영역(24,24) 30×20가 맵 크기 30×30 밖입니다.
after
통과 — 40×40 확장을 전제로 (24,24) 30×20 마을 승인
guard
plannedMap 20×20가 기존 맵 'm1' 30×30보다 작습니다. 기존 맵의 plannedMap 은 확장(현재 크기 이상)만 선언할 수 있습니다 — 줄이려면 경계 밖 이벤트를 먼저 move_event/remove_event 로 정리한 뒤 resize_map 을 직접 호출하세요.
코드 계산
plannedGrowthForSpec → {"width":54,"height":44}

2. specGate — 거부 문구가 resize_map 경로를 들고 온다

before
거부 안내가 전부 「영역을 좁히세요」 쪽으로만 유도 → 모델의 최소 수리는 늘 축소였다
after
맵 'm1'이 요구 영역보다 작습니다 — 영역을 좁히는 대신 키우는 것도 정답입니다. resize_map({mapId:"m1", width:26, height:26})을 먼저 호출한 뒤, 같은 크기를 plannedMap 으로 선언한 set_build_spec 을 제출하세요.
코드 계산
필요한 크기는 plannedGrowthForSpec 이 계산 — 모델이 숫자를 발명하지 않는다

3. author_village — 기존 맵 성장 목표

before
MIN_BOUNDS_SIZE(16×16)까지만 — 30×30 맵은 그대로 두고 집을 우겨넣음
after
집 수 환산값까지 성장: 집 12채 → 64×40, 집 20채 → 74×52
guard
bounds 를 명시하면 성장 없음(사용자가 정한 사각형), 축소 없음

4. intentDeclaration — 문장의 규모가 크기가 된다

before
construction 필드 없음 → 수량이 선언 계층에서 버려짐(환산기 호출자 0)
after
{"scale":"large","houseCount":20}
모델이 읽는 노트
[시공 규모] 선언된 수량: 규모 large · 집 20채. 코드가 환산한 권장 맵 크기는 74×52(집 20채 기준)이다. 대상 맵 'm_town' 은 30×30 로 부족하다. resize_map({mapId:"m_town", width:74, height:52}) 를 먼저 호출해 키운 뒤 시공하라 — 좌상단 기준 확장이라 기존 타일·이벤트는 그대로고 늘어난 칸만 잔디가 된다. 요청한 수량을 줄여 기존 크기에 우겨넣지 말 것.

실제 결과: 집 20채를 요청한 30×30 마을

좌상단 기준 확장 — 기존 타일·이벤트는 그 자리에 그대로 있고, 늘어난 칸만 잔디가 된다(비파괴).
