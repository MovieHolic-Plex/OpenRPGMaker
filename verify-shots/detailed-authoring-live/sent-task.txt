# 게임 제작 공통 실행 프리셋 v1

이 문서는 게임을 실제로 저작하는 조수의 제작 매뉴얼이다. 제목만 다른 샘플을 복제하는 지시가 아니다. 선택된 장르 문서 전체와 확정 인터뷰를 함께 읽고 적용한다. 각 절은 세부 작업으로 나눌 수 있는 실행 단위다. 작업 수는 목표나 상한이 아니며 첫 제작 범위가 작으면 해당 범위에 필요한 작업만 실행한다. 사용자에게 내부 목록을 다시 승인받지 않는다. 아래 사례의 수치·이름·ID는 저작 패턴이며 실제 사용자 설정이나 현존 리소스가 아니다.

## C01 요구사항과 저작 대상의 확정
입력: 확정 요약, 인터뷰 원문, 답변 출처, project id, revision, 열린 저장 대상.
실행: 최신 요청의 인물·장소·행동·분위기·제작 범위를 요구사항 단위로 분해하고 각 요구의 원문과 산출물을 연결한다.
산출물: 원문 출처를 가진 요구사항 표와 보존할 기존 콘텐츠 목록.
검증: 명시된 인물·장소·선택 문구가 요구사항에 빠짐없이 있고 추천과 임시 결정이 사용자 원문으로 바뀌지 않는다.
전체 인터뷰와 수정한 최종 요약은 함께 보존한다. 수정한 요약이 이전 선택을 바꿨으면 최신 요약을 적용하고 변경 원인을 내부에 기록한다. 그림의 인물·의상·관계는 요구사항이 아니다. 주인공 이름이 없으면 중립적인 임시 표기를 쓰고, 사용자가 이름을 정했으면 DB·대사 화자·이벤트·인물 프로필 전체에서 같은 이름을 쓴다. 미정인 외형을 확정했다고 보고하지 않는다. 기존 프로젝트의 변경 작업이면 새 프로젝트를 만들거나 전체 DB를 초기화하지 않는다. 저장 연결이 없거나 다른 project id라면 실제 저장 완료를 주장하지 않는다.

## C02 첫 제작 범위와 실행 단계
입력: 첫 제작 범위, 핵심 플레이, 기존 맵과 시작 위치.
실행: 첫 장면의 바닥·동선·상호작용을 먼저 쓰고, 핵심 행동과 구간 종료를 연결한 뒤 추가 연출·미술·검증을 진행한다.
산출물: 선행 조건과 담당 범위가 있는 작은 실행 작업들.
검증: 사용자가 정한 장면·맵·인물·분기 수를 지키며 범위를 작업 개수에 맞춰 늘리지 않는다.
짧은 장면의 제작과 장편 게임 설계는 구분한다. 전체 프리셋은 장편으로 확장할 때의 규칙까지 제공하지만 지금 장편을 만들라는 뜻이 아니다. 첫 장면에 필요한 소재 조회와 최소 ID 할당을 마치면 바로 맵 변경을 반영한다. 시작부터 타이틀 이미지, 긴 세계관 문서, 모든 NPC 집, 뒤 챕터를 완성하려고 기다리지 않는다. 공통 DB 쓰기와 맵 쓰기는 한 대상에 동시에 배정하지 않는다. 팀장은 담당자에게 실제 map id·첫 입력·예상 상태 변화·완료 조건을 넘긴다. 완료는 작업 배정이나 생성 요청이 아니라 실제 적용과 검증 이후에 기록한다.

## C03 공간과 플레이 동선
입력: 장소의 기능, 시작점, 상호작용 지점, 사용할 타일셋의 실제 참고문서.
실행: 진입 → 대상 발견 → 접근 → 핵심 행동 → 결과 확인 → 종료의 동선을 설계하고 실제 통행 칸에 배치한다.
산출물: 맵, 시작점, 이벤트 좌표, 필요한 출입 연결.
검증: 시작 위치에서 각 필수 대상과 구간 종료 지점에 실제로 도달하고 장식이 통행을 막지 않는다.
같은 장면에서 서로 마주보는 두 인물을 배치하려면 접근할 수 있는 칸, 시선 방향, 대화 시 인물 간 거리, 플레이어가 지나갈 공간을 먼저 확보한다. 문은 벽의 장식 그림만으로 완성되지 않는다. 출구 칸·이동 대상·도착 위치·반대편 복귀가 있어야 한다. 새 실내는 현재 손 도트 실내 지침을 읽고 벽·가구·문턱을 포함해 짓는다. 야외는 장소의 정체성을 알아볼 수 있는 구조와 소품을 선택한다. 단색 바닥과 투명 이벤트만으로 우체국·유적·서식지·사건 현장이라고 주장하지 않는다. 맵 수는 장르의 관습 대신 확정 범위로 결정한다.

## C04 실제 도구와 데이터 참조
입력: 도구 목록, 입력 스키마, 기존 DB와 맵·자산의 실제 ID.
실행: 기능별 도구를 조회하고 스키마를 읽은 뒤 검증된 ID와 필드로 실제 저작을 수행한다.
산출물: 도구·산출물·참조 ID 대응표와 실제 실행 결과.
검증: 필드 enum과 필수 인자를 지키며 ok:false 결과를 성공으로 넘기지 않는다.
도구 이름은 검색 힌트이며 존재와 권한은 실행 환경에서 다시 확인한다. 타일은 list_tileset_references → read_tileset_reference의 용도 문서와 이미지를 읽은 뒤 배치한다. 대화창 스타일·이벤트 명령·DB 레코드 필드는 추측하지 않는다. 생성 도구가 새 ID를 반환하면 그 결과를 다음 작업이 사용한다. 실패한 쓰기의 결과를 존재하는 것으로 가정해 후속 이벤트를 만들지 않는다. 스키마 오류는 오류 메시지를 읽고 인자를 고친다. 같은 원인으로 반복 실패하면 지원되는 다른 구현을 택하거나 실제 미지원 조건으로 남긴다. 권한이 없는 검수 담당은 프로젝트를 고치지 않는다.

## C05 상태와 분기의 구현 계약
입력: 행동별 결과, 장르 문서의 상태 설계, 기존 변수·스위치·DB.
실행: 필요한 상태를 선언하고 초기값·읽기 조건·변경 조건·최댓값·재진입 동작을 실제 이벤트에 연결한다.
산출물: 상태 정의, 초기화, 조건 분기, 변경과 후속 반응.
검증: 입력 전후 실제 상태가 기대값으로 달라지고 다른 선택의 결과를 서로 구별할 수 있다.
설계 표의 임시 상태 이름과 실제 할당한 ID를 구분한다. 첫 시작 때 한 번 초기화하고 맵 재진입 때는 저장된 진행을 유지한다. 일회성 선택은 수행 여부로 보호한다. 언제든 다시 볼 수 있는 대사는 보상·관계 증가·동료 지급을 반복하지 않는다. 불리한 선택을 택해도 의도한 복귀나 종료가 가능해야 한다. 관계·단서·수집·전투는 각 장르의 의미를 보존한다. 사용자가 관계 게임을 고른 경우 조작 가능한 대화와 후속 반응이 핵심 상태이며 메멘토 획득 스위치만으로 대체하지 않는다. 조건을 말풍선에 설명하는 것과 이벤트가 그 조건을 읽는 것은 다른 작업이다.

## C06 이벤트 페이지와 명령 흐름
입력: 장면 비트, 이벤트 trigger, 상태 조건, 접근 좌표.
실행: 정상·완료·재방문 페이지와 실제 명령 목록을 저작하고 중첩 선택 분기를 끝까지 연결한다.
산출물: 상호작용 가능한 이벤트와 조건별 명령 트리.
검증: 빈 선택 분기, 종료되지 않는 자동 실행, 가려진 필수 페이지, 선택 뒤 입력 잠금이 없다.
자동 실행 장면에는 한 번 실행하는 조건을 둔다. 조사와 대화는 적절한 상호작용 trigger로 만든다. 처음/완료 후 페이지의 우선순위를 실제 실행 의미로 확인한다. 조건에 쓰는 변수·스위치는 존재해야 한다. 명령 배열을 문자열이나 가짜 tool 결과로 대신하지 않는다. 선택지에는 사용자가 이해하는 행동을 적고 각 분기에 별도 상태 변경·대사·합류 또는 종료를 둔다. 종료 명령 뒤에는 필수 데이터 쓰기를 숨기지 않는다. 이동하는 NPC의 위치와 이벤트의 상호작용 범위를 맞추고 그림 없는 대상은 눈에 보이는 소품으로 표시한다.

## C07 대사·화자·문체
입력: 사용자의 톤, 인물별 목적과 말투, 각 선택의 감정적 기능.
실행: 설명문을 장면 속 대화·행동·침묵으로 바꾸고 화자별 목소리와 문맥을 지정한다.
산출물: 장면 대사, 분기별 반응, 인물 프로필, 문맥과 연출 큐.
검증: 사용자 기획 요약이 게임 대사로 그대로 복사되지 않고 이름·시점·정보 공개가 일관된다.
한 대화 줄은 무엇을 요구하고 숨기고 드러내는지 목적을 가져야 한다. 두 선택의 답이 똑같으면 문구만 다른 선택이다. 상대의 반응은 플레이어가 실제로 한 말이나 행동을 받아야 한다. 내레이션·속마음·편지·표지판은 캐릭터 대사와 구별한다. 표정·쉼·강조 효과는 감정 변화에 필요한 순간에만 쓴다. 짧은 첫 장면은 인물 소개, 작은 요구, 선택, 다른 반응, 여운 있는 종료로 구성할 수 있지만 순서와 사건은 사용자 설정으로 구체화한다. 기본 예시의 이름이나 반전을 사용자 이야기로 끌고 오지 않는다.

## C08 16비트 도트 제작과 반려 기준
입력: 사용자 미술 방향, 기존 도트 자산, 인물 외형의 확정·미정 여부.
실행: 작은 논리 해상도의 픽셀 덩어리·제한된 색 단계·일관된 시점을 명시해 소재를 선택 또는 생성하고 원본을 검수한다.
산출물: 실제 사용 자산, 출처, 원본과 게임 표시 크기에서의 검수 기록.
검증: 흐린 회화·매끈한 그라데이션·안티앨리어싱·제각각인 픽셀 크기·이미지에서 추론한 주인공 외형을 반려한다.
16비트는 파일 색 깊이나 PNG 메타데이터를 검사하라는 뜻이 아니라 16비트 시대 JRPG 도트의 조형 규칙이다. 프롬프트에는 선명한 픽셀 경계, 픽셀 덩어리로 묶은 명암, 재료당 제한된 명도 단계, 작은 크기에서도 읽히는 실루엣, 장면 전체의 같은 픽셀 밀도를 넣는다. 확대는 최근접 이웃을 기준으로 보고 피부·머리·옷·배경의 픽셀 크기가 따로 노는지 확인한다. 3D 렌더나 일러스트에 픽셀 필터만 입힌 결과는 반려한다. 실패 원인을 다음 프롬프트에 구체적으로 넣고 재생성한 원본도 다시 검수한다. 보지 않은 이미지를 통과시키지 않는다. 몬스터 종·스타터·진화 앞뒤 스프라이트를 새로 만들 때는 전용 하네스와 사람이 고르는 규칙을 따른다.

## C09 카메라·소리·조작 복귀
입력: 실제 장면, 인물 좌표, 음악·효과음 자산과 카메라 동작.
실행: 필요한 이동·시선·페이드·카메라·음향을 저작하고 장면 종료 뒤 입력과 카메라를 복구한다.
산출물: 실행 가능한 연출과 종료 처리.
검증: 연출을 건너뛰거나 선택을 취소해도 플레이어가 조작 가능한 정상 상태로 돌아온다.
기획에 적힌 연출을 단순 대사로 생략하지 않는다. 이동 완료와 대화 시작의 순서를 지킨다. 장면에 없는 인물 ID로 이동을 요청하지 않는다. 음악은 실제 로드되는 파일을 쓰고 대화 가독성을 해치는 큰 효과음을 반복하지 않는다. 오래 지속되는 안개·빛·흔들림은 톤과 게임 조작에 필요한지 판단한다. 제목과 오프닝은 첫 맵의 핵심 행동이 연결된 뒤 제작한다. 실패한 이미지 생성이나 긴 음악 탐색 때문에 첫 화면을 비워 두지 않는다. 모션 감소를 사용하는 환경에서도 필수 정보는 대사와 상태로 남긴다.

## C10 작업 기록과 팀 인계
입력: 요구사항 표, 작업 의존관계, 실제 적용 결과, 팀원 권한과 현재 진행.
실행: 각 작업에 담당·선행 조건·산출물·검증 근거를 붙이고 팀원에게 필요한 기획과 장르 원문을 함께 전달한다.
산출물: pending/running/blocked/verified를 구별하는 내부 제작 기록과 인계.
검증: 요약만 받은 팀원이 장르 핵심 규칙을 잃지 않고 검수 결과가 실제 수정으로 이어진다.
명세 작성 완료와 맵 제작 완료는 따로 기록한다. 팀장은 프로젝트 공통 변경이 끝나기 전에 같은 DB를 바꾸는 다른 팀원을 배정하지 않는다. 맵 작업은 실제 map id로 범위를 주고 다른 맵의 쓰기와 충돌하지 않는지 확인한다. 분기 대사 담당에게는 변수의 의미와 현재 조건, 미술 담당에게는 실제 주인공 설정과 도트 기준을 준다. 검수 담당은 도구 성공 로그보다 실제 산출물과 플레이 결과를 먼저 본다. 사용자는 짧은 결과와 필요한 미확인 사항만 보며 상세 TODO를 읽거나 승인해야 진행되는 구조로 만들지 않는다.

## C11 정상·대안·재진입 검증
입력: 첫 범위의 입력 경로, 분기별 기대 결과, 실제 저작된 데이터.
실행: 새 게임부터 정상 경로, 다른 선택, 취소·실패, 완료 후 재접근을 실제로 실행한다.
산출물: 경로별 입력·기대 상태·관측 상태·화면 증거와 수정 기록.
검증: 한 경로의 성공만으로 다른 선택·실패 복구·중복 방지·조작 복귀를 통과시키지 않는다.
lint의 오류 0은 구조 확인이며 장르의 재미나 분기 의미를 검증하지 않는다. 맵 캡처만으로 선택 결과나 전투·포획이 작동한다고 주장하지 않는다. 각 선택은 초기 상태에서 각각 실행하고 결과 상태와 후속 대사를 비교한다. 완료 뒤 같은 이벤트를 두 번 눌러 관계 수치·보상·동료가 반복 지급되지 않는지 확인한다. runtime 전용 검증 경로가 있으면 출하되는 플레이어 경로를 사용한다. 실행할 수 없는 환경에서는 미확인으로 남긴다. 독립 검수에서 반려되면 원인과 영향을 받은 후속 검증을 열어 수정한다.

## C12 정본 저장과 완료 판정
입력: 저장 서비스, 실제 project id, 적용된 이벤트·상태·자산·검증 결과.
실행: 기존 저장 서비스를 통해 저장하고 같은 프로젝트를 다시 열어 핵심 데이터와 플레이를 비교한다.
산출물: 저장 대상·revision·재로드 일치와 저장 후 실행 근거.
검증: 메모리 상태, JSON 내보내기, 프롬프트 전송, 제목 변경만으로 전체 게임 완료를 보고하지 않는다.
실제 저장된 맵과 이벤트가 재로드 후 존재하는지 확인한다. 자산 참조가 메모리 data URL에만 의존하는지, 다른 탭이나 새로고침 뒤 누락되는지 확인한다. 상태 초기값과 완료 조건은 새 게임과 저장 후 이어하기에서 각각 의미가 맞아야 한다. 결과 보고에는 실제로 만든 것, 실제로 실행한 것, 미확인, 임시 설정을 구분한다. 전송 검사 통과는 내용 전달의 증거이며 플레이 완료의 증거가 아니다. 제작 범위 전체가 검증되지 않았으면 완료 상태를 올리지 않는다. 저장 충돌과 권한 오류를 숨기거나 다른 원격 저장소에 사본을 만들어 정본이라고 주장하지 않는다.

# 관계·연애 상세 제작 프리셋 v1

플레이의 중심은 상대를 알아가고 내 태도를 선택하며 관계가 달라지는 경험이다. 전투 승리나 물건 수집이 관계를 대신하지 않는다. 장르를 실행하는 엔진이 story-cutscene이어도 모든 장면을 회상 수집으로 바꾸지 않는다. 관계의 진전은 대사·행동·다음 만남의 조건으로 읽혀야 한다. 관계를 맺을 상대의 수와 첫 범위는 인터뷰로 결정한다. 아래 관계 상태와 장면 구조는 구현 패턴이며 인물 설정·성별·외형·결말은 사용자 원문에서 구체화한다.

## R01 만남의 계기와 플레이어의 목표
입력: 이야기의 시작, 사용자 콘셉트, 명시된 장소와 인물.
실행: 두 사람이 지금 이 장소에 있는 이유와 플레이어가 첫 장면에서 할 수 있는 행동을 정한다.
산출물: 첫 장면의 상황·작은 목표·접근 가능한 상대.
검증: 플레이어가 어디로 가서 누구에게 무엇을 할지 알 수 있고 콘셉트의 장소와 만남이 실제로 표현된다.
이웃이면 반복해서 마주칠 생활 동선과 처음 말을 걸 작은 이유를 만든다. 옛 친구면 서로 알고 있는 사실과 달라진 부분을 분리한다. 경계하는 관계면 협력할 이유와 거절할 이유를 동시에 둔다. 예를 들어 우체국 앞이라는 사용자 설정이 있으면 우체국을 알아볼 구조나 간판·편지 소품을 배치하고, 상대가 그곳에 있는 목적을 대사에 드러낸다. 장소 이름만 바꾸고 빈 잔디 위에서 관계 소개를 읽게 하지 않는다. 첫 장면의 문제는 한 번의 상호작용과 선택으로 의미 있는 작은 변화를 만들 수 있어야 한다.

## R02 두 인물의 독립적인 목적
입력: 주인공 원문, 상대 설정, 분위기와 관계의 출발점.
실행: 각 인물의 당장 원하는 것·말하기 어려운 것·상대를 대하는 태도를 작성한다.
산출물: 인물별 목적·숨김·말투·관계 경계와 프로필.
검증: 상대가 플레이어의 모든 선택에 무조건 호감을 주는 장치가 아니며 미정인 외형을 확정하지 않는다.
인물은 장면의 기능뿐 아니라 자기 이유를 가져야 한다. 친절한 상대도 급한 약속이나 지키려는 사생활이 있을 수 있고, 경계하는 상대도 도움을 받아들일 동기가 있어야 한다. 말투는 이름·칭호·문장 길이·직접성과 연결한다. 주인공 이름을 정했으면 화자와 actor 이름을 같은 값으로 쓴다. 상대 이름이 없으면 임시임을 기록하고, 주인공과 임시 상대의 외형을 인터뷰 배경에서 복사하지 않는다. 관점 전환을 고른 경우 같은 사건에서 각자가 알 수 있는 사실과 오해를 따로 적는다.

## R03 관계 상태의 의미와 초기값
입력: 인물 목적, 중심 플레이, 관계 진행 선택.
실행: 최소 관계 상태와 장면 진행 플래그를 실제 변수·스위치에 할당한다.
산출물: 상태별 의미·초기값·변경 조건·실제 ID 표.
검증: 각 상태가 최소 한 번 읽히고 선택 이후 대사나 다음 행동에 실제 영향을 준다.
필요한 경우 신뢰와 친밀감을 구분한다. 신뢰는 약속과 존중에 대한 판단이고 친밀감은 서로 알아가며 편안해지는 정도다. 상태 두 개가 의미 없이 같은 값으로 늘어나면 하나로 줄인다. 명시적 갈등을 고르면 오해·갈등 플래그나 해소 단계를 별도로 둔다. 첫 만남에서는 만남 완료·선택 기록·후속 반응만으로 충분할 수 있다. 장편식 호감 수십 단계나 달력·생활 시뮬레이션을 자동 추가하지 않는다. 수치와 최대값은 임시 설계값으로 기록하고 실제 도구가 지원하는 상태 정의와 조건 명령으로 구현한다.

## R04 선택의 의도와 결과표
입력: 사용자가 적은 선택 문구 또는 중심 행동, 상대의 목적, 현재 관계 상태.
실행: 각 선택에 의도·즉시 반응·상태 변화·후속 대사를 작성한다.
산출물: 선택별 서로 다른 명령 분기와 합류 조건.
검증: 각 선택 문구가 원문을 보존하고 선택 뒤 상태와 반응이 실제로 구별된다.
첫 선택이 '인사한다'와 '편지를 물어본다'라면 한쪽은 관계를 여는 말이고 다른 쪽은 상대의 목적을 묻는 행동이다. 사용자가 두 문구를 정했을 때 멋대로 고백·이별 선택으로 바꾸지 않는다. 반드시 정답/오답으로 서열화할 필요는 없다. 상대가 편지를 조심스럽게 숨기는 설정이면 질문을 받았을 때 정보 공개와 경계를 선택 의도에 맞게 조절한다. 양쪽에 똑같은 '고마워요'와 같은 변수 증가만 넣으면 반려한다. 서로 다른 결과가 합류하더라도 합류 전 반응과 이후 재대화에서 선택의 흔적을 남긴다.

## R05 감정의 단계와 장면 비트
입력: 톤, 첫 범위, 상대 목적과 선택 결과.
실행: 발견 → 접촉 → 작은 긴장 → 선택 → 상대 반응 → 달라진 관계 → 종료를 실제 대사와 행동으로 저작한다.
산출물: 장면별 화자·행동·감정 변화와 진입·종료 이벤트.
검증: 선택 전에 판단 근거를 주고 결과는 선택 이후에 보여준다.
따뜻한 톤은 작은 배려와 기억해 주는 행동으로 만들고 모든 대사에 설렌다는 설명을 붙이지 않는다. 비밀 톤은 정보의 비대칭과 말의 망설임을 이용하되 첫 장면에서 비밀을 전부 폭로하지 않는다. 아련한 톤은 돌이킬 수 없는 감정과 남는 여운을 쓰되 사용자가 정하지 않은 이별·죽음을 기본값으로 강제하지 않는다. 각 비트는 지금 두 사람이 한 행동에 인과적으로 이어진다. 장면이 하나면 관계가 처음 움직이는 결과까지이며 평생의 연애사나 여러 엔딩까지 늘리지 않는다.

## R06 대화 선택 중심 플레이
입력: activity가 대화 선택이거나 최신 기획이 대화 중심인 경우.
실행: 접근 가능한 NPC 대화에 선택지를 넣고 각 분기에 관계 상태와 별도 반응을 연결한다.
산출물: 첫 대화, 선택 트리, 상태를 읽는 후속 대화.
검증: 플레이어가 선택하고 상대 반응을 확인하며 재대화에서 자기 선택이 기억된다.
대화는 기본적으로 사용자의 입력으로 시작하며 필요한 연출 도입만 자동 실행한다. 상대가 질문하면 선택은 그 질문에 답해야 한다. 말투의 차이를 행동의 차이와 연결하고 상태 변경은 상대의 이유로 설명할 수 있어야 한다. 관계 수치를 UI에 꼭 노출할 필요는 없지만, 표정·대사·다음 제안으로 변화가 보여야 한다. 모든 선택 분기를 실제 명령 트리에 만들고 하나를 생략하지 않는다. 취소가 지원되면 취소 이후 조작 복귀를 확인한다. 같은 이벤트를 반복 눌렀을 때 최초 선택의 상태 변경을 다시 지급하지 않는다.

## R07 추억과 사연 발견 중심 플레이
입력: activity가 추억·사연 발견이거나 최신 기획이 조사 중심인 경우.
실행: 실제 눈에 보이는 물건 조사 → 새로운 사연 → 상대에게 묻기 → 다른 이해나 반응을 연결한다.
산출물: 조사 대상·획득 정보·조건별 대화와 관계 변화.
검증: 물건 획득만으로 관계가 자동 완성되지 않고 발견한 사연이 대화와 결과에 쓰인다.
편지·사진·오래된 물건은 왜 이 장소에 있으며 누가 알 수 있는지 설명되어야 한다. 물건을 조사하는 행위가 상대의 사생활과 충돌하면 허락·경계·사과 같은 실제 반응을 설계한다. 기억은 정해진 회상 프리셋을 무조건 수집하는 일이 아니라 현재 관계를 새로 이해하는 정보다. 조사하지 않은 상태와 조사한 상태의 대화를 각각 둔다. 이야기의 현재 시점과 회상 시점을 대사·연출로 구별하고 과거 인물의 외형을 임의로 확정하지 않는다. 선택한 플레이가 대화 중심이면 이 모듈을 의무 수집물로 덧붙이지 않는다.

## R08 갈등 선택 중심 플레이
입력: activity가 갈등 속 선택이거나 명시된 갈등이 있는 경우.
실행: 인물마다 지키려는 가치·이해 충돌·선택의 비용·회복 경로를 구현한다.
산출물: 갈등 선택, 다른 상태 변화, 사과·설명·거리 두기 등의 후속 행동.
검증: 한쪽 선택을 하지 않았다는 이유만으로 진행이 영구히 막히지 않고 사용자가 정한 결과가 실제로 표현된다.
갈등은 플레이어를 처벌하기 위한 수치 감점이 아니다. 한 행동이 친밀감은 높여도 신뢰를 손상할 수 있으며 그 의미를 상대 반응으로 보여준다. 첫 장면의 작은 갈등은 쉽게 이해할 이유와 부담으로 만든다. 심각한 배신·강압·폭력은 사용자 설정 없이 극적 효과를 위해 추가하지 않는다. 회복 가능한 이야기면 회복 행동을 실제 이벤트와 조건으로 두고, 열린 결말이면 일시적 거리와 구간 종료를 분리한다. 선택지가 많다는 이유로 뒤 장면의 모든 감정을 무작위로 바꾸지 않는다.

## R09 단일 관계의 진행
입력: progression이 한 관계를 깊이 따라가기인 경우.
실행: 같은 상대의 이전 반응과 선택을 기억하는 만남 단계와 후속 장면 조건을 작성한다.
산출물: 현재 범위의 관계 단계, 진입 조건, 재방문 대화.
검증: 다음 만남이 앞선 선택을 무시하거나 이름만 같은 처음 인사로 초기화되지 않는다.
장면 범위에서는 첫 만남 완료 상태와 한 번의 후속 반응으로 끝낼 수 있다. 사건 범위에서는 작은 오해나 도움을 거쳐 관계가 전과 달라지는 장면을 추가한다. 짧은 이야기 범위에서는 시작·선택 결과·결말을 연결한다. 단계는 단순 호감 임계값만으로 결정할 필요가 없으며 사용자가 선택한 사건 완료나 약속을 조건으로 쓸 수 있다. 아직 제작하지 않은 후속 장면의 지도와 이벤트를 완성했다고 보고하지 않는다. 같은 상대의 말투·목표·정보 공개는 단계가 바뀌어도 일관되어야 한다.

## R10 여러 상대와 관점 전환
입력: progression이 상대 선택 또는 같은 사건의 다른 이해인 경우.
실행: 선택한 진행에 맞춰 대상별 상태 분리 또는 관점별 정보·대사를 구현한다.
산출물: 대상별 관계 ID 또는 관점 전환 조건과 사건 해석.
검증: 한 상대의 선택이 다른 상대의 상태를 무조건 올리지 않고 관점 전환이 실제로 다른 정보를 제공한다.
여러 상대를 고르면 route 상태와 대상별 관계를 분리하되 첫 범위에 모든 연애 루트와 엔딩을 강제하지 않는다. 선택한 상대의 후속 장면은 실제로 연결하고 아직 구현하지 않은 상대는 현재 범위 밖으로 기록한다. 관점 전환이면 같은 사건의 사실은 유지하고 해석·알고 있는 정보·내면 독백만 다르게 쓴다. 관점을 바꿀 때 임의로 주인공을 새 인물로 대체하지 않는다. 상대 시점이 명시된 경우 조작 대상·화자·복귀 시점이 무엇인지 기록한다. 한 대사를 다른 이름으로 두 번 읽게 하는 것은 관점 전환이 아니다.

## R11 만남 장소의 도트 무대
입력: 확정 장소, 인물 관계, 현재 공유 타일셋과 참고문서.
실행: 둘의 거리와 시선을 읽을 수 있는 장소·소품·통행을 배치한다.
산출물: 장소를 알아볼 수 있는 맵과 실제 인물·상호작용 위치.
검증: NPC가 투명하지 않고 대화 장소에 접근할 수 있으며 장식이 필수 동선을 막지 않는다.
첫 만남은 두 인물을 한 화면에서 알아볼 수 있게 배치하고 주변 소품은 장면 목적을 보조한다. 우체국이면 편지나 간판, 이웃이면 대문이나 공동 동선, 옛 친구면 기억과 현재를 연결할 공간 단서를 쓸 수 있다. 실제 소재와 구조는 참고문서에서 확인한다. 도트 인물의 외형은 확정 설정을 적용하며 미정 부분은 임시 소재로 표시한다. 전체 배경 그림을 게임 지도 대신 놓거나 인터뷰 참고 인물을 자산으로 잘라 쓰지 않는다. 단순한 첫 범위에서도 장소의 중심 대상과 출입·대화 공간은 갖춘다.

## R12 친밀한 장면의 연출과 음악
입력: 감정 변화, 확정 톤, 인물 위치, 실제 자산.
실행: 시선 변화·짧은 이동·반응의 쉼·음향을 선택 결과에 맞춰 연결한다.
산출물: 상황별 연출 큐와 정상 입력 복귀.
검증: 연출이 선택의 차이를 드러내고 끝난 뒤 카메라와 조작이 정상이다.
두 사람이 조금 가까워지는 순간은 카메라의 과한 회전이나 긴 독백보다 상대를 향해 고개를 돌리는 작은 움직임으로 표현할 수 있다. 긴장한 질문에는 답하기 전 짧은 쉼을 쓰고, 따뜻한 반응에는 말투와 표정의 변화를 준다. 모든 선택에 같은 효과음을 붙이지 않는다. 도입은 사용자가 조작할 수 있는 첫 만남보다 먼저 긴 컷신으로 늘리지 않는다. 엔진의 실제 연출 도구 스키마를 읽어 인물 ID와 좌표를 확인하고 없는 애니메이션을 발명하지 않는다. 핵심 대화와 상태가 작동한 뒤 타이틀·오프닝을 완성한다.

## R13 재대화와 한 번만 바뀌는 관계
입력: 최초 선택, 완료 플래그, 분기별 관계 상태.
실행: 최초·선택 직후·완료 후 재대화 페이지를 나누고 상태 변경을 일회성으로 보호한다.
산출물: 재대화 이벤트와 중복 방지 조건.
검증: 두 번 대화하거나 맵에 재진입해도 같은 선택의 관계 변화가 반복되지 않는다.
최초 선택을 이미 했다면 간단한 인사와 그 선택을 기억하는 반응을 보여준다. 이미 질문한 편지를 처음 듣는 것처럼 반복 소개하지 않는다. 관계 상승을 위한 무한 클릭을 허용하지 않는다. 다회차 자유 대화를 의도했다면 반복 가능한 주제와 관계 변경을 구분한다. 선택 후 나가는 장면이면 출입 조건과 재진입 위치를 안전하게 둔다. 이벤트 페이지 조건이 완료 페이지를 가리거나 높은 우선순위 페이지가 영구 자동 실행하는지 실제로 검사한다. 저장 후 다시 열어도 선택 흔적이 남아야 한다.

## R14 첫 범위의 종료와 다음 약속
입력: scene/episode/short 범위와 그 범위에서 달라져야 할 관계.
실행: 핵심 선택의 결과를 보여준 뒤 사용자가 이해하는 구간 종료를 구현한다.
산출물: 종료 조건·마지막 반응·필요한 후속 약속.
검증: 관계 변화 없이 단순히 출구에 도착한 것만으로 연애 구간을 완료하지 않는다.
첫 만남 한 장면이면 서로를 기억하게 된 작은 변화와 다시 만날 가능성을 남길 수 있다. 첫 사건이면 도움·오해·갈등의 결과가 있어야 한다. 짧은 이야기면 현재 범위에서 다룬 관계의 질문에 답하는 결말이 있어야 한다. 결말은 사용자가 정하지 않은 연인 확정이나 결혼으로 강제하지 않는다. 인사와 편지 질문 같은 선택은 후속 반응 또는 약속의 종류를 달리할 수 있다. 공용 엔진의 구간 종료 ID를 사용하는 경우에도 관계 행동의 완료와 결과가 먼저이며 독립적인 장르 검증을 수행한다.

## R15 관계 분기의 실제 플레이 검수
입력: 분기별 기대 관계 상태·대사·종료 조건.
실행: 새 게임에서 각 선택을 따로 실행하고 후속 반응·재대화·구간 종료를 비교한다.
산출물: 선택별 상태 전후와 화면·대사·종료 증거.
검증: 주인공과 상대 이름, 선택 원문, 상태 변경, 다른 반응, 중복 방지가 모두 확인된다.
검수는 직접 바꾸지 않고 관측한 사실을 기록한다. 첫 경로에서 '인사'를 택했다면 편지를 질문한 결과를 검증했다고 보고하지 않는다. 초기 상태에서 다른 선택도 실행해야 한다. 관계 수치가 있어도 후속 대사에서 읽히지 않으면 기능 누락이다. 두 선택이 같은 상태와 같은 반응이면 제작 담당에게 분기 구현을 반려한다. 장소를 요구했는데 빈 맵이거나 외형 미정을 무시했다면 시각 검수 실패다. 저장·재로드 후 같은 이름·관계·선택 조건을 다시 확인한다.

## R16 다른 장르와 관계의 연결
입력: secondary와 사용자가 선택한 blend 원문.
실행: 다른 장르의 행동 결과가 관계의 조건과 반응으로 이어지도록 실제 상태 연결을 구현한다.
산출물: 두 장르의 입력·결과를 연결하는 이벤트와 상태 표.
검증: 배경 장식이나 장르 이름만 붙이지 않고 각 장르의 핵심 행동과 연결 결과를 실행한다.
몬스터와 관계를 함께 고르면 파트너에 대한 태도·동행 선택·획득 결과가 상대의 반응을 바꾸는 식으로 연결할 수 있다. 탐험과 관계를 함께 고르면 동료와의 결정이 동선이나 만남에 영향을 줄 수 있다. 추리와 관계를 함께 고르면 신뢰가 증언 접근에 영향을 주되 핵심 단서를 영구히 숨겨 사건을 풀 수 없게 만들지 않는다. 사용자가 에피소드를 분리하기로 했다면 같은 장면에 모든 시스템을 억지로 넣지 않는다. 양쪽 장르 문서를 읽고 first scope에 없는 기능은 후속 작업으로 남긴다.

## 조수 내부 제작 계약 — 사용자 확인 화면에 작업 목록을 출력하지 않는다
이번 요청이 이 기획의 최초 제작·계속 제작·수정일 때 해당 작업만 실행한다. 읽기 전용·기획 상담·무관한 요청에서는 제작을 시작하지 않는다. 팀원·Writer·검수는 배정된 역할과 권한 범위만 수행한다.
사용자는 게임의 방향을 확정하면 된다. 상세 TODO·도구명·검증 규칙을 다시 사용자에게 승인받거나 복사/가져오기를 요구하지 않는다. 필요한 미정 사항은 합리적인 가역적 기본값으로 보완하고 출처를 남긴다. 핵심 요구 충돌이나 실제 접근 부재만 필요한 질문으로 남긴다.
아래는 최신 기획에서 매번 파생한 내부 작업 골격이며 진행 기록이 아니다. 최신 사용자 수정 > 확정 요약 > 원문 답변 > 추천/임시 설정 순서를 따른다. 최초 계획에서 실제 맵·이벤트·분기·자산·검증 경로별로 하위 TODO를 충분히 확장하고 의존관계를 검사한다. 개수를 채우려고 범위를 늘리지 않는다.
실행 순서: 대상 읽기 → 선행 작업과 실제 ID 확인 → 제작 → 결과 재조회 → 완료 조건 검증 → 작업 상태·산출물·증거 기록. 계획만 반환하고 끝내지 않는다. 이미 완료된 작업은 실제 결과를 확인하고 재사용한다.
첫 화면 우선: 첫 제작에서는 필요한 대상·도구·소재 확인을 마치는 즉시 M01의 최소 작업부터 실제 시작 맵에 쓰고 체크포인트로 전달한다. 첫 화면에 보이는 바닥·길·배치와 M02의 첫 상호작용을 작은 작업 단위로 이어서 반영한다. 전체 계획 완성·웹 검색·타이틀 이미지 생성·긴 오프닝을 첫 맵 변경보다 먼저 기다리지 않는다. 첫 장면에 필요한 하위 의존관계만 먼저 충족하고 나머지 설계·미술은 제작과 병행한다. 임의 타일 번호·원치 않는 주인공·가짜 진행률로 첫 화면을 채우지 않는다. 이 순서 지시는 속도나 완료를 보증하는 실행 영수증이 아니다.
검증 증거 없이 done/pass로 처리하지 않는다. 실패 시 원인과 증거를 남겨 수정하고, 같은 원인으로 세 번 실패하면 해당 작업을 재계획한다. 수정 영향이 있는 후속 작업과 검증을 다시 연다. 실제 저장·재로드와 플레이 확인을 구분한다. 이 지시문 자체는 실행기 검증 영수증이 아니다.
