# 캐릭터 칩 선택 수정 · 2026-10-05

## 원인과 변경

기존 조수의 칩 검색은 이름·태그·외형 설명·시트/칸 번호를 반환했으며 실제 칩 이미지를 전달하지 않았다. 저수준 이벤트의 sprite/pattern을 선택 결과와 대조하는 관문도 없었다. 골렘 정본은 monster2의 4번 칸(아래 정지 프레임 73), 왕은 people3의 0번 칸(25)이다.

검색 결과 순서와 같은 번호의 원본 크롭을 함께 전달하고, 정확한 결과 본문+PNG가 실제 제공자 입력에 포함된 뒤 성공 응답이 끝난 후보만 적용한다. 새/변경 외형을 후보 ID와 비교하고 실패 쓰기를 원자적으로 되돌린다. 기존 그림을 유지하는 대사·위치 수정은 허용한다. 고수준 selectionId+query는 외형 질의도 대조하며 슬롯→프레임 계산을 도구가 한다. 업로드 시트도 파일명/ID로 실제 8칸을 검색한다. 50개 후보는 504×480 PNG로 전달한다.

## 실제 조수 검증

`assistant-capability`의 실제 입력창 → Pi → google-antigravity/gemini-3.8-flash 경로를 사용했다. 모델 대체나 완료 선언으로 판정하지 않았다. 테스트 프로젝트는 별도 SQLite 폴더다.

- 골렘: r2 실제 실행에서 4턴/4도구, 도구 오류 0. 원본 trace의 이미지 입력 응답 완료 뒤 monster2 frame 73으로 변경했다. 대사·조건·다른 페이지·다른 NPC·타일·DB 전체 보존, player.html의 시작/대화/재대화 6비트, SQLite 저장·새 context 재로드와 실제 PNG 검수를 통과했다. project id/정본 경로/같은 SHA-256 재로드는 golem-receipt.json.
- 왕: r5의 명시 `/pi` 실제 입력에서 요구·보존·플레이 6비트·저장·시각 6개 관문 모두 통과했다. 실행 단계는 4턴/5도구, 도구 오류 0이고 실제 후보 이미지 수신 뒤 people3 frame 25를 적용했다. 같은 프로젝트 ID `5c43a671-14e9-4a58-8734-d6685a4972b2`의 revision 4를 새 context에서 다시 읽었으며 전체 SHA-256 `20189e2e2e7c31c98344956c3780b19bc79fa4348a3d96371cf1be80a71d32b2`가 일치했다. 정본 경로·모델 요청·시각 영수증은 king-receipt.json.
- 앞선 왕 r3의 일반 자연어 입력에서도 정확한 frame 25, 보존·플레이 6비트는 통과했다. 재로드 사이 공용에 독낭가시개가 추가되어 전체 문서 해시가 달라졌으므로 저장 관문은 실패로 남겼다. r4는 과제별 공용 SQLite backup으로 판본을 고정했지만 제품 의도 분류의 30초 제한에서 실패하여 Pi에 도달하지 못했다. r5 명시 Pi 결과는 기본 자연어 의도 분류 성공으로 집계하지 않는다.
- 대사 보존: r3 실제 Pi 4턴/3도구·도구 오류 0, 요구·보존·플레이가 통과했고 같은 공용 라이브러리 추가로 전체 저장 해시가 달라져 저장 관문은 실패했다. r5 명시 `/pi` 실제 입력은 요구·보존·플레이 6비트·저장·시각 6개 관문 모두 통과했다. 실행 단계 4턴/3도구·도구 오류 0이며 칩 조회 없이 기존 그림을 보존했다. project id `cb0524ba-5662-4eec-8ccd-74f492bb1173`, revision 4, 동일 전체 SHA-256 `3a6d7332645c66b903bc08d35943aca9a7c8e3404094fd2faa193dfcf9026c96`; 정본 경로와 재로드 근거는 line-receipt.json.

최초 r1은 Gemini가 텍스트 블록을 합쳐 JSON+별도 번호 설명이 하나가 되는 실제 제공자 계약을 놓쳐 실패했다. 번호 설명을 JSON 안에 넣고 실제 중첩 functionResponse.parts 회귀를 추가했다. r2 골렘의 후속 캡처는 미완료 글꼴 로딩 때문에 시간 초과했다. 저장 결과를 바꾸거나 모델을 재호출하지 않고 recheck로 재로드·플레이·이미지를 확인했으며 원래 실패는 verification-history에 보존했다. r2 왕은 입력 전 로딩, r2 대사 수정은 라우터 응답 대기로 시간 초과했다. 해당 시도도 보존한다.

## 코드 검사

- 관련 Vitest 4파일/56케이스: threads, 2워커, exit 0. 마지막 50칩 미리보기 크기 수정 후 해당 회귀 파일 15케이스 별도 exit 0(기존 42+최종 15).
- 앱 타입 게이트: errors 0 / exit 0 / 기준선 대비 회귀 없음.
- 최종 packaged 빌드: exit 0. Electron 빌드도 exit 0.
- 검증기 자체 반례 교정: r5 self-check 61/61, self-check.json 영수증 보존.
- surface 게이트는 기본 병렬 실행이 종료된 뒤 CPU 2개로 범위를 묶어 실행했으며 기존 셸 표면 기대값 실패와 8GB 힙 OOM/결과 누락, .ee-icon margin-top CSS 기준선 실패로 exit 1이었다. 해당 CSS 실패와 셸 22케이스 중 같은 2개 실패는 수정 전 HEAD 소스 사본에서도 똑같이 재현됐다. 기준선 사본은 src/scripts/test를 git archive로 추출하고 변경하지 않은 assets/public 및 의존성만 연결했다. 심볼릭 링크 그림에 대한 Vite 파일 접근 경계만 테스트 사본에서 허용했다. 전체 표면 게이트의 통과를 주장하지 않는다.
- 추가 Bun 툴 발견 검사 8케이스 통과. 기존 map-image mock 검사는 시간 초과했으며 render 재전송 기대값도 현재 ACK 계약과 어긋났다. piRenderBroker.ts의 SHA-256은 수정 전 HEAD와 동일(29f0cf4a5716afa6d28421c232da2cc7d48c5ec7dab4e50d4e5de992403f2e21). 전체 스위트의 통과로 보고하지 않는다.

## 범위

이미지 수신 증거는 모델이 모든 후보의 의미를 항상 정확히 이해한다는 보증이 아니다. 실제 시험은 선택된 과제/모델에 대한 관찰이며 core 12개 전체 수행률이나 다른 모델의 성공률로 확대하지 않는다.

시험 시점 codeCommit은 기준선 HEAD다. 미커밋 수정의 실제 소스 SHA-256은 verified-source.json(최종 기능 코드)과 verified-source-r5.json(판본 고정·명시 Pi 하네스 포함)에 따로 보존했다.
