# 게임 제작 공통 실행 프리셋 v1

이 문서는 게임을 실제로 저작하는 조수의 제작 매뉴얼이다. 제목만 다른 샘플을 복제하는 지시가 아니다. 선택된 장르 문서 전체와 확정 인터뷰를 함께 읽고 적용한다. 각 절은 세부 작업으로 나눌 수 있는 실행 단위다. 작업 수는 목표나 상한이 아니며 첫 제작 범위가 작으면 해당 범위에 필요한 작업만 실행한다. 사용자에게 내부 목록을 다시 승인받지 않는다. 아래 사례의 수치·이름·ID는 저작 패턴이며 실제 사용자 설정이나 현존 리소스가 아니다.

## C01 요구사항과 저작 대상의 확정
입력: 확정 요약, 인터뷰 원문, 답변 출처, project id, revision, 열린 저장 대상.
실행: 최신 요청의 인물·장소·행동·분위기·제작 범위를 요구사항 단위로 분해하고 각 요구의 원문과 산출물을 연결한다.
산출물: 원문 출처를 가진 요구사항 표와 보존할 기존 콘텐츠 목록.
검증: 명시된 인물·장소·선택 문구가 요구사항에 빠짐없이 있고 추천과 임시 결정이 사용자 원문으로 바뀌지 않는다.
전체 인터뷰와 수정한 최종 요약은 함께 보존한다. 수정한 요약이 이전 선택을 바꿨으면 최신 요약을 적용하고 변경 원인을 내부에 기록한다. 그림의 인물·의상·관계는 요구사항이 아니다. 주인공 이름이 없으면 중립적인 임시 표기를 쓰고, 사용자가 이름을 정했으면 DB·대사 화자·이벤트·인물 프로필 전체에서 같은 이름을 쓴다. 미정인 외형을 확정했다고 보고하지 않는다. 기존 프로젝트의 변경 작업이면 새 프로젝트를 만들거나 전체 DB를 초기화하지 않는다. 저장 연결이 없거나 다른 project id라면 실제 저장 완료를 주장하지 않는다.

## C02 첫 제작 범위와 실행 단계
입력: 첫 제작 범위, 핵심 플레이, 기존 맵과 시작 위치.
실행: 첫 장면의 바닥·동선·상호작용을 먼저 쓰고, 핵심 행동과 구간 종료를 연결한 뒤 추가 연출·미술·검증을 진행한다.
산출물: 선행 조건과 담당 범위가 있는 작은 실행 작업들.
검증: 사용자가 정한 장면·맵·인물·분기 수를 지키며 범위를 작업 개수에 맞춰 늘리지 않는다.
짧은 장면의 제작과 장편 게임 설계는 구분한다. 전체 프리셋은 장편으로 확장할 때의 규칙까지 제공하지만 지금 장편을 만들라는 뜻이 아니다. 첫 장면에 필요한 소재 조회와 최소 ID 할당을 마치면 바로 맵 변경을 반영한다. 시작부터 타이틀 이미지, 긴 세계관 문서, 모든 NPC 집, 뒤 챕터를 완성하려고 기다리지 않는다. 공통 DB 쓰기와 맵 쓰기는 한 대상에 동시에 배정하지 않는다. 팀장은 담당자에게 실제 map id·첫 입력·예상 상태 변화·완료 조건을 넘긴다. 완료는 작업 배정이나 생성 요청이 아니라 실제 적용과 검증 이후에 기록한다.

## C03 공간과 플레이 동선
입력: 장소의 기능, 시작점, 상호작용 지점, 사용할 타일셋의 실제 참고문서.
실행: 진입 → 대상 발견 → 접근 → 핵심 행동 → 결과 확인 → 종료의 동선을 설계하고 실제 통행 칸에 배치한다.
산출물: 맵, 시작점, 이벤트 좌표, 필요한 출입 연결.
검증: 시작 위치에서 각 필수 대상과 구간 종료 지점에 실제로 도달하고 장식이 통행을 막지 않는다.
같은 장면에서 서로 마주보는 두 인물을 배치하려면 접근할 수 있는 칸, 시선 방향, 대화 시 인물 간 거리, 플레이어가 지나갈 공간을 먼저 확보한다. 문은 벽의 장식 그림만으로 완성되지 않는다. 출구 칸·이동 대상·도착 위치·반대편 복귀가 있어야 한다. 새 실내는 현재 손 도트 실내 지침을 읽고 벽·가구·문턱을 포함해 짓는다. 야외는 장소의 정체성을 알아볼 수 있는 구조와 소품을 선택한다. 단색 바닥과 투명 이벤트만으로 우체국·유적·서식지·사건 현장이라고 주장하지 않는다. 맵 수는 장르의 관습 대신 확정 범위로 결정한다.

## C04 실제 도구와 데이터 참조
입력: 도구 목록, 입력 스키마, 기존 DB와 맵·자산의 실제 ID.
실행: 기능별 도구를 조회하고 스키마를 읽은 뒤 검증된 ID와 필드로 실제 저작을 수행한다.
산출물: 도구·산출물·참조 ID 대응표와 실제 실행 결과.
검증: 필드 enum과 필수 인자를 지키며 ok:false 결과를 성공으로 넘기지 않는다.
도구 이름은 검색 힌트이며 존재와 권한은 실행 환경에서 다시 확인한다. 타일은 list_tileset_references → read_tileset_reference의 용도 문서와 이미지를 읽은 뒤 배치한다. 대화창 스타일·이벤트 명령·DB 레코드 필드는 추측하지 않는다. 생성 도구가 새 ID를 반환하면 그 결과를 다음 작업이 사용한다. 실패한 쓰기의 결과를 존재하는 것으로 가정해 후속 이벤트를 만들지 않는다. 스키마 오류는 오류 메시지를 읽고 인자를 고친다. 같은 원인으로 반복 실패하면 지원되는 다른 구현을 택하거나 실제 미지원 조건으로 남긴다. 권한이 없는 검수 담당은 프로젝트를 고치지 않는다.

## C05 상태와 분기의 구현 계약
입력: 행동별 결과, 장르 문서의 상태 설계, 기존 변수·스위치·DB.
실행: 필요한 상태를 선언하고 초기값·읽기 조건·변경 조건·최댓값·재진입 동작을 실제 이벤트에 연결한다.
산출물: 상태 정의, 초기화, 조건 분기, 변경과 후속 반응.
검증: 입력 전후 실제 상태가 기대값으로 달라지고 다른 선택의 결과를 서로 구별할 수 있다.
설계 표의 임시 상태 이름과 실제 할당한 ID를 구분한다. 첫 시작 때 한 번 초기화하고 맵 재진입 때는 저장된 진행을 유지한다. 일회성 선택은 수행 여부로 보호한다. 언제든 다시 볼 수 있는 대사는 보상·관계 증가·동료 지급을 반복하지 않는다. 불리한 선택을 택해도 의도한 복귀나 종료가 가능해야 한다. 관계·단서·수집·전투는 각 장르의 의미를 보존한다. 사용자가 관계 게임을 고른 경우 조작 가능한 대화와 후속 반응이 핵심 상태이며 메멘토 획득 스위치만으로 대체하지 않는다. 조건을 말풍선에 설명하는 것과 이벤트가 그 조건을 읽는 것은 다른 작업이다.

## C06 이벤트 페이지와 명령 흐름
입력: 장면 비트, 이벤트 trigger, 상태 조건, 접근 좌표.
실행: 정상·완료·재방문 페이지와 실제 명령 목록을 저작하고 중첩 선택 분기를 끝까지 연결한다.
산출물: 상호작용 가능한 이벤트와 조건별 명령 트리.
검증: 빈 선택 분기, 종료되지 않는 자동 실행, 가려진 필수 페이지, 선택 뒤 입력 잠금이 없다.
자동 실행 장면에는 한 번 실행하는 조건을 둔다. 조사와 대화는 적절한 상호작용 trigger로 만든다. 처음/완료 후 페이지의 우선순위를 실제 실행 의미로 확인한다. 조건에 쓰는 변수·스위치는 존재해야 한다. 명령 배열을 문자열이나 가짜 tool 결과로 대신하지 않는다. 선택지에는 사용자가 이해하는 행동을 적고 각 분기에 별도 상태 변경·대사·합류 또는 종료를 둔다. 종료 명령 뒤에는 필수 데이터 쓰기를 숨기지 않는다. 이동하는 NPC의 위치와 이벤트의 상호작용 범위를 맞추고 그림 없는 대상은 눈에 보이는 소품으로 표시한다.

## C07 대사·화자·문체
입력: 사용자의 톤, 인물별 목적과 말투, 각 선택의 감정적 기능.
실행: 설명문을 장면 속 대화·행동·침묵으로 바꾸고 화자별 목소리와 문맥을 지정한다.
산출물: 장면 대사, 분기별 반응, 인물 프로필, 문맥과 연출 큐.
검증: 사용자 기획 요약이 게임 대사로 그대로 복사되지 않고 이름·시점·정보 공개가 일관된다.
한 대화 줄은 무엇을 요구하고 숨기고 드러내는지 목적을 가져야 한다. 두 선택의 답이 똑같으면 문구만 다른 선택이다. 상대의 반응은 플레이어가 실제로 한 말이나 행동을 받아야 한다. 내레이션·속마음·편지·표지판은 캐릭터 대사와 구별한다. 표정·쉼·강조 효과는 감정 변화에 필요한 순간에만 쓴다. 짧은 첫 장면은 인물 소개, 작은 요구, 선택, 다른 반응, 여운 있는 종료로 구성할 수 있지만 순서와 사건은 사용자 설정으로 구체화한다. 기본 예시의 이름이나 반전을 사용자 이야기로 끌고 오지 않는다.

## C08 16비트 도트 제작과 반려 기준
입력: 사용자 미술 방향, 기존 도트 자산, 인물 외형의 확정·미정 여부.
실행: 작은 논리 해상도의 픽셀 덩어리·제한된 색 단계·일관된 시점을 명시해 소재를 선택 또는 생성하고 원본을 검수한다.
산출물: 실제 사용 자산, 출처, 원본과 게임 표시 크기에서의 검수 기록.
검증: 흐린 회화·매끈한 그라데이션·안티앨리어싱·제각각인 픽셀 크기·이미지에서 추론한 주인공 외형을 반려한다.
16비트는 파일 색 깊이나 PNG 메타데이터를 검사하라는 뜻이 아니라 16비트 시대 JRPG 도트의 조형 규칙이다. 프롬프트에는 선명한 픽셀 경계, 픽셀 덩어리로 묶은 명암, 재료당 제한된 명도 단계, 작은 크기에서도 읽히는 실루엣, 장면 전체의 같은 픽셀 밀도를 넣는다. 확대는 최근접 이웃을 기준으로 보고 피부·머리·옷·배경의 픽셀 크기가 따로 노는지 확인한다. 3D 렌더나 일러스트에 픽셀 필터만 입힌 결과는 반려한다. 실패 원인을 다음 프롬프트에 구체적으로 넣고 재생성한 원본도 다시 검수한다. 보지 않은 이미지를 통과시키지 않는다. 몬스터 종·스타터·진화 앞뒤 스프라이트를 새로 만들 때는 전용 하네스와 사람이 고르는 규칙을 따른다.

## C09 카메라·소리·조작 복귀
입력: 실제 장면, 인물 좌표, 음악·효과음 자산과 카메라 동작.
실행: 필요한 이동·시선·페이드·카메라·음향을 저작하고 장면 종료 뒤 입력과 카메라를 복구한다.
산출물: 실행 가능한 연출과 종료 처리.
검증: 연출을 건너뛰거나 선택을 취소해도 플레이어가 조작 가능한 정상 상태로 돌아온다.
기획에 적힌 연출을 단순 대사로 생략하지 않는다. 이동 완료와 대화 시작의 순서를 지킨다. 장면에 없는 인물 ID로 이동을 요청하지 않는다. 음악은 실제 로드되는 파일을 쓰고 대화 가독성을 해치는 큰 효과음을 반복하지 않는다. 오래 지속되는 안개·빛·흔들림은 톤과 게임 조작에 필요한지 판단한다. 제목과 오프닝은 첫 맵의 핵심 행동이 연결된 뒤 제작한다. 실패한 이미지 생성이나 긴 음악 탐색 때문에 첫 화면을 비워 두지 않는다. 모션 감소를 사용하는 환경에서도 필수 정보는 대사와 상태로 남긴다.

## C10 작업 기록과 팀 인계
입력: 요구사항 표, 작업 의존관계, 실제 적용 결과, 팀원 권한과 현재 진행.
실행: 각 작업에 담당·선행 조건·산출물·검증 근거를 붙이고 팀원에게 필요한 기획과 장르 원문을 함께 전달한다.
산출물: pending/running/blocked/verified를 구별하는 내부 제작 기록과 인계.
검증: 요약만 받은 팀원이 장르 핵심 규칙을 잃지 않고 검수 결과가 실제 수정으로 이어진다.
명세 작성 완료와 맵 제작 완료는 따로 기록한다. 팀장은 프로젝트 공통 변경이 끝나기 전에 같은 DB를 바꾸는 다른 팀원을 배정하지 않는다. 맵 작업은 실제 map id로 범위를 주고 다른 맵의 쓰기와 충돌하지 않는지 확인한다. 분기 대사 담당에게는 변수의 의미와 현재 조건, 미술 담당에게는 실제 주인공 설정과 도트 기준을 준다. 검수 담당은 도구 성공 로그보다 실제 산출물과 플레이 결과를 먼저 본다. 사용자는 짧은 결과와 필요한 미확인 사항만 보며 상세 TODO를 읽거나 승인해야 진행되는 구조로 만들지 않는다.

## C11 정상·대안·재진입 검증
입력: 첫 범위의 입력 경로, 분기별 기대 결과, 실제 저작된 데이터.
실행: 새 게임부터 정상 경로, 다른 선택, 취소·실패, 완료 후 재접근을 실제로 실행한다.
산출물: 경로별 입력·기대 상태·관측 상태·화면 증거와 수정 기록.
검증: 한 경로의 성공만으로 다른 선택·실패 복구·중복 방지·조작 복귀를 통과시키지 않는다.
lint의 오류 0은 구조 확인이며 장르의 재미나 분기 의미를 검증하지 않는다. 맵 캡처만으로 선택 결과나 전투·포획이 작동한다고 주장하지 않는다. 각 선택은 초기 상태에서 각각 실행하고 결과 상태와 후속 대사를 비교한다. 완료 뒤 같은 이벤트를 두 번 눌러 관계 수치·보상·동료가 반복 지급되지 않는지 확인한다. runtime 전용 검증 경로가 있으면 출하되는 플레이어 경로를 사용한다. 실행할 수 없는 환경에서는 미확인으로 남긴다. 독립 검수에서 반려되면 원인과 영향을 받은 후속 검증을 열어 수정한다.

## C12 정본 저장과 완료 판정
입력: 저장 서비스, 실제 project id, 적용된 이벤트·상태·자산·검증 결과.
실행: 기존 저장 서비스를 통해 저장하고 같은 프로젝트를 다시 열어 핵심 데이터와 플레이를 비교한다.
산출물: 저장 대상·revision·재로드 일치와 저장 후 실행 근거.
검증: 메모리 상태, JSON 내보내기, 프롬프트 전송, 제목 변경만으로 전체 게임 완료를 보고하지 않는다.
실제 저장된 맵과 이벤트가 재로드 후 존재하는지 확인한다. 자산 참조가 메모리 data URL에만 의존하는지, 다른 탭이나 새로고침 뒤 누락되는지 확인한다. 상태 초기값과 완료 조건은 새 게임과 저장 후 이어하기에서 각각 의미가 맞아야 한다. 결과 보고에는 실제로 만든 것, 실제로 실행한 것, 미확인, 임시 설정을 구분한다. 전송 검사 통과는 내용 전달의 증거이며 플레이 완료의 증거가 아니다. 제작 범위 전체가 검증되지 않았으면 완료 상태를 올리지 않는다. 저장 충돌과 권한 오류를 숨기거나 다른 원격 저장소에 사본을 만들어 정본이라고 주장하지 않는다.

# 추리·미스터리 상세 제작 프리셋 v1

플레이의 중심은 관찰한 사실과 사람의 말을 비교하고 근거를 사용해 가설을 확인하는 경험이다. 분위기만 기묘한 컷신이나 공포 추격은 추리 구현이 아니다. 사건의 정답은 제작자 내부에서 먼저 정하되 플레이어에게는 발견 가능한 근거와 순서로 제공한다. 첫 범위가 이상 현상과 단서 하나면 전체 범인 지목과 여러 엔딩을 강제하지 않는다. 실제 사건 저작 도구와 상태를 사용하고 장면·공간·증거를 분리해 검증한다.

## Y01 사건 질문과 현재 범위
입력: 사라진 사람/기록 모순/열려서는 안 되는 장소 선택, 사용자 콘셉트와 범위.
실행: 플레이어가 지금 풀 질문과 처음 발견할 이상을 실제 장면으로 정한다.
산출물: 사건 질문·첫 이상·행동 목표.
검증: 사용자가 조사할 이유를 이해하고 첫 범위 밖의 범인 정답이 도입에서 공개되지 않는다.
사라진 사람은 부재를 알아보는 근거와 남겨진 물건, 기록 모순은 기록이 말하는 내용과 실제 관찰의 차이, 금지 장소는 닫힌 이유와 들어갈 계기를 둔다. 사용자 설정 없이 살인·저택·귀신을 사건 기본값으로 추가하지 않는다. 기획에 있는 장소와 인물 이름을 보존한다. 현재 질문은 플레이어가 가능한 조사로 답할 수 있어야 한다. '무언가 이상하다'는 말만 반복하고 어느 대상에 상호작용할지 알 수 없는 장면은 반려한다.

## Y02 내부 정답과 사건의 인과관계
입력: 사건 질문, 등장인물, 현재 범위에서 밝혀야 할 사실.
실행: 실제 일어난 일·시간 순서·동기·오해·알고 있는 사람을 내부 표로 작성한다.
산출물: 일관된 사건 정답과 정보 공개 순서.
검증: 증거·증언·정답이 서로 모순되지 않고 아직 보여주지 않은 사실을 필수 추론 근거로 쓰지 않는다.
현재 범위가 단서 하나면 그 단서가 어떤 사실을 드러내며 어떤 질문을 남기는지 정한다. 첫 추론이면 두 단서가 왜 특정 가설을 지지하거나 반박하는지 명시한다. 짧은 사건이면 해결 가능한 인과관계를 만든다. 반전을 넣으려면 기존 근거를 다시 해석할 수 있어야 하며 정답을 임의로 바꾸지 않는다. 인물이 거짓말하는 이유와 틀린 기억을 구분한다. 제작자만 알고 있는 정보와 플레이어가 이미 얻은 정보는 다른 목록으로 관리한다.

## Y03 단서의 출처와 실제 발견
입력: 정답 표, 현재 장소, 조사 가능한 소품과 문서.
실행: 단서별 출처·관찰 내용·획득 조건·의미·연결 가설을 실제 조사 이벤트에 작성한다.
산출물: 실제 단서 ID와 접근 가능한 조사 대상.
검증: 단서 설명과 소품이 일치하며 조사 전후 획득 상태가 실제로 달라진다.
단서는 '중요한 편지' 같은 이름만으로 추론 근거가 되지 않는다. 어떤 문구·시간·흔적을 관찰했고 왜 관련이 있는지 구체적으로 써야 한다. 사건과 무관한 장식은 단서와 구별한다. 증거 이미지가 없더라도 관찰 내용은 원문 대사나 실제 기록으로 남겨야 한다. 조사물이 그림 없이 투명하게 빈 바닥에 있으면 실패다. 단서의 위치는 플레이어가 실제로 접근할 수 있는 칸이다. 단서를 놓고 자동으로 이미 획득한 상태로 시작하지 않는다.

## Y04 조사 중심 입력
입력: 장소·물건 자세히 조사 선택과 단서 표.
실행: 일반 관찰 → 의미 있는 세부 관찰 → 획득 정보 → 다시 조사 반응을 저작한다.
산출물: 조사 이벤트와 발견·재조사 상태.
검증: 플레이어의 조사 입력이 정보와 상태를 만들고 여러 번 조사해 보상이 반복되지 않는다.
핵심 단서는 매우 정밀한 숨은 픽셀 클릭만으로 접근하게 만들지 않는다. 눈에 보이는 소품이나 위치의 이상이 있어야 한다. 재조사는 이미 안 사실을 짧게 상기시키며 새로운 근거가 생겼을 때만 다른 반응을 준다. 관찰 내용은 정답 전체를 말하지 않아도 추론에 충분해야 한다. 필요 없는 모든 물건을 긴 독백으로 만들지 않는다. 첫 단서 범위에서는 조사 하나의 의미와 다음 질문을 분명하게 만든다. 조사 성공과 사건 해결은 서로 다른 완료 상태다.

## Y05 증언과 정보의 신뢰도
입력: 사람의 말 비교 선택, 인물별 알고 있는 사실·숨기는 이유.
실행: 인물의 주장·시각·알리바이·입장과 단서 이후 달라지는 답을 실제 대화에 작성한다.
산출물: 인물별 증언과 조건별 대화·확인 상태.
검증: 모든 인물이 같은 설명을 복사하지 않고 증언이 단서와 비교 가능한 구체적 사실을 포함한다.
거짓말하는 사람과 사실을 오해한 사람, 아직 말할 수 없는 사람의 반응을 구분한다. 증언에 시간·장소·행동 등 비교할 항목을 둔다. 플레이어가 모순을 발견하면 무엇을 물어볼 수 있는지 선택에 반영한다. 증언을 듣기 전에 그 내용을 주인공이 알고 있다고 말하지 않는다. 신뢰 선택으로 대사가 달라져도 필수 근거를 영구히 봉쇄해 진행을 막지 않는다. 사용자 인물 설정과 미정 외형을 보존하고 기본 샘플 사건의 집사·약초상을 자동 등장시키지 않는다.

## Y06 기록과 관찰의 모순
입력: 기록과 현실의 모순 선택, 실제 문서 내용과 장소.
실행: 기록 주장과 관찰 사실을 각각 획득한 뒤 비교와 후속 질문을 구현한다.
산출물: 두 사실의 상태, 비교 입력, 새 가설 또는 조사 목표.
검증: 비교할 두 사실을 실제로 얻기 전에는 모순 해결 결과를 주지 않는다.
문서가 특정 시간에 문이 열렸다고 말하면 그 시간과 실제 문 상태를 확인할 근거가 있어야 한다. 기록의 작성자·작성 시점·왜 남겼는지를 내부에서 정한다. 플레이어가 기억해야 할 핵심은 대화나 지원되는 기록 시스템으로 다시 확인 가능하게 한다. '기록이 거짓이었다'는 한 줄로 결론을 내려 버리지 않는다. 기록이 틀린 이유와 실제 사실을 바탕으로 다음 질문을 만든다. 단서 둘과 첫 추론 범위에서는 이 비교의 결과까지 구현하고 사건 전체 해결을 불필요하게 덧붙이지 않는다.

## Y07 가설·증거 제시·반박
입력: 증거를 맞춰 가설 확인 선택, 실제 획득 단서와 증언.
실행: 제시 가능한 근거와 가설의 조건, 올바른 제시·잘못된 제시·취소 반응을 저작한다.
산출물: 실제 증거 제시 입력과 결과 상태.
검증: 미획득 증거를 사용할 수 없고 잘못된 제시를 정답으로 처리하지 않으며 취소 뒤 복귀 가능하다.
author_mystery_case 등 현재 사건 도구가 제공하는 구조를 읽고 사용한다. 단서·용의자·제시·지목을 제각각 가짜 스위치와 컷신으로 흉내 내지 않는다. 가설은 근거를 통해 확인하거나 반박되어야 한다. 틀린 제시는 현재 범위에서 재시도나 설명을 제공할 수 있으며 의도되지 않은 게임오버를 강제하지 않는다. 보기 문구에 정답 증거와 범인을 노골적으로 표시하지 않는다. 실제 툴의 예시는 입력 형태이며 기본 사건의 이름과 독살 설정을 복사하는 원문이 아니다.

## Y08 공간과 사건 저작 순서
입력: 사건 장소, 각 조사·인물 좌표, 현재 타일 참고문서.
실행: 실제 장소와 통행 공간을 먼저 만든 뒤 그 안에 사건 단서와 인물을 저작한다.
산출물: 벽·가구·출입이 있는 장소와 도구로 저작한 사건.
검증: 맨바닥 위에 사건만 올려 만든 방이라고 보고하지 않고 모든 필수 대상에 접근한다.
실내 사건이면 손 도트 실내 참고문서와 parts를 읽고 build_hand_interior_room로 실제 방을 만든다. 야외 사건이면 해당 장소의 구조와 통행을 먼저 갖춘다. check_mystery_case로 저작 입력을 확인하고 author_mystery_case의 오류·검증 안내를 따른다. 맨땅 경고가 있으면 장면 테스트부터 돌리지 않는다. 사건을 다시 저작할 때 같은 실제 case id를 사용해 중복 단서와 용의자가 생기지 않게 한다. 특정 방·문·서랍의 위치는 사건 사실과 일치해야 한다.

## Y09 사건 진행 상태와 정보 차단
입력: 단서·증언·가설의 의존관계와 현재 도구 데이터.
실행: 획득·확인·제시·해결 단계와 그 단계에서 허용되는 행동을 실제 조건으로 연결한다.
산출물: 정보와 진행의 상태 전이, 재접근 조건.
검증: 선행 정보 없이 해결되거나 필수 단서를 영구히 놓쳐 진행이 막히지 않는다.
각 단계는 플레이어가 실제로 얻은 근거를 읽는다. 새 맵 진입 때 전체 사건 상태를 다시 초기화하지 않는다. 단서를 먼저 보거나 증언을 먼저 들어도 사건의 인과관계가 성립하도록 지원하는 순서를 정의한다. 허용하지 않는 순서라면 필요한 정보를 알아볼 안내를 제공한다. 단서 회수와 증언 확인을 같은 플래그로 뭉개면 비교 조건을 검증할 수 없다. 새 사건을 시작할 때 기존 사건의 완료 상태와 ID를 덮어쓰지 않는다. 첫 범위가 작으면 현재 범위의 질문에 필요한 상태만 만든다.

## Y10 사건·장소·신뢰 진행
입력: progression의 한 사건/여러 장소/누구를 믿을지 선택.
실행: 선택한 진행에 맞게 조사 순서·공간 연결·정보 접근과 결과를 저작한다.
산출물: 실제 조사 경로와 진행 조건.
검증: 선택한 진행 방식이 UI 문구에만 있고 실제 플레이는 동일한 선형 컷신이 되지 않는다.
한 사건이면 현재 질문에 도달할 단서와 결론을 집중해서 연결한다. 여러 장소면 출입과 돌아오기, 각 장소의 다른 정보가 비교에 쓰여야 한다. 신뢰 선택이면 증언 방식과 관계 반응이 달라져도 풀 수 있는 근거 경로를 유지한다. 첫 범위에서 장소 하나를 요구하면 여러 조사 맵을 강제하지 않는다. 아직 만들지 않은 장소를 필수 전이 대상으로 쓰지 않는다. 단서가 많다는 이유만으로 사건이 정교해지는 것은 아니며 각 근거가 어떤 판단에 쓰이는지 기록한다.

## Y11 기묘함·긴장·위협의 톤
입력: wonder/tension/danger 선택, 사용자 사건과 첫 범위.
실행: 장소·소리·문체·정보 공개 간격으로 확정 톤을 실제 장면에 표현한다.
산출물: 단서를 읽을 수 있는 분위기와 필요한 연출.
검증: 추리 핵심 입력을 공포 추격·즉사·점프스케어로 대체하지 않는다.
기묘하지만 아름다운 톤은 정상과 어긋난 작은 관찰로 만들 수 있다. 팽팽한 톤은 대답의 망설임이나 두 주장 사이의 틈을 보여준다. 위협이 있으면 조사할 수 있는 시간과 복귀를 실제 지원되는 사건 구조에 맞춰 정한다. 사용자가 요구하지 않은 추격자를 기본 삽입하지 않는다. 긴 안개와 어두운 효과로 단서와 통행을 숨기지 않는다. 정답을 도입 내레이션이나 타이틀에 공개하지 않는다. 중요한 근거는 연출을 건너뛰어도 다시 확인할 수 있어야 한다.

## Y12 단서가 읽히는 도트 미술
입력: 실제 장소·조사물·16비트 도트 방향·참고문서.
실행: 중요한 물건의 실루엣·배치·대비를 확보하고 장식과 조사 지점을 연결한다.
산출물: 실제 소품·인물·환경과 접근 가능한 이벤트.
검증: 투명한 증거와 빈 방, 회화풍 배경을 도트 사건 장소라고 통과시키지 않는다.
편지·시계·문·발자국은 명확한 픽셀 덩어리와 실제 위치로 읽혀야 한다. 그려진 물건과 이벤트 좌표가 다르면 사용자에게 존재하지 않는 것을 조사하게 된다. 단서마다 과도한 빛을 붙여 정답을 표시하지 않고 장소의 맥락과 작은 대비로 주의를 준다. 새 자산의 원본과 게임 표시 크기를 검수한다. 작은 픽셀 경계, 제한된 명암, 같은 시점과 밀도를 유지한다. 생성 실패 자산은 원인을 기록해 재제작하며 본 적 없는 이미지를 통과시키지 않는다.

## Y13 첫 추론과 현재 결말
입력: scene/episode/short 범위와 현재 질문에 필요한 근거.
실행: 첫 이상과 단서, 단서 둘의 추론, 짧은 사건 해결 중 해당 결과를 구현한다.
산출물: 현재 범위의 결론·다음 질문 또는 실제 사건 종료.
검증: 전체 범인 지목을 첫 단서 한 장면에 강제하지 않고 현재 범위의 결과가 실제로 작동한다.
첫 단서면 작은 사실을 알게 되고 더 조사할 이유가 남는 결과가 될 수 있다. 첫 추론이면 어떤 가설이 틀리거나 새 질문이 생기는지 보여준다. 짧은 사건이면 충분한 근거로 해결하고 인물과 장소의 후속 반응을 둔다. 사건 도구의 검증·엔딩 기능이 범위에 맞는지 확인한다. 해결 메시지 뒤 상태가 미해결로 남거나 재대화에서 범인이 다시 처음 증언을 하는지 검사한다. 공용 엔딩으로 이동한 것만으로 사건 논리가 검증되었다고 보고하지 않는다.

## Y14 오답·취소·재조사 복구
입력: 가설·증거 제시·신뢰 선택의 실패 경로.
실행: 잘못된 제시와 취소의 반응, 다시 조사·증언·추론할 수 있는 복귀를 저작한다.
산출물: 정상 조작 복귀와 미해결 상태의 재시도 경로.
검증: 잘못된 근거를 낸 뒤 필수 단서를 잃거나 입력이 잠겨 사건을 계속할 수 없게 되지 않는다.
오답은 왜 그 근거가 부족한지 현재 정보 범위에서 이해할 수 있는 반응을 줄 수 있다. 정답을 직접 알려주는 설명을 모든 오답에 붙이지 않는다. 단서가 소비되는 기능이면 재획득이나 확인 경로를 실제로 마련한다. 취소는 사건 진행과 보상을 바꾸지 않는다. 조사 완료 뒤 재조사하면 이미 얻은 정보를 상기시키고 같은 지급을 반복하지 않는다. 완료한 사건은 별도 반응과 상태를 유지하며 저장 후 재개에서도 정답과 획득 기록이 남는다.

## Y15 독립적인 사건 플레이 검수
입력: 내부 정답, 플레이어가 얻을 수 있는 근거, 정상·오답·재접근 경로.
실행: 실제 조사·증언·제시·추론·종료를 실행하고 선행 정보 없이 해결되는 경로도 확인한다.
산출물: 단서 전후 상태·증언·추론 결과·오답 복귀·재로드 증거.
검증: 구조 lint나 사건 도구 성공만으로 논리와 플레이를 합격 처리하지 않는다.
검수자는 내부 정답과 플레이어 정보의 차이를 읽고 모든 필수 근거가 실제로 접근 가능한지 본다. 단서 하나를 아직 얻지 않은 상태에서 정답 제시가 가능한지 확인한다. 증언의 모순은 실제 기록과 대사에서 비교해야 한다. 공간·시각 검수는 조사의 접근성과 함께 수행한다. 오류를 발견하면 사건 데이터인지 이벤트 조건인지 통행인지 구분해 반려한다. 지원 도구가 제공한 verificationScene은 그 안내에 따라 실행하며 별도 runtime 경로의 실제 조작과 저장 재확인도 구분한다.

## Y16 다른 장르와 추론의 연결
입력: secondary와 blend 원문, 다른 장르의 행동 결과.
실행: 관계·수집·탐험의 결과를 실제 사건의 근거·정보 접근·후속 반응으로 연결한다.
산출물: 두 장르의 상태와 증거를 연결하는 이벤트.
검증: 다른 장르의 이름만 붙거나 신뢰·포획·전투만 성공하면 근거 없이 사건이 해결되지 않는다.
관계와 결합하면 신뢰에 따라 증언 태도가 달라져도 증거로 비교할 경로가 있어야 한다. 몬스터와 결합하면 관찰한 생태·동료 행동이 구체적인 사건 사실에 쓰일 수 있다. 탐험과 결합하면 새로운 장소에서 발견한 기록이 기존 가설과 연결된다. 사용자가 같은 선택이 두 장르에 영향을 주게 했다면 각각의 상태와 반응을 구현한다. 별도 에피소드면 현재 사건의 끝과 다음 장르 사건의 시작을 명시하되 첫 범위에 모든 시스템을 강제하지 않는다.

## 조수 내부 제작 계약 — 사용자 확인 화면에 작업 목록을 출력하지 않는다
이번 요청이 이 기획의 최초 제작·계속 제작·수정일 때 해당 작업만 실행한다. 읽기 전용·기획 상담·무관한 요청에서는 제작을 시작하지 않는다. 팀원·Writer·검수는 배정된 역할과 권한 범위만 수행한다.
사용자는 게임의 방향을 확정하면 된다. 상세 TODO·도구명·검증 규칙을 다시 사용자에게 승인받거나 복사/가져오기를 요구하지 않는다. 필요한 미정 사항은 합리적인 가역적 기본값으로 보완하고 출처를 남긴다. 핵심 요구 충돌이나 실제 접근 부재만 필요한 질문으로 남긴다.
아래는 최신 기획에서 매번 파생한 내부 작업 골격이며 진행 기록이 아니다. 최신 사용자 수정 > 확정 요약 > 원문 답변 > 추천/임시 설정 순서를 따른다. 최초 계획에서 실제 맵·이벤트·분기·자산·검증 경로별로 하위 TODO를 충분히 확장하고 의존관계를 검사한다. 개수를 채우려고 범위를 늘리지 않는다.
실행 순서: 대상 읽기 → 선행 작업과 실제 ID 확인 → 제작 → 결과 재조회 → 완료 조건 검증 → 작업 상태·산출물·증거 기록. 계획만 반환하고 끝내지 않는다. 이미 완료된 작업은 실제 결과를 확인하고 재사용한다.

interview.genre/secondary는 사용자가 고른 장르이고 preset은 이를 실행하는 엔진이다. 관계·연애를 회상 수집물로, 추리를 공포 추격으로 임의 변환하지 않는다. 두 장르를 고른 경우 blend에 적은 연결 방식과 각각의 핵심 행동을 실제 이벤트·상태·결과로 연결한다.

아래 장르 저작 요령은 도구 사용 참고다. 선택한 조우가 교감·부화라면 3종 스타터 선택이나 포획을 강제하지 말고, 선택한 방식으로 동료 획득과 중복 방지를 구현한다. 미술은 16비트 JRPG풍의 선명한 도트와 제한된 색 단계로 통일한다. 회화·매끈한 그라데이션·안티앨리어싱으로 도트를 흉내 낸 자산은 반려하고 다시 제작·검수한다.

기존 첫 구간 뼈대의 인물·대사·기억 조사·스타터는 사용자 설정이 아니라 임시 시드다. 확정 기획의 핵심 행동으로 고치되 시작부터 구간 끝까지의 연결과 검증 계약을 보존한다.
