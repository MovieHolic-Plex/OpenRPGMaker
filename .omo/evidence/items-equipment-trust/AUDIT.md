# 아이템·장비 적대적 평가 — 2026-09-05

판정: 화면의 설정값·설명·효과 요약과 실제 동작의 일치성이 부족하다. 외관 정리보다 저작 결과의 신뢰성을 먼저 고쳐야 한다.

## 조사 범위와 증거

- 현재 워크트리의 구현을 기준으로 평가했다. Firefox에서 실제 데이터베이스 화면을 1280×800, 1024×768로 열고 스크린샷과 DOM 치수를 확보했다.
- 재현용 임시 fixture로 UI 이벤트, 실제 아이템 사용 함수, 전투 파생값, 로드 정규화 함수를 호출했다. 9개 특성 확인 실험이 모두 통과했다. 이 통과는 **결함이 재현되었다는 뜻**이다.
- 실험 원본: `audit-characterization.test.ts`, 결과: `experiments.log`. 원본은 실행 당시 `test/itemsEquipmentAdversarialAudit.test.ts` 위치였으며 `./fakeDom`을 사용한다. 재실행하려면 그 위치로 복사하고 `npm test -- test/itemsEquipmentAdversarialAudit.test.ts --maxWorkers=1 --reporter=verbose`를 실행한다. 정상 동작을 요구하는 회귀 테스트로 등록한 것이 아니다.
- 실제 브라우저 조작에서도 메뉴 전용 ON→OFF 후 필드 제한 잔류, 발동/연결 스킬 불일치, 범위 변경 후 요약 미갱신, 장비 탭 이동 시 기존 청동 검 선택, MP 소모 절반 체크 후 효과 요약 표시를 확인했다. 증거: `interactions.json`.
- 게임 화면 QA, 실제 원격 저장·재로드, 사용자 특정 Supabase 프로젝트 데이터, 모든 전투 모드의 실행까지 검증한 것은 아니다. 원격 콘텐츠를 수정하지 않았다. 코드 수정도 하지 않았다.
- 심각도: P1은 저작 결과를 잘못 만들거나 사용자 의도를 무력화하는 기능 문제, P2는 오해·탐색 비용·가시성 문제다.

## P1 — 먼저 고칠 기능 문제

### 1. 종류를 바꿔도 이전 종류의 숨은 효과가 실행된다

재현: 책에 습득 스킬 지정 → 종류를 약으로 변경 → 게임 메뉴 사용. 화면에서는 습득 스킬 편집기가 사라지고 효과 요약에도 스킬 습득이 없지만, 실제로 그 스킬을 배운다. UI의 종류 변경과 `useItemFromMenu`를 연결한 실험으로 확인했다.

원인: `src/editor/panels/databaseItemRecordView.ts:780`은 종류·일부 대상·소모 여부만 변경한다. `learnedSkillId` 등은 남는다. `src/player/playerItemUse.ts:27`은 `learnedSkillId`가 있으면 종류와 무관하게 책 사용을 먼저 실행한다.

개선: 종류별로 활성 효과를 정의하고 런타임도 그 계약을 따르게 한다. 종류 전환 시 영향받는 효과를 미리 보여주고, 이전 설정을 보관하더라도 비활성 효과가 실행되지 않게 해야 한다.

### 2. 장비의 작동하지 않는 효과 6개가 정상 기능처럼 제공된다

선제 공격 / 회피 무시 / 치명타 방지 / 물리 회피율 증가 / MP 소모 절반 / 지형 피해 무효. 체크하면 ‘이 장비를 착용하면’ 요약에도 효과가 표시된다. 하지만 턴제 전투의 장비 효과 집계에는 이 6개가 들어가지 않는다. 6개 모두를 켜도 실제 전투 장비 파생값이 동일한 실험과 소비자 코드 검색으로 확인했다.

근거: `src/editor/panels/databaseEquipmentRecordView.ts:71`, `:110`, `src/battle/battleBattlers.ts:280`. 화면 마지막의 지원 안내(`databaseEquipmentRecordView.ts:366`)에도 이 플래그들의 미지원 설명이 없다.

개선: 구현 전까지 해당 옵션을 숨기거나 해당 컨트롤에 지원 범위를 명시한다. 효과 요약은 실제 실행 가능한 효과만 표시한다. ‘저장된다’와 ‘게임에서 적용된다’를 구분해야 한다.

### 3. ‘메뉴에서만 사용’을 해제해도 전투 사용이 복원되지 않는다

재현: 필드·전투에서 사용 가능한 약 → 메뉴에서만 사용 ON → OFF. 체크는 해제되지만 `occasion`은 `field`로 남는다. UI 이벤트 실험으로 확인했다. 약 폼에는 이 값을 직접 복구할 일반 사용 시점 선택기도 없다.

근거: `src/editor/panels/databaseItemRecordView.ts:269`. ON일 때만 `occasion`을 변경하며 OFF는 현 값을 그대로 쓴다.

개선: 사용 시점은 ‘필드 / 전투 / 둘 다 / 직접 사용 불가’ 한 컨트롤을 정본으로 삼는다. 상호 중복되는 플래그를 사용자가 조합하게 하지 않는다.

### 4. 삭제한 기본 아이템·장비가 다시 나타난다

기본 레코드를 제거한 프로젝트에 실제 로드 정규화 함수를 적용하면 해당 레코드가 다시 추가되는 것을 실험으로 확인했다. 실제 Supabase 저장 후 재로드는 수행하지 않았으므로 그 부분은 코드 경로 분석 근거다.

근거: `src/editor/databaseActions.ts:381`은 삭제를 허용하지만, `src/project/defaults/defaultDatabaseIconResources.ts:95`, `:116`은 빠진 기본 아이템·장비를 재주입한다. `src/project/store.ts:1178`이 로드 정규화에서 이를 호출한다.

개선: 새 프로젝트 초기화와 기존 프로젝트의 로드 보정을 분리한다. 기본 자료 복구는 사용자가 실행하는 작업으로 만들거나, 의도적 삭제를 기록하고 존중해야 한다.

### 5. 스킬 선택기가 서로 다른 진실을 보여준다

특수 아이템에는 ‘발동 스킬’과 ‘연결 스킬 → 스킬’이 동시에 있다. 전자는 `activateSkillId`와 `skillId`를 같이 쓰고 후자는 `skillId`만 쓴다. 따라서 A와 B를 각각 표시하는 상태를 만들 수 있으며, 전투는 `activateSkillId`를 우선한다. 두 입력이 갈라지는 UI 이벤트 실험을 통과했다. 책에도 유사한 중복 구조가 있다.

근거: `src/editor/panels/databaseItemRecordView.ts:300`, `:499`, `src/editor/panels/databaseBasicRecordFields.ts:148`, `src/battle/runtime.ts:1565`.

장비도 기본 카드의 ‘스킬’(`skillId`)과 장착 규칙의 ‘사용 시 발동 스킬’(`usableAsItemSkillId`)이 구분 설명 없이 공존한다.

개선: 사용자 목적에 해당하는 스킬 입력은 하나만 둔다. 레거시 필드는 내부 마이그레이션으로 처리하고, 실제 다른 기능이라면 발동 조건과 차이를 필드 바로 옆에 설명한다.

### 6. ‘사용 가능’ 제한이 특수 아이템에서는 적용되지 않는다

특수 아이템에도 배우·직업 제한을 편집할 수 있지만 `isItemActorEligible`은 약·책·씨앗 이외를 즉시 허용한다. 특정 배우만 허용한 특수 아이템으로 다른 배우를 검사해도 허용되는 실험으로 확인했다.

근거: `src/editor/panels/databaseItemRecordView.ts:329`, `src/project/itemEligibility.ts:16`.

개선: 특수 아이템의 제한을 실행 경로에서 지원하거나, 이 종류에서는 해당 편집기를 제공하지 않는다.

### 7. 공격 속성 다중 선택과 상태 방어 모드가 런타임 계약과 어긋난다

공격 속성을 여러 개 체크하고 요약에도 전부 표시할 수 있지만, 일반 공격은 첫 속성 하나만 쓴다. 선택 순서가 전투 결과를 좌우할 수 있는데 UI는 복수 속성 효과처럼 보인다.

또한 상태 방어의 ‘공격 시 부여’는 공격 상태 부여 경로에 연결되지 않는다. `inflict` 장비 하나라도 있으면 전체 장비의 집계 방어 모드가 `inflict`가 되고, 상태 저항 판정이 빠져나가는 구조다. 이 항목은 소스 추적 근거이며 별도 전투 실험은 하지 않았다.

근거: `src/editor/panels/databaseEquipmentRecordView.ts:94`, `:683`, `src/battle/runtime.ts:2149`, `src/battle/battleBattlers.ts:298`, `src/battle/battleStates.ts:172`.

개선: 현재 계약이면 공격 속성은 단일 선택이어야 한다. 상태 부여와 상태 저항은 별도 효과로 저작·집계한다.

## P2 — 화면과 사용 흐름 문제

### 8. ‘사용 횟수: 제한 없음’이 무한 사용이라는 뜻이 아니다

기본 회복약은 ‘제한 없음’이 선택되어 있지만, 상단은 ‘사용할 때 1개 소비’라고 표시한다. 실제 성공 사용마다 1개가 줄어드는 실험을 확인했다. UI에서 비소모 아이템으로 바꾸는 명시적 컨트롤도 없다.

근거: `src/editor/panels/databaseItemRecordView.ts:642`, `src/project/itemTransitions.ts:88`. 스크린샷 `items-1280.png`에 상충하는 문구가 함께 나온다.

개선: ‘매회 1개 소모 / 한 개를 N회 사용 / 소모하지 않음’처럼 사용자가 이해할 수 있는 수명 규칙으로 제공한다.

### 9. 아이템에서 장비를 만들려는 흐름이 막다른 길이다

종류에 무기·방패·갑옷 등이 있지만 실제 착용 장비 레코드로 전환되지 않는다. ‘장비 탭 열기’는 탭만 이동하며 이름·아이콘·설정을 가져가거나 대응 장비를 찾아주지 않는다. 장비형 아이템 안내에는 ‘이름·가격·아이콘만 관리’라고 적지만 그 화면에는 가격 입력도 없다.

근거: `src/editor/panels/databaseItemRecordView.ts:44`, `:230`, `:357`. 브라우저에서 ‘감사 테스트’ 아이템을 무기로 바꾸고 이동했지만 장비 이름은 기존 ‘청동 검’이었다 (`interactions.json`의 `redirectEquipmentName`).

개선: 신규 아이템 종류에서 장비형을 제거하고 레거시만 안내하거나, 실제 장비로 변환하는 명시적 동작을 제공한다.

### 10. 효과 요약이 항상 최신 상태를 반영하지 않는다

특수 아이템의 범위를 아군에서 적으로 바꿔도 상단 대상 요약은 이전 값으로 남는 UI 이벤트 실험과 실제 브라우저 조작을 확인했다. 포획 설정과 공용 스킬 선택기도 상단 요약 갱신 콜백을 호출하지 않는다. 후자의 재현은 코드 추적 근거다.

근거: `src/editor/panels/databaseItemRecordView.ts:262`, `src/editor/panels/databaseBasicRecordFields.ts:35`, `:42`, `:148`.

개선: 모든 입력 후 하나의 실제 효과 모델로 요약을 다시 계산한다. 탭을 나갔다 돌아와야 맞는 요약은 미리보기로 신뢰할 수 없다.

### 11. 아이템·장비의 허용 목록은 뜻이 다른데 설명이 부족하다

아이템의 배우·직업 목록은 각각 비어 있으면 제한 없음이며, 둘 다 설정하면 AND 조건이다. 장비는 배우 또는 직업 허용의 OR 조건이고 직업 탭의 권한으로도 허용된다.

장비 폼은 ‘아무것도 체크하지 않으면 누구도 장착할 수 없습니다’라고 단정하지만 직업 탭에서 허용하면 두 목록이 비어 있어도 장착된다. 실제 `canEquip` 실험으로 확인했다.

근거: `src/project/itemEligibility.ts:18`, `src/project/equipmentRules.ts:37`, `src/editor/panels/databaseEquipmentRecordView.ts:324`.

개선: ‘모두 허용 / 선택한 대상만’ 모드를 명시하고 실제 최종 허용 결과와 그 이유를 보여준다. 아이템에서는 사용 주체와 사용 대상도 구분해야 한다.

### 12. 요약·비교·보조 설정이 실제 편집 공간을 과도하게 차지한다

Firefox 실측:

| 화면 | 아이템: 가시 본문 / 전체 본문 | 장비: 가시 본문 / 전체 본문 |
|---|---:|---:|
| 1280×800 | 577 / 1,504px | 533 / 2,308px |
| 1024×768 | 545 / 2,045px | 459 / 3,254px |

1024px 장비 화면에서 본문은 약 7.1화면 분량이다. 고정 헤더가 174px이고 그 아래 큰 초기 빌드 비교가 펼쳐져 있다. 첫 화면에 능력치 보정 입력이 보이지 않는다. 명중률·치명타는 헤더와 요약에서 중복되며, 아이템 기본 카드에는 모든 종류에 농사 도구가 나온다. 아이템에는 포획 카드가 공통으로, 장비에는 액션 전투 스윙 카드가 전투 방식·부위와 무관하게 포함된다.

근거: `audit.json`, `equipment-1024.png`, `items-1280.png`, `src/editor/panels/databaseEquipmentRecordView.ts:253`, `:347`.

개선: 기본·효과·사용/장착 조건·외형으로 탐색을 나누고 요약과 비교는 접거나 요청 시 펼친다. 농사·포획·액션 설정은 해당 기능을 켰을 때 노출한다. 목록과 상세 사이 너비 조정도 필요하다.

### 13. 용어와 미지원 안내가 사용자 판단을 돕지 못한다

- ‘씨앗’은 영구 능력치 보정인데 실제 작물 씨앗과 쉽게 혼동된다. ‘능력치 성장 아이템’처럼 목적을 먼저 밝혀야 한다.
- ‘스위치 토글 ON/OFF’라고 하지만 실제 사용은 ON만 수행하고 이미 ON이면 사용할 수 없다 (`databaseItemRecordView.ts:528`, `playerItemUse.ts:32`).
- ‘사용 메시지’는 편집 가능하지만 저장 전용이다. 안내는 본문 맨 끝의 접힌 영역에 있다 (`databaseFieldSupport.ts:65`).
- 이미지와 아이콘을 같은 모습으로 두 번 설정하게 하면서 실제 어디에 쓰이는지는 멀리 떨어진 지원 안내에 있다. 런타임 소비 현황은 별도 전수 검사하지 않았으나 편집기의 자체 안내도 저작 화면용이라고 설명한다.

개선: 기능 이름을 결과와 일치시키고, 적용되지 않는 설정은 해당 입력 바로 옆에서 판단할 수 있게 한다.

## 권장 수정 순서

1. 종류 전환의 숨은 효과, 미작동 장비 옵션, 사용 시점 토글, 삭제 후 복구부터 수정한다.
2. 스킬 입력·권한 규칙·속성 선택·효과 요약을 실제 런타임 계약 하나에 맞춘다.
3. 그 뒤에 카드 분할, 비교 접기, 조건부 노출, 용어를 정리한다.

이미 있는 아이콘·필터·장비 비교는 개선의 재료로 쓸 수 있다. 현재 가장 큰 문제는 기능 수가 아니라, 사용자가 화면을 보고 예측한 결과가 실행·재로드와 어긋난다는 점이다.
