# Battle flash / map visibility TypeScript audit

## WHAT IS BEHIND THE BATTLE SCENE

### Shipped-player DOM stack

From back to front, the relevant shipped-player stack is:

```text
.play-viewport                                  (src/player/playSurface.ts:22-26)
└─ .play-stage                                 (src/player/playSurface.ts:27-30)
   ├─ .phaser-container                        (src/player/playSurface.ts:31-36)
   │  └─ canvas (created by Phaser.Game in that parent)
   │     └─ live PlayScene map render
   ├─ .dialogue-overlay                        (src/player/dialogue.ts:95-98)
   ├─ [transient .battle-transition-overlay]   (src/player/battleTransition.ts:23-39,54-54)
   └─ section.battle-scene                     (src/player/battleDom.ts:82-99)
      ├─ .battle-field                         (src/player/battleDom.ts:122-123)
      │  └─ .battle-backdrop                   (src/player/battleFieldDom.ts:84-94,381-398)
      ├─ .battle-animation-layer               (src/player/battleDom.ts:124-126)
      ├─ .battle-message-window
      ├─ .battle-enemy-list-panel
      ├─ .battle-command-host
      ├─ party status
      └─ .battle-result-host                   (src/player/battleDom.ts:127-138)
```

`createPlaySurface` creates `.play-stage`, creates `.phaser-container`, and appends the latter as the stage's first child (`src/player/playSurface.ts:22-36`). The shipped player passes that container to `startPlayGame` (`src/player/player.ts:252-253`); `createPlayGame` supplies it as the Phaser game's `parent`, with a black renderer background (`src/player/createPlayGame.ts:25-29`). Phaser therefore owns the canvas inside `.phaser-container`; `PlayScene.create` puts the lower and upper map tile containers into that renderer and loads the current map (`src/player/PlayScene.ts:183-199`).

The host above that canvas is the same `.play-stage`: after game creation, the player creates the dialogue UI on `playStage` and registers `playStage` under `dialogueHost` (`src/player/player.ts:288-290`). `dialogueHost(scene)` returns exactly that registry element (`src/player/playSceneDom.ts:4-6`). The real battle path resolves this host (`src/player/playSceneBattle.ts:42-48`), covers it with an entry transition, and mounts the battle only after the cover finishes (`src/player/playSceneBattle.ts:128-134`). `mountBattleScene` creates `section.battle-scene` and appends it directly to the host (`src/player/battleDom.ts:81-99`). Thus `.battle-scene` is a later sibling painted over the still-present Phaser container/canvas, not a replacement for it (`src/player/playSurface.ts:31-37`, `src/player/battleDom.ts:99-99`).

The map scene is **merely covered; it is not hidden, stopped, or torn down for battle**. The battle entry path appends the DOM root (`src/player/battleDom.ts:82-99`), while battle teardown removes only that root (`src/player/battleDom.ts:900-912`). On normal exit, the code destroys the battle root and then reveals the exit overlay back to the already-existing player surface (`src/player/playSceneBattle.ts:140-152`). The map's lower/upper Phaser containers were created once in `PlayScene.create` (`src/player/PlayScene.ts:183-199`), and no battle lifecycle call in `playBattle` replaces or destroys them (`src/player/playSceneBattle.ts:128-154`).

The sole opaque battle-owned backing is the root's `background: #000` (`src/styles/runtime/battle/01-scene-base.css:32-84`). The `.battle-field` itself has no opaque base declaration (`src/styles/runtime/battle/01-scene-base.css:87-94`), and its `::after` is a translucent radial gradient (`src/styles/runtime/battle/01-scene-base.css:96-103`). Consequently, making the root background translucent or moving the exact-size root exposes the live Phaser map canvas beneath it (`src/styles/runtime/battle/01-scene-base.css:69-84`, `src/player/createPlayGame.ts:25-29`). The `.play-stage` also has a black background, but the live Phaser container/canvas is its earlier child, above that background and below the later battle root (`src/styles/runtime/playSurface.css:53-63`, `src/player/playSurface.ts:31-37`, `src/player/battleDom.ts:99-99`).

### The other shipped `battle-scene` path is only a placeholder

There is a second, similarly named path that must not be confused with the live battle DOM. `PlayScene.showBattleScene` calls generic `showRuntimeOverlay("battle-scene", ...)` (`src/player/PlayScene.ts:378-380`), and the exported helper in `playSceneBattle.ts` does the same (`src/player/playSceneBattle.ts:38-40`). Generic `showRuntimeOverlay` creates `div.runtime-overlay[data-testid="battle-scene"]` and appends it to `dialogueHost` (`src/player/playSceneOverlays.ts:13-25`); it does **not** create `.battle-scene` or a `BattleRuntime`. The nonblocking scheduler invokes this placeholder path for `battleProcessing` (`src/player/playSceneSchedulers.ts:207-229`). Its generic runtime-overlay styling is inset and glass-backed (`src/styles/editor/core.part-1.css:370-385`), so the map remains visible around/through it, but this is not the mounted battle implementation investigated by the report (`src/player/battleDom.ts:82-99`). The normal blocking interpreter instead awaits `scene.playBattle` (`src/player/playSceneInterpreter.ts:388-391`), which reaches the real mount path above (`src/player/PlayScene.ts:382-387`, `src/player/playSceneBattle.ts:128-134`).

### Exhaustive exposure verdict

The shipped TypeScript routes that can expose the map during the battle lifecycle are: (1) non-healing damage calling `flashBattleField` with `hit` or `critical`, which installs a class whose CSS animates the root's own backing (`src/player/battleDom.ts:221-226`, `src/player/battleJuice.ts:81-98`, `src/styles/runtime/battle/06-damage-flash-targeting.css:98-125`); (2) critical juice or authored animation timing applying `battle-screen-shake` to the root, whose translation can uncover edge strips (`src/player/battleJuice.ts:92-97`, `src/player/battleAnimationDom.ts:287-300`, `src/styles/runtime/battle/06-damage-flash-targeting.css:133-148`); and (3) deliberate entry/exit transition reveal while the battle root is absent (`src/player/playSceneBattle.ts:128-152`, `src/styles/runtime/transitions.css:54-89`). The generic nonblocking `runtime-overlay[data-testid="battle-scene"]` is also map-translucent but is a placeholder, not a live mounted battle (`src/player/playSceneSchedulers.ts:207-229`, `src/player/playSceneOverlays.ts:13-25`). No other class/style mutation in the requested modules changes the root backing, stage backing, map-container visibility, or map-canvas visibility (`src/player/battlePresentation.ts:17-46`, `src/battle/battleBackdrop.ts:19-58`).
