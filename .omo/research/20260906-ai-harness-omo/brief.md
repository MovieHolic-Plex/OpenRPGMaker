# Research brief: omo-inspired RPG ZZU AI harness

## Question and ideal outcome

Which principles of the installed omo-ai native/Senpi harness should RPG ZZU
adopt, adapt or reject, and how should its implementation plan change?
Deliver a sourced Korean synthesis and one executable revised plan. No engine,
editor, database, game content or deployed service changes in this run.

## Scope and source baseline

Installed omo-ai 5.0.0-0.beta.43 / Senpi 2026.9.5 is the primary baseline.
Historical upstream OpenCode OMO sources are context only, not evidence of the
installed runtime. RPG current source outranks dated wiki prose.
The prior report is reports/ai-assistant-guide-2026-09-06/index.html.
No AI harness implementation plan is present in .omo/plans at initial discovery;
check other plan/session locations before claiming a specific predecessor.

## Research axes and owners

1. prior-plans: preceding plan and user decisions; scope continuity.
2. goal-evidence: goals, tasks, proof and stop conditions; prompt vs enforcement.
3. execution-async: tools, eval, delegation, monitor, cancellation lifecycle.
4. memory-recovery: compaction, journal, restart and durable state.
5. rpg-gaps: current RPG contracts and failure seams; what already exists.
6. architecture: adopt/adapt/reject boundaries and options.
7. migration: implementable dependency order and regression/live-surface scenarios.
8. skeptic: disprove superficial copying and unsupported completion guarantees.

All axes are read-only. Members return evidence and bounded findings; the lead
owns all journal/claim/plan writes. No nested swarms or runtime changes.

## Expected truths to challenge

- A stronger harness is not achieved by copying a long system prompt.
- Durable goals, outcome evidence and explicit terminal reasons improve
  observability only if their state contracts are machine-enforced.
- RPG already has planning, loop continuation, compaction and tool validation;
  adoption must not duplicate them or restore removed approval friction.
- Browser game-authoring transactions and Supabase persistence differ from
  filesystem coding-agent edits; generic parallel execution cannot be copied.
- UI success must reflect actual applied/persisted/verified state, not model prose.
