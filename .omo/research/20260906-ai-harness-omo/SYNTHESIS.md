# RPG ZZU AI 하네스에 omo 철학을 어떻게 가져올 것인가

작성: 2026-09-06. RPG 기준 HEAD:
`49067218aebf889d98c2dc05be08231787483427`.
비교 대상: 설치된 **omo-ai 5.0.0-0.beta.43 / Senpi 2026.9.5**.

## 결론

**가져올 것은 “AI가 끝났다고 말할 때까지 계속 시키는 방식”이 아니라,
“사용자의 목표를 유지하고, 실제 결과를 확인하며, 중단과 재개를 관리하는 방식”이다.**

다만 omo 자체를 RPG에 넣거나 새 범용 하네스를 만들 필요는 없다. RPG는 이미
계획, 도구 실행, 결과 검증, 자동 적용, 대화 압축을 갖췄다. 지금 필요한 것은
이 장치들을 **하나의 믿을 수 있는 완료·복구 계약으로 연결하는 것**이다.
[C01,C05,C09-C11]

권고 순서는 다음과 같다.

1. **거짓 완료부터 없앤다.** 실행 종료와 목표 달성을 구별하고 저장 증명을 바로잡는다.
2. **중단된 작업을 안전하게 이어 간다.** 대화 기억과 실행 체크포인트를 구별한다.
3. **늦은 결과와 오래된 초안이 현재 작업을 덮지 못하게 한다.**
4. **실제 프로젝트와 플레이 결과로 평가한다.** 에이전트 수나 재시도 횟수를 품질 지표로 삼지 않는다.

이것은 구현 완료 보고가 아니라 **수정 개발 계획의 근거**다. 이번 작업에서
제품 코드·게임 데이터·DB는 변경하지 않았다.

## 1. 먼저 정리한 전제

직전 산출물은 AI 조수의 현재 동작을 설명한 HTML이었다. 별도의 선행 하네스
구현 계획은 현재 main, 관련 작업 폴더의 계획 경로, 이 대화 원문에서 특정되지
않았다. 발견한 9월 3일 `assistant-deck` 계획은 이미 병합된 UI 작업이며
`src/ai` 데이터층 변경을 범위 밖으로 두었다. 따라서 이번 계획은 그것을
덮어쓰는 수정이 아니라, **직전 설명에서 파악한 구조를 바탕으로 새로 구체화한
하네스 개선안**이다. 다른 세션에 미발견 계획이 있을 가능성은 남긴다. [C14,O19]

또한 설치된 omo는 native/Senpi 계열이다. 이름이 비슷한 옛 OpenCode용 OMO,
설치본과 버전이 다른 upstream 코드, 오래된 README를 같은 것으로 취급하지
않았다. `/home/main/z-project/omo`는 실제 git 소스 저장소가 아니었다. [C01]

## 2. 쉬운 비유: 조수에게 필요한 것은 ‘작업 책임표’

현재 구조를 식당으로 보면 AI는 주문을 읽고 조리 도구를 부르는 사람이다.
하지만 “불을 껐다”는 것과 “주문한 음식이 손님에게 나갔다”는 것은 다르다.

| 현재 관찰할 수 있는 것 | 앞으로 분명히 구별할 것 |
|---|---|
| AI 응답이 끝남 | 이번 실행이 멈춘 이유 |
| 도구가 성공함 | 요청한 결과가 실제로 만들어짐 |
| 계획의 모든 항목이 종료됨 | 필수 요구가 빠짐없이 충족됨 |
| 화면에 변경이 보임 | 해당 변경이 서버에 저장됨 |
| 재조회 요청을 실행함 | 같은 프로젝트의 같은 저장 결과를 확인함 |
| 대화가 다시 열림 | 실행 상태를 안전하게 복원함 |

이 구별을 모델의 말투가 아니라 데이터로 유지하는 것이 핵심이다.
상세 감사 로그를 기본 화면에 늘어놓자는 제안은 아니다. 사용자에게는
“적용됨 / 원격 확인됨 / 일부 미완료 / 사용자 중단 / 복구 확인 필요”처럼
실제 상태에 맞는 짧은 결과를 보여주면 된다. [C02,C05-C10]

## 3. omo에서 채택할 것, 바꿔 가져올 것, 버릴 것

| 원칙 | 결정 | RPG에 맞춘 적용 |
|---|---|---|
| 대화 한 턴보다 오래 유지되는 목표 | 채택 | 기존 WorkPlan에 원래 요청·필수 요구·범위 변경 근거를 유지 |
| 요구별 실제 증거를 확인하고 끝내기 | 강화해서 채택 | 기존 ToolVerificationEvidence와 적용·저장 영수증을 연결 |
| 작업 목록과 현재 진행 상태를 분리해 관리 | 채택 | 항목 done/skipped와 사용자 목표 충족을 별도 판정 |
| 기다림·중단·실패·완료 구별 | 변형 | 브라우저 작업에 맞는 typed 결과와 run epoch 사용 |
| 재개 가능한 기록 | 변형 | 파일 저널 대신 기존 IndexedDB에 버전 있는 실행 체크포인트 |
| 취소 후 늦은 결과 폐기 | 채택 | runId/epoch와 프로젝트 기준 버전이 맞는 결과만 수용 |
| 독립 작업 병렬화 | 제한 채택 | 읽기·분석만 후보. 같은 프로젝트의 저작·적용은 단일 작성자 |
| CLI의 파일·PTY·Git 메모리 방식 | 그대로 복사하지 않음 | 브라우저 사건 구독, 프로젝트 스냅샷, 기존 저장 경로로 치환 |
| 범용 DAG·다중 에이전트 기본 실행 | 거부 | 현재 문제를 해결하지 않고 변경 충돌과 복구 복잡도부터 늘림 |
| 긴 프롬프트·무한 계속·모든 경고 차단 | 거부 | 기계 계약은 코드로, 지침은 판단 보조로; 현재 예산·advisory 구별 유지 |

근거: C05,C08-C13 및 `debate-log.md`. 성능·비용 개선 비율은 측정하지 않았으므로
주장하지 않는다.

## 4. 중요한 반전: omo도 모든 것을 보장하지 않는다

설치본의 완료 감사 프롬프트는 “각 요구를 현재 증거에 대응시키라”고 요구한다.
그러나 실제 `update_goal` 실행부가 검사하는 것은 이유 필드와 열린 todo다.
파일·실행·산출물 증거의 충분성을 판정하는 범용 검증기가 아니다. [O07]

설치된 순수 함수를 직접 실행한 결과:

- 증거 인자 없이 todo를 done/drop/rm 하면 열린 항목이 사라진다.
- 순수 목표 전이 함수는 증거 없이 complete로 이동할 수 있다.
- 첫 blocked도 이유가 있으면 허용된다.
- 무인 계속 상한은 monitor 경로까지 포괄하는 절대 상한이 아니다. [E01]

따라서 **“omo에 있으니 검증된 완료 보장을 가져온다”는 주장은 기각했다.**
좋은 규율은 가져오되, 게임 제작의 실제 판정은 RPG의 도구 결과와 프로젝트
상태에서 수행해야 한다. [C05, debate 1]

## 5. RPG에 이미 있는 것은 다시 만들지 않는다

| 이미 있는 장치 | 근거 | 계획에서의 처리 |
|---|---|---|
| 의도 해석·WorkPlan·항목 계속·실행 상한 | `assistantSession.ts`, `workPlan.ts` | 유지하고 누락된 종료 의미만 보강 |
| 검사 실행 성공과 실제 verdict 구분 | `toolVerificationEvidence.ts:18-34` | 그대로 재사용 |
| 관련 쓰기 뒤 명시적 검증을 stale 처리 | 같은 파일 `36-50` | 복원과 최종 표시에서도 이 규칙 유지 |
| 일반 채팅 자동 적용·undo | `approvalPolicy.ts`, `applyChangesetToStore.ts` | 승인 카드 부활 금지 |
| 질문 모드 쓰기 차단 | `assistantSession.ts`의 노출·실행 가드 | 강한 회귀 계약으로 유지 |
| 새 계획/확인 턴 정지와 기존 계획 계속 | `assistantSession.ts:1663-1699` | 둘을 같은 읽기 전용 모드로 취급하지 않음 |
| 압축·대화 보관·이전 기록 주입 | `contextCompaction.ts`, `conversationStore.ts`, `conversationReplay.ts` | “기억이 없다”가 아니라 실행 복원 공백만 보완 |
| 프로젝트 변경·undo·원격 저장 | 기존 tools/store/supabase 경로 | 우회 저장·별도 저작 엔진 금지 |

RPG의 레이어 전체 검증에는 의도적으로 advisory인 부분이 있다. 기존 전역
lint 오류 때문에 관계없는 작업까지 반복·중단되던 문제가 이유다. 이를 모두
hard gate로 바꾸면 퇴보다. 명시한 필수 검사와 참고 경고를 구별해야 한다.
[O11,O14]

## 6. 실제로 확인한 우선순위

### P0. 저장 증명이 사실보다 앞선다

`maybeRunEndProof()`는 flush가 saved이면 재조회를 호출하지만,
reload 결과가 failed/cancelled여도 `agent_run_saved`와 완료 메시지를 낸다.
또 성공 전에 planId를 시도 완료처럼 기록해 같은 계획의 재시도도 막는다.

리드가 **읽어온 실제 메서드 본문**을 격리 실행해 세 분기를 확인했다.
failed/cancelled 모두 saved 감사가 나왔고 두 번 호출해도 flush는 한 번이었다.
이는 실제 Supabase 장애 재현은 아니지만 해당 분기 결함의 직접 실행 증거다.
[C02,E02]

수정 원칙: 실제 적용 버전에 묶인 저장 영수증과 동일 대상의 읽기 결과를
비교한다. 시도·실패·성공을 구분하고 실패 후 같은 버전의 재검증을 허용한다.
재조회가 사용자 최신 편집을 덮지 않도록 **검증용 읽기는 편집기 상태를
교체하지 않는 방식**을 우선한다. 기존 새 프로젝트 트랜잭션의 정규화된 비교
패턴을 재사용한다. [C13,O16]

### P1. 계획 종료와 목표 완료가 섞인다

WorkPlan은 모든 항목이 done 또는 skipped면 종료된 것으로 본다.
이것은 스케줄러로서 타당하지만, 사용자가 요청한 필수 결과까지 달성했다는
의미로 쓰면 안 된다. 선택적인 작업 생략은 허용하되 필수 요구는 사라지지
않아야 한다. [workPlan.ts:739-757,850-863]

새 거대한 Goal DB 대신 기존 WorkPlan 안에 요구 식별자와 근거 연결을 두고,
최종 결과는 기존 원장으로 계산한다. 모델이 임의 evidence 문자열을 써서
성공으로 승격하는 입력은 만들지 않는다.

### P1. 대화 복원과 실행 복원이 다르다

현재 대화 레코드는 감사 항목 중심이며 실행 체크포인트가 아니다.
새 세션에는 최대 12,000자의 이전 기록 텍스트를 넣는다. 특히 부팅 경로는
마지막 user/assistant만 보므로 성공한 tool 항목이 뒤에 있어도 user를 다시
전송할 수 있다. [C06,C07,O09,O10]

다만 **모든 복원이 재실행되는 것은 아니다.** 제안 적용은 도구를 재호출하지
않고 스냅샷을 적용한다. 위험은 확인되지 않은 부팅 재전송과 적용 경계의
복구에 한정한다. [debate 1]

새 체크포인트는 현재 계획·예산·종료 이유·미확정 변경·확인된 적용 버전을
보관한다. 복원 때 현재 프로젝트와 대조하고, 적용 여부를 판단할 수 없는
쓰기 작업은 자동으로 반복하지 않는다. 로컬 저장만으로 전 기기 exactly-once를
보장한다고 말하지 않는다. [C10]

### P1. 취소·늦은 응답·오래된 초안의 소유권

omo에서 가져올 만한 실제 기계 장치는 terminal 전이 제한, run epoch,
취소 세대가 다른 늦은 응답 폐기다. 이를 RPG의 적용·저장·검증 콜백에도
같은 실행 식별자로 연결한다. [C11]

현재 turnBusy와 집 보호가 일반 프로젝트 버전 잠금은 아니다.
기존 테스트는 집이 아닌 영역의 최신 편집이 오래된 제안에 의해 덮이는
정책을 명시적으로 허용한다. 이를 막는 것은 **명시적인 정책 변경**으로 계획에
기록하며, 기존 테스트를 이유 없이 약화시키는 방식으로 숨기지 않는다. [C12]

### P2. 시각 자료 전달과 시각 품질을 분리한다

맵 조회 범위가 기록된 것, 이미지가 생성된 것, 모델 요청에 이미지가 첨부된 것,
게임이 보기 좋고 플레이 가능한 것은 다른 사실이다. 이미지 렌더러가 실패했는데
조회 좌표만으로 시각 검증 완료를 표시해서는 안 된다.
전달 영수증은 “첨부됐다”까지만 보장하며 모델의 내부 이해를 증명하지 않는다.
[RPG source: assistantSession.ts:2202-2224,2249-2276,3763-3804]

## 7. 바뀐 계획의 구조

```text
기존 설명의 중심
요청 → 컨텍스트 → 계획 → 도구 반복 → 적용 → 저장

수정 계획의 중심
사용자 요구·보존 조건
        ↓
기존 WorkPlan + 기존 검증 원장
        ↓
실행 식별자·버전이 붙은 도구/적용 결과
        ↓
적용됨 ── 저장됨 ── 동일 저장본 확인됨
        ↓
목표 결과 판정 / 짧고 정확한 사용자 표시

중단·재시작 시:
체크포인트 → 현재 프로젝트 대조 → 안전한 재개 또는 확인 대기
```

실행 항목과 RED/GREEN·실표면 시나리오는
[`../../plans/ai-harness-omo-adoption.md`](../../plans/ai-harness-omo-adoption.md)에
정리한다. 요구 추적·정확한 완료·복구·수명주기·검증을 순서대로 이행한다.

## 8. 검증 수준과 남은 제한

- 리드 직접 실행: OMO 순수 완료/계속 함수 반례, RPG 실제 저장 증명 본문 분기.
- 소스 대조: 기존 검증 원장, WorkPlan skip, 부팅 재전송, 저장 결과 타입,
  기존 비파괴적 저장 처리·정규화 비교 패턴.
- 연구자 보조 실행: 관련 10개 테스트 파일은 **78 통과·1 시간 초과, exit 1**.
  단독 재실행 성공이 원래 결과를 지우지 않는다. 현재 전체 게이트 통과라고
  보고하지 않는다. [E03]
- 실제 브라우저/DB/충돌·크래시 주입은 **후속 구현의 승인 조건**이다.
  이번 연구에서 실행하거나 성공했다고 주장하지 않는다.
- 새 원격 테이블, 분산 잠금, 서버 상주 에이전트, 임의 코드 실행기는 이번
  권고에서 도입하지 않는다. 필요성을 입증할 후속 근거가 없기 때문이다.
- 한국어 연구·계획 산문이므로 문장 일치 테스트는 만들지 않았다.

## 근거 읽는 법

`Cxx`는 `claim-graph.md`, `Oxx`는 `observation-manifest.md`,
`Exx`는 `evidence.md`의 식별자다. 독립성은 에이전트 수가 아니라
소스·실행 경로의 차이로 판단했다. 설치본 단일 출처만 있는 좁은 내부 동작은
단일 출처 한계를 표시한다. 상반된 가정의 판정은 `debate-log.md`에 남겼다.
