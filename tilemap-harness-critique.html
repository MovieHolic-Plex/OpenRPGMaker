1. 시스템 구조 한눈에 보기

"타일맵 하네싱"이란: LLM(AI)이 프로시저럴하게 맵을 생성하고, 결정론 평가기가 결과를 채점해서 실패하면 자동 수리하는 루프 시스템이다.

🏠

Interior Room Harness

실내 맵 생성 (침실, 주방, 서재 등)

레이어: plan → floor → walls → furniture → entrance → critique

interiorRoomPipeline.ts (~1,800줄)

🏘️

Village Harness

마을 맵 생성 (집, 도로, NPC, 나무)

레이어: plan → map → water → settlement → forest → critique → look

🎯 Walkability Enforcement — 뚫리지 않는 벽

가구 배치 후 BFS로 문→모든 개방 셀 도달을 확인한다. 막힌 곳이 있으면 "제거 가능 단일 소품"을 녹여서(최대 12개) 길을 뚫는다.

치명적 한계: 침대, 긴 탁자, 피아노 같은 Hard Cluster 멀티타일이 길을 막으면 포기하고 경고만 남긴다.

성공률 체감: 작은 방 OK, 복잡한 다실 구조에서 실패 빈번

3. 게임성 비판

🎮 비판 #1: 완전한 블랙박스 — 유저는 구경꾼

맵 생성이 전적으로 LLM ↔ 하네스 사이에서 일어난다. 유저가 "큰 침실 만들어줘"라고 채팅에 치면, 뒤에서 5~12턴이 돌아간 후 "완성됐습니다" 한 줄 뿐.

  • 생성 중간 미리보기 없음
  • 배치 의도 설명 없음 ("여기에 침대를 놓은 이유는...")
  • 진행률 바 없음 — 10초인지 2분인지 모름

RPG 메이커 2003이 25년 전에도 타일 하나하나 직접 찍는 쾌감을 줬다. 자동 생성기가 그 쾌감을 대체하려면 최소한 "만들어지는 과정"을 보여줘야 한다.

🎮 비판 #2: 테마 7종의 한계

실내 테마:

bedroom
study
dining
kitchen
storage
tavern
corridor

빠진 것들:

❌ 성/왕좌실
❌ 교회/신전
❌ 학교/도서관
❌ 감옥/지하실
❌ 상점/대장간
❌ 온천/목욕탕

JRPG 한 작품에 쓰이는 실내 유형은 최소 15~20종. 현재 7종으로는 "어떤 마을이든 집 안이 다 비슷한" 지루함을 피할 수 없다.

🎮 비판 #3: NPC 스케줄은 유령 기능

평가기가 NPC 시간표를 요구하지만, 프로젝트의 timeSystem.enabled = false이면 시간표가 절대 실행되지 않는다.

// villageEvaluate.ts 실측: if (metrics.scheduledNpcs > 0 && !resolveTimeSystem(input.project)) { issues.push("시간 시스템이 꺼져 있어 주민 시간표가 실행되지 않는다"); // 하지만 이것은 게이트를 실패시키지 않음! (무한 재시도 방지) }

결과: NPC가 3단계 일정(아침-낮-저녁)을 갖고 있어도 게임 플레이 시 제자리에 서 있다. 생성기가 만든 "생동감"은 허상이다.

🎮 비판 #4: Walkability 실패 = 플레이어 갇힘

enforceWalkability는 최대 24패스 × 12제거로 길을 뚫지만, Hard Cluster(침대, 피아노, 긴탁자)가 경로를 막으면 포기한다.

실패 시 반환:

"walkability: 도달 불가 개방 셀 3개 — 제거 가능한 소품 없음 (멀티타일 세트가 길을 막음), 예: (4,7)"

이 경고는 LLM에게만 전달된다. 만약 LLM이 수리에 실패하고 세션이 그냥 종료되면, 플레이어가 방 구석에 갇히는 맵이 그대로 저장된다.

🎮 비판 #5: 시드 = 재현성 ≠ 다양성

같은 테마 + 같은 시드 → 같은 맵. mulberry32 RNG를 쓰는데, 시드를 바꾸는 방법이 "seed+1로 재시공" 뿐이다.

가구 배치 규칙이 표면(surface) 기반이라, 같은 테마에서는 가구 종류가 고정이고 위치만 랜덤 → "다른데 같아 보이는" 방이 양산된다.

4. UI/UX 비판

💻 비판 #1: 채팅 = 유일한 인터페이스

맵 생성의 전체 UX:

사용자: "침실 3개짜리 집 내부 만들어줘" AI: (5~30초 동안 아무 피드백 없음) AI: "완료했습니다. 맵 ID: harness-interior-house-v1-xyz"

비교 대상:

도구피드백 방식
RPG Maker MZ실시간 타일 미리보기 + 커서
Tiled Map Editor즉시 반영 + 레이어 토글
RPG ZZU Harness텍스트 "완료" 한 줄 🤷

💻 비판 #2: 40 도구 쿼터 — 도구가 사라진다

LLM에 노출되는 도구가 최대 40개로 제한된다. 핀(pin) 시스템이 보장하는 것은 "tile" 도메인의 핵심 도구뿐.

MAX_EXPOSED_TOOLS = 40; // 실측: place_chest가 크라우드아웃되어 LLM이 호출 불가했던 사건 // → round-robin 분산으로 완화했지만 근본 해결 아님

결과: 유저가 "상자 놓아줘" 라고 해도 AI가 "그 도구를 모릅니다" 라고 답할 수 있다. 도구 존재를 유저가 알아야 하는 구조.

💻 비판 #3: 평가 실패 = 유저에게 안 보이는 내부 독백

feedbackForLlm이라는 이름이 모든 것을 말한다. 평가 결과(issues, fixes, score)는 전부 LLM이 소비하는 텍스트이고 유저에게는 보여주지 않는다.

유저가 보는 것

"맵을 수정하고 있습니다..."
(또는 아예 아무 메시지 없음)

LLM이 보는 것

"도로 직선 구간이 96타일로 너무 길다.
NPC 활동이 2종뿐이다.
울타리가 필지를 과도하게 둘러싼다.
fix: meander_roads, diversify..."

💻 비판 #4: 부분 수정 불가 — 전체 재생성만

실내 하네스의 furnish_interior_space가 개별 방 단위 리퍼니시를 지원하긴 하지만:

  • 벽은 수정 불가 (floor/walls 레이어 재실행 필요)
  • 방 크기 변경 불가 (plan부터 재시작)
  • "침대만 왼쪽으로 옮겨줘" → 전체 리퍼니시 (위치 지정 API 없음)
  • 마을: 집 하나만 이동/삭제 불가 → rebuild_settlement

유저 의도의 세밀함 vs 시스템의 거친 조작 단위 사이 격차가 크다.

💻 비판 #5: 세션 실패 시 "왜?" 를 모른다

마을 세션이 12턴 예산을 소진하면:

session.status = "failed" // 끝. 유저에게 "실패했습니다" or 침묵.

실패 원인(도달성? 수목 부족? NPC?) 을 유저 언어로 번역하는 계층이 없다. 디버깅은 session.checklist를 코드 레벨로 들여다봐야 가능하다.

5. 아키텍처 약점

🔧 약점 #1: 타일 ID 하드코딩 — 아트셋 교체 불가

// 침대가 355+356이라는 것이 코드에 70번 이상 등장 VR.BED_L = 355; VR.BED_R = 356; VR.STOVE_TOP = 21; VR.STOVE_BOT = 51; // ... 60개 이상의 const // 다른 타일셋을 쓰고 싶다면? → 전체 재작성.

추상화 계층 없이 combined_town과 easyrpg_chipset_interior 타일셋에 완전 종속. 유저가 커스텀 타일셋을 쓰면 하네스가 무용지물.

🔧 약점 #2: 1,800줄 단일 파일 — 유지보수 지옥

interiorRoomPipeline.ts 하나에:

  • 타일 상수 60개
  • 러그 패턴 3종
  • 바닥/벽 재질 매핑
  • PropSurface 배치 테이블
  • Hard Cluster 규칙 4개
  • TileGroupMetadata 정의 15+개
  • enforceWalkability BFS 알고리즘
  • fillSparseQuadrants 로직
  • 레이어 실행 함수 6개
  • 평가(critique) 로직

대비: villageSession.ts는 빌더를 village/ 하위 7개 모듈로 분리한 좋은 사례가 이미 있다.

🔧 약점 #3: 시각 평가 부재 — 숫자만 세는 평가기

// villageEvaluate.ts 첫 줄 주석에 이미 적혀있다: // "멀티모달 LLM은 같은 VillageLookReport 스키마를 채우면 된다" // → 2026년 7월 현재, 아직 구현 안 됨

타일을 세고(treeCells ≥ 20), 직선 도로 길이를 재고(≤ 50%), 문 앞 BFS를 돌리는 것으로 "예쁜 마을"인지 판단한다.

못 잡는 것들: 색 조화, 건물 간격의 리듬감, 도로 곡선의 자연스러움, 나무 분포의 시각적 밸런스, 전체적 구도.

7. 최종 판정

🏚️

엔지니어를 위한 시스템, 유저를 위한 제품은 아님

프로시저럴 생성 + 자동 수리 루프라는 엔진은 인상적이다. 하지만 그 엔진 위에 유저가 느끼는 쾌감, 통제감, 이해도를 전달하는 계층이 완전히 빠져있다.

지금 당장 고쳐야 할 3가지:

1️⃣ 생성 중간 미리보기 — 각 레이어 완료 시 캔버스 스냅샷을 유저에게 보여줄 것

2️⃣ 평가 결과 유저 번역 — feedbackForLlm을 사람 언어로 요약해 채팅에 표시

3️⃣ 부분 편집 API — "침대를 왼쪽으로", "나무 3개 더" 수준의 세밀한 조작 지원
