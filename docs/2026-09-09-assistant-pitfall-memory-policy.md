# 조수 함정 기억(pitfall memory) 정책 — OPRN-OUT-015 결정 기록

> 작성: 2026-09-09
> 목적: 이슈 #701 의 `OPRN-OUT-015` 가 **구현 전에 요구하는 「기록된 정책」**. 코드가 아니라 결정이 산출물이다.
> 범위: 스튜디오 조수가 과거 실수를 반복하지 않게 하는 「함정 → 예방 → 검증 → 해소」 계약.
> 상태: v1 방향 확정. 아래 D1·D2 는 감독 결정, D3~D5 는 그 두 결정에서 따라 나오는 권고안.

---

## 0. 왜 이 문서가 코드보다 먼저인가

`OPRN-OUT-015` 의 수용 기준 첫 줄은 *"고비용 모델 리뷰와 명시적 인간 관리자 결정이 구현 승인 전에 기록되어야 한다"* 이고, 마지막 줄은 *"각 조수 표면마다 개별 인벤토리와 명시 승인이 필요하다"* 다. 원 제안자도 이렇게 못박았다 — **"적용되지 않고 넘어가는 것보다도 큰 고민 없이 적용됐을 때가 더 리스크 있다."**

즉 이 항목에서 코드를 먼저 쓰는 것은 이슈 자체를 위반하는 것이다. 이 문서가 그 요구를 만족시키는 기록이다.

---

## 1. 무엇이 이미 있고, 무엇이 없는가 (소스 확인)

재료는 대부분 있다. 없는 것은 **한 조각**이다.

| 있는 것 | 근거 |
| --- | --- |
| 구조화된 활동 기록(지시·툴콜·감사·진단·실행 결과) | `src/ai/activityLogTypes.ts` |
| 상한 있는 로컬 활동 링, **조건부 원격 미러링** | `src/ai/activityLog.ts` — `legacyDbProjectConfig` / `recordLegacyDbAiActivityLog` / `remoteOutbox` |
| 결정적 선호 신호 수집 | `src/ai/preferenceSignals.ts` — `CORRECTION_WINDOW_MS = 60_000`, `CORRECTION_CUES`, `COUNTER_LIMIT = 60` |
| 임계 초과 시에만 도는 라이트 모델 증류 | `src/ai/preferenceDistiller.ts` |
| 스코프·근거수·강도·출처·고정·축출·크기상한·삭제를 갖춘 기억 | `src/ai/preferenceMemory.ts` |
| **기억이 현재 지시를 이기지 못하게 하는 우선순위 문장** | `preferenceMemory.ts:63` — "이번 지시와 충돌하면 **지시가 우선**한다" |
| 사용자 열람·추가·고정·삭제 UI | `src/editor/panels/aiPreferenceMemorySettings.ts` |
| 레이어별 자문 검증 선택·1회 실행 | `src/ai/agentVerification.ts`, `src/ai/assistantSession.ts` |
| 차단·취소·예산소진·실패·미완·충족 결과 구분 | `src/ai/runOutcome.ts` |

**없는 것**: 「실패 종류 + 예방 규칙 + 검증 레시피 + 해소 상태 + 신뢰도 + 적용 범위 + 만료」를 담는 **타입 있는 함정 레코드**와, 결정적 체크포인트에서 그것을 한 번 꺼내 쓰는 경로.

선호 기억 스키마를 재사용하지 **않는다**. 그 스키마는 취향과 작업 습관을 담고, 실패 종류·검증 레시피·해소 상태·만료를 담지 못한다. 이슈의 표현대로 **정확성 함정을 개인 취향으로 위장하면 안 된다** — 우선순위·보존·동의 정책이 달라야 하는 데이터를 한 상자에 넣으면 둘 다 잘못 다루게 된다.

## 2. 감독 결정

### D1 — opt-out 상태의 강제 1회 검사: **거절**

원 제안은 자동 검사를 끈 사용자에게도 반복 활동이나 불만족 표현이 감지되면 1회는 함정 노트를 참조하게 하자는 것이었다. 이슈도 이것을 "승인된 기본값이 아닌 열린 고위험 정책 질문"으로 따로 떼어 기록했다.

**거절한다. 「자동 검사 끔」은 숨은 예외 없이 꺼진 상태로 남는다.** 사용자가 끈 것이 꺼지지 않으면 그 스위치는 거짓말이 된다.

대신 같은 목적을 달성하는 경로를 둔다.

- 결정적 신호(§D3)가 걸리면 **모델 호출·툴 호출 없이** 한 줄만 제시한다: 「비슷한 작업에서 이런 함정이 기록돼 있습니다. 확인할까요?」
- 실제 조회·검사는 **사용자가 그 제안을 눌렀을 때만** 돈다. 누르는 행위가 그 1회에 대한 동의다.
- 제안 자체도 작업 항목당 1회, 그리고 거절되면 그 작업 항목에서 다시 뜨지 않는다.

이 경로는 토큰을 쓰지 않고, opt-out 의미를 보존하며, 반복 실수 차단이라는 원 요청의 목적은 달성한다.

### D2 — v1 데이터 범위: **큐레이션 규칙만**

네 부류를 개념적으로 분리하되, v1 에는 첫 번째만 배포한다.

| 부류 | v1 | 출처·동의 |
| --- | --- | --- |
| 제품 큐레이션 함정 | **포함** | 제품·도구 소유, 버전·리뷰됨, 사용자 대화 데이터 없음 |
| 프로젝트 함정 | 보류 | 한 프로젝트/명시적 프로젝트 family 한정 |
| 개인 학습 노트 | **보류** | 사용자 교정·undo 에서 도출 — 동의 규칙 승인 후에만 |
| 일회성 트리거 | **포함**(비영속) | 한 작업의 경고·검사 영수증. 해소 확인 전까지 영속 기억으로 승격 금지 |

**v1 에서 금지하는 것**을 명시한다.

- 원시 사용자 텍스트와 툴 인자를 이 목적에 재사용하지 않는다.
- 이 목적의 데이터를 원격에 저장·미러링하지 않는다. `activityLog` 가 프로젝트 설정에 따라 이미 조건부 원격 미러링을 하므로(§1) 이것은 가상의 제약이 아니라 실재하는 경계다.
- 모델이 자기 이전 해소를 성공이라 판단한 것만으로 규칙을 승격하지 않는다.

개인 학습 노트를 나중에 도입할 때는 §5 의 조건을 먼저 만족해야 한다.

## 3. D3 — 트리거: 제안된 두 트리거를 **명시적으로 거절**한다

이슈의 수용 기준은 「같은 라벨」·「5회」·「불만족」·「1회」·리셋·쿨다운·재동의를 **정의하거나 명시적으로 거절하라**고 요구한다. 거절한다.

**거절: 「같은 라벨 5회」.** 라벨 정체성이 chat·맵 영역·이벤트 편집·타일셋 분석에 걸쳐 안정적이라는 근거가 없다. 무엇을 세는지(시도·툴콜·완료된 턴)도 미정이고, 5 라는 숫자에 어떤 작업 계열에 대한 근거도 없다.

**거절: 「불만족 단어」를 트리거로 쓰는 것.** 짧은 한국어 구절로 불만족을 판정하면 부정·인용·비꼼·문맥에서 틀린다. `preferenceSignals` 의 `CORRECTION_CUES` 는 60초 창 안의 **약한 가중치 신호**(-2)로 쓰이도록 설계된 것이고, 검사를 발동시키는 용도가 아니다.

**채택: 결정적 신호만.**

- 구조화된 툴 실패 진단(`runOutcome` 의 실패·차단 결과)
- undo 이벤트
- 현재 작업 계획의 항목·레이어 라벨 (이미 존재하는 것만, 새로 만들지 않음)
- 사용자의 명시적 확인

감정 단어는 **후보 지명까지만** 허용한다 — 즉 어떤 함정 레코드가 관련될 수 있는지 고르는 데는 쓰되, 그것만으로 영속 규칙을 만들거나 모델 워크플로를 발동시키지 않는다.

## 4. D4 — 주입·검사의 한계와 실패 시 동작

- 작업과 **관련된** 레코드만 조회한다.
- 주입은 **작업 항목 또는 결정적 국면당 1회**. 메시지당이 아니다.
- 중복 제거하고, 줄 수·문자 수를 대화 문맥과 **독립적으로** 상한한다.
- 검사는 **등록된 검증 도구와 증거 의미론을 재사용**한다. 별도 검증 실행기를 만들지 않는다.
- 추가 모델 호출·토큰·툴 호출·시간에 각각 상한을 둔다. 소진 시 `runOutcome` 의 기존 예산·결과 계약을 보존한다.
- 영수증을 남긴다: 무엇이 트리거했는지, 어떤 규칙을 골랐는지, 어떤 검사를 했는지, 비용, 결과, 우회·동의 상태. `src/editor/panels/aiHarnessModal.ts` 가 이미 오케스트레이션 타임라인·툴 인자·토큰 총계를 보여 주므로 그 표면을 쓴다.
- **함정 검사가 다시 함정 검사를 트리거할 수 없다.**
- 기억은 현재 지시에 종속된다 — `preferenceMemory.ts:63` 의 우선순위 계약과 같은 규칙을 쓴다.

**실패 시 동작.** 자문은 **fail-open** 이다. 함정 검사가 실패하거나 예산이 소진되면 그 사실을 보고하고 작업은 계속한다. **fail-closed 는 독립적으로 승인된 무결성 게이트에만** 허용된다. 선택적 검사의 실패가 무관한 작업을 조용히 막거나 바꾸거나 범위를 넓히는 일은 없다.

## 5. D5 — 롤아웃과 개인 노트 도입 조건

**v1**: 큐레이션 규칙 + 비영속 일회성 트리거. 읽기 전용 섀도 평가부터 — 「자동 검사가 있었다면 몇 번 맞췄고 몇 번 헛다렸는가」를 먼저 재고, 그 수치로 다음 단계를 정한다.

**측정 항목**은 이익과 해악을 함께 본다: 반복 실패율, 검사 정밀도, 사용자 우회 횟수, 추가 지연·비용, 거짓 차단, 낡은 규칙 비율, 프라이버시 사건.

**개인 학습 노트를 도입하려면** 그 전에 다음이 전부 있어야 한다.

- opt-in 기본값, 스코프, 저장 위치, 원격 미러링 동작, 보존·만료, 내보내기, 교정, 삭제, 프로젝트 삭제 시 동작, 계정·기기 경계가 명시된 동의 문서
- 노트가 열람·수정·삭제·내보내기 가능하고, 스코프·용량 상한이 있으며, 만료 정책이 붙어 있음
- 해소 승격에 **독립적 근거 또는 사용자 확인**이 필요하고, 낡으면 만료·폐기됨
- 킬 스위치, 롤백 경로, 스키마 마이그레이션, 삭제 동작이 **테스트된** 상태
- `OPRN-OUT-009`·`010`·`011`(동의 기반 진단 내보내기, opt-in 조수/테스트플레이 진단, 이벤트 커맨드 검증 핸드오프)의 동의·증거 결정을 **재사용** — 충돌하는 별도 컨트롤을 만들지 않는다

**표면별 승인.** 조수 채팅·이벤트 커맨드 보조·영역 작업·타일셋 분석·자율 작업 계획·전용 빌드 하네스는 각각 작업 정체성·사용 가능한 검증 레시피·데이터 민감도·동시성·비용 프로필·실패 영향을 인벤토리한 뒤 개별 승인을 받는다. **한 파일럿 승인이 스튜디오 전역 배포를 승인하지 않는다.**

## 6. 아직 확립되지 않은 것 (구현 전 확인 대상)

이슈가 "미확립"으로 분류한 항목 중 이 정책이 **해소하지 못한** 것들이다.

- 작업 라벨이 표면들에 걸쳐 검사를 구동할 만큼 의미적으로 정확한가 — §D3 은 기존 라벨만 쓰기로 회피했을 뿐 검증하지 않았다.
- 모델이 생성한 해소 노트가 프로젝트 변경·제품 업데이트 후에도 맞는가 — §D2 가 개인 노트를 보류해 회피했다.
- 이익이 토큰·지연·저장·프라이버시·거짓양성 비용을 넘는가 — §D5 의 섀도 평가가 답해야 한다.
