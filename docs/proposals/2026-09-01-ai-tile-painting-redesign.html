— LLM 은 의도를, 코드는 픽셀을

지금 구조는 LLM 에게 붓을 쥐여 주고(좌표·타일 인덱스 직접 지정) 잘 칠하도록 설득한다(스펙 게이트·볼륨 계약·다양성 되먹임). 제안은 반대다 — LLM 은 붓을 고르기만 하고(작은 JSON 하나), 칠하는 것은 전부 시드 기반 결정적 생성기가 한다. 다양성은 설득이 아니라 표본추출 규칙으로 보장된다.

§1 · 진단

왜 "지형을 깎으라"가 가장 어려운 작업이 됐나

코드베이스가 이미 답을 알고 있다. 다섯 가지 사실을 코드에서 그대로 읽었다.

사실 1 — LLM 이 좌표와 타일 인덱스를 직접 뱉는다

현행 경로는 프롬프트 → 플래너(LLM) → WorkPlan → 생성기(LLM) → paint_tiles {cells, tileId} 툴콜 수십 개다. 타일 하나하나가 토큰이고, 토큰 하나하나가 비결정성이다. 그래서 느리고, 비싸고, 같은 프롬프트가 매번 다른 품질로 나온다. 이 비결정성을 막으려고 게이트가 자랐다 — buildSpec 밑그림 검증(682줄), WorkPlan successTools 게이트(850줄), 완성도 린트, Ralph 재주입.

사실 2 — 타일 의미론의 진실이 세 벌이다

① 코드 시맨틱 테이블(tileSemantics*.ts 9파일 · 346항목 · 43종 자유 역할 문자열 · 사람이 UI 로 못 고침), ② 프로젝트 데이터(tileGroups/tileMeta · AI 프롬프트에 실림), ③ 역할 enum 두 벌(TileGroupRole vs PaletteSlotRole · terrain/ground, fence/boundary 동의어 난립). PR #435(A-1·A-2)가 15곳의 역할 분기를 roleCapabilities() 하나로 모은 것은 옳은 수술이었다. 문제는 다음 단계 A-3 — 역할을 사용자 정의 문자열로 개방하고 DB 탭·마이그레이션·villagePresets 를 얹는 방향이다. 43종 어휘가 복잡해서 생긴 병을 "사용자가 어휘를 더 만들 수 있게" 해서 고칠 수는 없다.

사실 3 — 다양성을 '설득'으로 만들고 있다

"author_house 는 kitId 6종만 흔들 수 있어서 AI 가 같은 사각형에 색만 바꿔 깔았다. 모양 어휘(templateId)를 열어 주더라도 모델이 '지금 몇 종을 썼는지'를 볼 수단이 없으면 여전히 한 종에 수렴한다. 그래서 감지 → 리포트 → 프롬프트 되먹임의 관찰 고리를 만든다." — src/editor/tools/houseVariety.ts 머리말 (2026-08-31)

집 형태 카탈로그 34종은 이미 선언형 데이터로 존재한다(houseTemplateCatalog.ts). 그런데 "어떤 템플릿을 쓸지"를 LLM 이 고르게 했더니 한 종에 수렴했고, 그걸 고치려고 맵을 되읽어 다양성을 리포트하고 프롬프트로 되먹이는 관찰 고리가 생겼다. 확률 모델에게 "골고루 뽑아라"라고 부탁하는 구조 — 비복원 추출 세 줄이면 코드가 보장할 수 있는 성질이다. 숲은 더 심하다. 숲 전용 생성기는 아예 없고, fill_region+scatter 를 LLM 이 즉흥 조합한다.

사실 4 — 볼륨 계약이 폭주의 근인이다

2026-09-01 적대적 20프롬프트 실사: 마을·집을 요청한 프롬프트가 0개인데 맵 1→39개, 이벤트 0→593개. "방금 한 거 취소해" 요청에 맵이 16→32로 두 배. 원인은 플래너가 직접 실행 계획을 내면 코드가 그것을 거부하고 고정 볼륨 계약(허브맵→NPC→상점→퀘스트)으로 갈아끼우는 경로 + 완성도 린트가 "변경 0건 = 미이행"으로 처벌하는 규칙이다. 판단력의 문제가 아니라 쓰기 경로의 강제 주입 문제라는 것이 실사의 결론이었다.

사실 5 — 검증이 vision 에 기대고 있다

상·하층 타일이 겹쳐 렌더된 이미지를 모델이 "보고" 판정해야 한다. 겹친 픽셀에서 의미를 복원하는 것은 비전 모델에게도 어려운 문제라서(타일 80을 탁자로 오인한 전례), 검증이 느리고 확률적이다. 반면 의미 그리드(이 칸은 tree, 이 칸은 path)가 별도 자료구조로 존재하면 연결성·도달성·정합성은 전부 코드로 판정된다.

§2 · 원칙

오컴의 면도날 세 개

원칙의미베어내는 것
① 의미와 픽셀의 분리 AI 는 의미(숲·마을·호수·밀도)만 다루고, 타일 인덱스는 결정적 코드(생성기+오토타일러)만 다룬다. paint_tiles 좌표 지정, 밑그림 게이트, 타일 어휘 프롬프트 주입
② 다양성은 구성으로 보장 템플릿·킷·부속의 시드 기반 비복원 추출. "골고루"는 확률 모델에게 부탁하는 게 아니라 표본추출기가 보장하는 성질이다. houseVariety 관찰 고리, look_at_houses 되먹임, 다양성 프롬프트
③ 검증은 의미 그리드에서 코드로 연결성(flood fill)·문 도달성·지붕-벽 정합은 의미 그리드에서 O(n) 판정. vision 은 최종 스팟체크로 강등. vision 기반 품질 판정, 완성도 린트의 "0건=미이행"

한 문장으로: 지금까지는 LLM 을 더 잘 감시하는 코드를 쌓았다. 이제는 LLM 이 감시가 필요 없는 일만 하게 줄인다.

§3 · 새 구조

다섯 단 — 프롬프트에서 타일까지

LLM 계약 — 이것이 산출물의 전부다

// "남쪽에 어촌 마을 하나, 집은 다섯 채쯤" →
{
  "op": "village",
  "region": { "x": 4, "y": 18, "w": 28, "h": 14 },   // 생략 시 사용자 선택 영역
  "params": {
    "houses": 5,
    "preset": "fishing",          // 농촌|어촌|산촌 — 파라미터 프리셋일 뿐
    "layout": "spine",            // spine|plaza|scatter
    "fields": 1, "fences": 0.5
  },
  "seed": 271828                    // 생략 시 랜덤 — 재생성 = 새 시드
}

파싱 실패가 곧 검증이다. op 가 카탈로그에 없거나 파라미터 타입이 틀리면 그 자리에서 재요청 — 밑그림 게이트도, 구간 격리도, 좌표 선분배도 필요 없다. 영역 밖 번짐은 기존 clipMapCellsToRegion 하드 클립이 그대로 막는다. 모호한 프롬프트("좀 꾸며줘")는 의도 파서가 후보 오퍼레이터 2–3개를 질문으로 반환한다 — 뭐라도 만들어야 한다는 압력(볼륨 계약·0건 처벌)이 없으므로 되묻기가 자연스러워진다.

§4 · 사람의 설정

재료 슬롯 보드 — 새 칩셋 등록이 5분이 되는 방법

A-3 의 "역할을 사용자 정의 문자열로 개방" 대신, 코드가 소유한 고정 슬롯 12칸을 제안한다. 사람은 역할을 정의하지 않는다 — 슬롯에 타일을 꽂기만 한다.

슬롯은 오퍼레이터가 소비하는 재료의 전체 목록이다. forest 는 ground·ground-alt·tree·bush·flower 를 쓰고, village 는 house-kit·path·plaza·fence·field 를 쓴다. 슬롯이 채워졌는가 = 그 오퍼레이터를 쓸 수 있는가. 43종 자유 어휘, 역할 enum 두 벌, 시맨틱 테이블 9파일이 전부 이 보드 하나로 접힌다. PR #435 의 roleCapabilities 8능력 표는 그대로 슬롯의 정적 속성이 된다 — 슬롯이 곧 능력의 담지자라서 A-3 의 "role: string 개방"이 필요 없어진다.

부트스트랩 — 설정은 1회, 생성은 무한

  • 번들 칩셋 9종: 기존 시맨틱 테이블 346항목을 슬롯 배치로 1회 변환하는 스크립트를 돌린다. 변환 후 테이블은 폐기 대상이 된다.
  • 사용자 칩셋: 임포트 시점에 vision 을 딱 한 번 호출해 슬롯 배치 초안을 제안하고, 사람이 보드에서 확인·교정한다. 생성 루프에서 vision 이 빠지는 대신, 설정 시점으로 한 번만 이동하는 것.
  • 승인 모델 재사용: 슬롯 배치 = origin:"user" — 기존 vocab 신뢰 계약(번들=승인)이 그대로 적용된다.
§5 · 오퍼레이터

카탈로그 — 일곱 개면 시작할 수 있다

오퍼레이터 = 의미 그리드를 쓰는 결정적 함수. 전부 시드를 받고, 전부 ms 단위로 끝난다.

"숲을 울창하게" → forest{density:0.85}. "마을을 만들어줘" → village{houses:4..6}. 사용자 프롬프트의 형용사가 파라미터로, 명사가 오퍼레이터로 떨어진다 — 의도 파서가 할 일은 그 번역뿐이다. 기존 author_house·author_village·34종 템플릿·킷 6종·오토타일 엔진은 오퍼레이터의 내부 부품으로 전부 재사용된다. 버리는 건 "LLM 이 그것들을 직접 지휘하는 층"이다.

§6 · 사례 A

숲 — "뻔한 숲"이 다섯 겹으로 갈라진다

숲이 뻔했던 이유는 취향이 아니라 구조다: 숲 생성기가 없어서 모델이 나무 반복 배치로 수렴했다. 이 절의 오퍼레이터는 이 워크트리에 실제로 구현되어 있다 — src/editor/regionTask/forestWrites.ts(순수 함수·시드 결정적) + 하네스 __oprnRegionTaskHarness.forest(), 불변식 테스트 6개(결정성·영역 경계·수관-밑동 페어·구조물 보호·밀도 단조·오솔길 연결성) 전부 통과. 아래 그림은 전부 실제 에디터 스크린샷이다.

§7 · 사례 B

집과 마을 — 34종은 이미 있다, 뽑는 손이 문제였다

집 모양이 뻔한 건 카탈로그가 없어서가 아니다. houseTemplateCatalog.ts 에 직사각·ㄱ자·T자·ㄷ자·본채+헛간 등 34종이 좌표 데이터로 있다. LLM 이 고르니까 한 종에 수렴했을 뿐이다.

§8 · UX

변형 3장과 슬라이더 — 생성이 공짜여야 가능한 흐름

기존 승인 UX(before/after 게이트 · region 하드 클립)는 그대로 두고, 그 앞에 두 가지가 추가된다.

단계화면비고
1프롬프트 입력 "남쪽에 어촌 마을" — 또는 스튜디오 버튼에서 오퍼레이터 직접 선택영역 미지정 시 사용자 선택 영역 = 암묵 region (기존 계약)
2변형 3장 썸네일 — 시드 3개로 즉시 생성, 클릭으로 선택. "다시" = 새 시드 3장LLM 재호출 없음 · ms 단위라 가능
3파라미터 슬라이더 — density · houses · fields… 선택한 변형 위에서 실시간 조정"더 울창하게" 재타이핑 소멸
4before/after 승인 → 커밋 (undo 스냅샷 1개)기존 게이트 재사용 (PR #13)

부수 효과: AI 없이도 돌아간다. 오퍼레이터+슬라이더는 스튜디오의 일반 도구로도 노출되므로, LLM 미연결 사용자도 "숲 버튼"으로 같은 품질을 얻는다. 의도 파서는 그 위의 편의층일 뿐이다. 수동 편집과의 충돌도 사라진다 — 오퍼레이터 산출은 일반 편집과 동일한 커밋 경로라서, AI 전용 상태가 없다.
