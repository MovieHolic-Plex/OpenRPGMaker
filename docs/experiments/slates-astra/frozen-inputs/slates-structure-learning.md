# Slates 구조 학습 — 성곽 마을을 위한 교정 기록

**Slates 작업의 첫 문서.** 이전 `slates-village-authoring.md`의 단순 주택/50×50 물버들 마을은
성곽 마을의 품질 표준이 아니다. 아래 비교판을 보고 구조를 선택한 뒤 저작한다.
사용자 참고의 건물 밀도·깊은 지붕·돌출층·기단·성벽 단면을 생략하면 같은 칩셋이어도 다른 결과가 된다.

## 학습 자료와 범위

- 사람용 이미지 HTML: `reports/slates-mastery/index.html` — 핵심 교정, 40개 표본, 46개 구역.
- [40개 구조 표본과 비교 이미지](slates-structure-samples.md): 참고 28, 반복 실험 4, 기구 자세 8.
- [46개 구역 전체 재검토](slates-atlas-review.md): 56×22의 1232슬롯 전부를 덮는 번호판과 사용 규칙.
- 기계용 `public/assets/slates/slates-mastery-catalog.json`: 카드별 원본 사각형, 16px 조각 합성 순서,
  v1/v2 구분, 레시피, 픽셀 차이, 검토 상태. `recipeManifest`가 가리키는 파일에 patches의 원본 사각형 인덱스가 있다. `cards[].review`를 먼저 읽는다.
- 원본 그림을 새로 그리거나 참고 스크린샷을 타일로 잘라 쓰지 않았다. 아틀라스 픽셀만 조립한다.
  참고 PNG는 비교의 목표 이미지로만 사용한다.

**모든 구역을 검토한 것 ≠ 모든 가능한 조합을 검증한 것.** 구역 전체를 익혔다고 해도
새 건물을 조립할 때는 아래의 끝/중간/겹침/통행 계약을 확인해야 한다. 미확인 부분을
원본 복원 완료·완성 가변 키트·플레이 가능 콘텐츠로 표현하지 않는다.

## 1. 좌표와 조각의 단위

- v2: 1792×704, 56열, 32px 타일. v1: 1536×704, 48열. 두 원본은 상단 제목 32px 제거 상태.
- 타일 번호는 `floor(sourceY/32) * columns + floor(sourceX/32)`.
- 참고 스크린샷은 원본 픽셀의 2배 확대다. 1088×960 → native 544×480.
- 이번 재조립은 **16×16 원본 사각형과 일부 8×8 세부 사각형**을 32px 칸의 사분면에 합친다. 타일 id 하나만 기록하면
  반칸 위상을 잃는다. 원본 버전, source x/y, width/height, destination x/y, 순서를 기록한다.
- 카드의 `rect`는 참고 문맥에서는 **16px 단위**, `source-object`에서는 **32px 단위**다.
  sourceParts와 definitions의 x/y는 픽셀 단위다. 이 단위를 혼용하지 않는다.
- 홀수 폭/높이 표본을 32px에 넣는 마지막 반칸은 잔디 받침이다. 원본 비교 수치는 이 패딩을 제외한다.

## 2. 건물은 박공 삼각형 하나가 아니다

![돌출집의 참고/재조립/차이](images/slates/mastery/projecting-house.png)

1. 지붕의 폭과 깊이를 나눈다. 폭을 늘리면 사면의 경계가 달라지고, 깊이는 가운데 지붕 면의
   반복 길이가 달라진다. 같은 연산이 아니다.
2. 뒤 지붕 면 → 앞 박공/처마 → 상층 창 → 돌출층 아래 받침 → 1층 벽/문 → 기단을 연결한다.
3. 지붕창/굴뚝은 방향에 맞는 면에 붙인다. 반대 방향 지붕의 같은 크기 조각으로 대체하지 않는다.
4. 연결 상점은 각 몸통/지붕의 높이를 달리하고 접합부를 별도로 만든다. 단독 집을 서로 겹치면
   처마·창·기단이 이웃 집을 절단한다.
5. 꽃 창, 세로 가새, 차양, 간판을 기능과 입구 위치에 맞춰 사용한다. 변형 없이 같은 집 13채를
   반복한 이전 결과는 참고의 건축 조합을 재현하지 못했다.

![지붕의 깊이를 바꾼 실험](images/slates/mastery/roof-deep.png)

이 실험은 특정 문맥의 반복 행만 늘린 것이다. 배경도 같이 늘어나므로 독립 가변 건물 생성기라고
취급하지 않는다. 새 지붕의 T/L자 교차, 임의 폭 변형은 별도의 조립·시각 확인이 필요하다.

## 3. 성벽·성문·탑의 단면

![성벽의 중앙 단면 반복](images/slates/mastery/wall-long.png)

- 뒤쪽 경계/흉벽 → 보행면 → 앞쪽 흉벽 → 수직 벽면 → 바깥 지면의 순서다.
- 600~603, 656~659, 712~715를 모두 같은 바닥처럼 반복하지 않는다. **657/658은 기둥/홈**이다.
- 가로 길이는 중간 단면만 반복한다. 모서리와 양끝, 성문 접합부는 유지한다.
- 내측/외측 모서리와 옆면은 방향별 부재로 만든다. 90도 회전은 광원/투시를 바꾼다.
- 둥근 탑의 원통 음영과 지붕 덮개 폭을 유지하고 세로 몸통만 늘린다.
- 푸른 탑 밑동은 수면 반사다. 풀밭용 기단과 혼동하지 않는다.
- 성문은 두 탑 사이의 공간이다. 문 격자, 아치 아래 그늘, 착지 바닥, 개폐 상태를 따로 둔다.

![성문: 남아 있는 문 내부 오차](images/slates/mastery/gate.png)

**성문 표본은 사용 보류다.** 탑/벽의 결합은 보이지만 격자문 왼쪽과 아치 아래의 조각이 다르다.
일치율이 90%를 넘는다는 이유로 이 표본 전체를 올바른 성문 템플릿으로 등록하지 않는다.
문 내부 조합을 고치고 통행/개폐까지 저작하기 전에는 다음 마을에 자동 적용하지 않는다.

## 4. 기단·계단·그림자는 높이를 설명한다

![중정의 높이와 계단](images/slates/mastery/terraced-court.png)

- 기단은 건물과 지면 사이의 경계다. 회색으로 보이는 원본의 투명 내부를 지면으로 채운다.
- 직선 계단의 반복 디딤판, 양옆 받침, 위/아래 착지, V자 모서리는 다른 부재다.
- 위쪽 공간이 높다는 사실을 벽과 계단이 함께 표현해야 한다. 높은 성벽 위와 성문 아래가
  그림으로 겹쳐 보이더라도 단일 평면의 통과 가능한 길로 합치지 않는다.
- **그림자 568의 실제 RGBA는 (0,0,0,64)**, 다른 그림자 조각도 알파64의 형태별 마스크다.
  밝은 바닥 위에 합성해야 한다. 이전 레시피는 어둡게 보이는 흙을 골라 그늘을 갈색으로 만들었다.
- 픽셀 후보 탐색을 바닥+그림자 공동 비교로 보완했다. 수정한 321개 16px 패치, 이어서 808개 8px 세부 패치를 수정했다. 이 결과도 시각 검토가 필요하다.
  색 오차를 줄이는 계산은 사물의 의미나 올바른 조합을 보증하지 않는다.

## 5. 자연·수면·부두·소품의 경계

![부두·기둥·울타리가 섞인 구역](images/slates/mastery/region-dock.png)

- 숲은 단독 나무의 줄 세우기보다 군락, 가장자리 나무, 열린 틈의 조합으로 만든다.
  수관/밑동을 나누고 문·길·간판을 가리지 않게 한다.
- 풀→모래→젖은 모래→얕은 물→깊은 물의 띠를 유지한다. 오목/볼록 해안은 다른 조각이다.
- 낙수는 시작·면·물보라의 순서이며 강둑 높이와 맞아야 한다.
- 목교는 양쪽 착지와 판자 중심선을 잇는다. 격자 부두의 구멍을 꽉 찬 바닥으로 취급하지 않는다.
- 기존에 부두로 뭉뚱그린 20~23열 아래쪽에는 **울타리·울타리 문·표지판**도 있다.
- 기존의 물/파편 구역 52~55열에는 **판매대, 작은 지붕, 검과 꽃 등 소품**이 섞여 있다.
- 물레방아 2×3 네 자세와 풍차 날개 2×2 네 자세를 각각 확인했다. 설치 축과 수면/건물 접점을
  맞춰야 한다. 도안 네 개를 나열했다고 실제 회전 애니메이션이 구현되는 것은 아니다.

## 6. 성곽 마을 배치에 적용할 순서

1. 성곽 외곽과 성문 방향을 먼저 정한다. 성문→중심 골목→대표 건물로 연결되는 동선을 잡는다.
2. 성벽 내부를 대표 건물, 붙은 상점가, 주거, 작은 정원/묘역, 광장으로 구획한다.
3. 완성 건물의 지붕/기단 범위로 필지를 잡고 골목을 남긴다. 넓은 초지 위에 도로부터 십자로 깔지 않는다.
4. 주도로·골목·문 앞 여백을 다른 폭으로 사용한다. 참고에서 관찰한 반칸 여백을 32px 그리드에서
   구현할 때에는 픽셀 조합과 칸 단위 충돌의 차이를 의식한다.
5. 기단·계단·벽의 그림자를 연결하고 마지막에 나무·차양·간판·벤치·우물을 배치한다.
6. 골목의 연결, 문 앞 접근, 성벽 밖/안, 계단 위/아래를 각각 확인한다. 전체 연결성 검사는
   시각적 높이/밀도/건축 품질 검토를 대체하지 않는다.

## 7. 저장된 관찰 자료와 다음 작업의 계약

- 프로젝트 `rpg-zzu-slates32-38e6`, 새 칩셋 `slates_mastery_32`.
- 4개 관찰 맵: `slates_mastery_architecture`, `slates_mastery_fortification`,
  `slates_mastery_terrain`, `slates_mastery_detail`.
- 40개 관찰 스탬프는 모두 **문맥 포함/고정 크기**다. 원본 바닥이 들어 있으며 통행은 관찰용으로 막았다.
  성문은 이름에도 사용 보류를 표시한다. 실전용 구조 키트로 오인하지 않는다.
- 기존 6개 맵과 시작 맵/시작 위치는 보존한다. 자료 추가가 기존 마을을 재설계했다는 뜻이 아니다.
- 생성기: `scripts/content/build-slates-mastery.mjs`, `build-slates-mastery-report.mjs`.
  수동 규칙: `slates-mastery-specs.mjs`, `slates-mastery-notes.mjs`.
- 저장/재로드 근거: `verify-shots/slates-mastery/persistence.json`, `local-persistence.json`, `SUMMARY.md`.
- 다음 작업 전 최신 LegacyDb root를 `read-slates-project.mjs`로 읽고 SHA 조건 저장한다.
  기존 입력 스냅샷을 최신인 것처럼 재사용하지 않는다.

아직 완료로 말하면 안 되는 것: **정확한 성문 내부 복원, 임의 T/L자 건물 생성, 모든 성벽 방향의
자유 결합, 건물 없는 순수 오브젝트 분리, 다층 보행, 문 개폐/수문/애니메이션, 성곽 마을 전체의 저작.**
이를 요청받으면 해당 조립부터 구현하고 실제 맵으로 검토한다. 이 문서는 그 작업을 위한 근거다.

## 숫자 비교를 재현할 때

1. `prepare-slates-patch-analysis.mjs`로 원본/참고 픽셀을 측정용 바이너리로 내보낸다.
2. `g++ -O3 -std=c++17 scripts/content/slates-patch-analysis.cpp -o /tmp/slates-patch-analysis`로 컴파일한다.
3. 바이너리에 `output/slates-mastery/patch-input.bin output/slates-mastery/patch-matches.txt`를 전달한다.
4. `apply-slates-patch-analysis.mjs` → `prepare-slates-fine-analysis.mjs`.
5. 같은 C++를 `-DSLATES_PATCH_SIDE=8`로 별도 컴파일해서 fine-input.bin → fine-matches.txt를 만든다.
6. `apply-slates-fine-analysis.mjs` → `build-slates-mastery.mjs` → `build-slates-mastery-report.mjs`.

이는 원본 사각형 후보를 찾는 수치 분석이다. 최소 색 오차를 골라도 의미가 다른 조각을
고를 수 있으므로 자동 결과를 완성 구조로 인증하지 않는다. 확정된 입력 레시피는 public/assets에 보관한다.
