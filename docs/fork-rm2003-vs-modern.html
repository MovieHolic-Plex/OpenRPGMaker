조건 분기,
RM 리듬 × 모던 조건

“RM2003처럼 하면 조건이 빈약해지나?” — 아니다. 편집 표면(어디서 고치나)과 조건 엔진(무엇을 걸 수 있나)은 다른 축이다. 모던 AI 편집기는 리듬은 RM, 표현력은 확장이 정답이다.

골격 조건 창 / 본문 리스트 엔진 Condition AST + 복합식 AI 자연어 → 구조화 조건 레포 fork + Condition union 상태 P0–P2 implemented
두 축 RM2003 원작 분리 원칙 지금 레포 모던 확장 AI 파이프라인 결론

3. 왜 이 분리가 강한가

📐

한 창 한 책임

조건 창은 조건만.
본문 창(리스트)은 시퀀스만.

🧱

중첩이 자연스럽다

fork 안 fork, 선택지 안 fork.
리스트 들여쓰기가 스케일됨.

🧠

멘탈모델이 안정

선택지와 같은 철학.
배우면 전 커맨드에 전이.

🛠️

본문 편집 도구 재사용

복사/붙여넣기/드래그/단축키가
리스트 한곳에서 동작.

💣

미니 IDE 함정 회피

다이얼로그 안 조잡한
then/else 에디터를 안 키움.

🤖

AI와도 잘 맞음

AI는 조건 AST + 본문 커맨드를
분리 생성하면 됨.

4. 지금 이 레포 위치

항목 RM2003 rpg-zzu 현재 판정
데이터 모델 IF / then / else 블록 fork + condition + then + else? 정렬됨
단일 조건 종류 스위치·변수·아이템… 스위치·변수·셀프·배우·아이템·골드·타이머 + 시간대·계절·활동·호감 이미 더 넓음
복합 조건 사실상 단일 / 중첩 IF 단일 Condition (AND/OR 그룹 없음) 확장 여지
조건 편집 UX 라디오 + 라벨 필드 라벨 필드 스택으로 개선 중 진행 중
본문 편집 위치 메인 리스트 들여쓰기 다이얼로그 미니 리스트 + 메인 리스트 공존 RM과 어긋남
else 생성 체크박스 한 개 버튼 “그 외 분기 추가” 의미는 같음
AI 조건 작성 없음 툴/내러티브 플래그는 일부, 자연어→AST는 약함 다음 단계
⚠️

lagged 한 것 = 표현력이 아니라 표면

Condition vocabulary는 이미 꽤 모던하다. 어색함의 본체는 then/else 본문을 다이얼로그 안에 끌어둔 편집 표면과 복합식/AI 작성 레이어 부재다.

5. 모던 AI 편집기라면 조건을 어디까지

확장할 것은 “다이얼로그 크기”가 아니라 “조건 엔진”이다.

  • npcActivity 스케줄
🎒

  • 소지 여부 → 수량 비교
  • 레벨/직업/장비 슬롯
  • 골드 비교 (이미 있음)
🤖

AI 작성NEXT

  • 자연어 → Condition AST
  • 미선언 플래그 제안
  • 빌더로 검수 후 커밋
🔎

디버그 표면

  • 현재 세션 TRUE/FALSE
  • 실패 원인 한 줄
  • explain_event 와 연결

복합 조건 트리 예시

ALL  // 모두 참이어야 then
├─ switch  0001:문 열림  == ON
├─ timePhase  night
└─ ANY
   ├─ friendshipAtLeast  민수 ≥ 100
   └─ item  낡은 열쇠  소지

자연어: “문이 열렸고 밤이며, 민수 호감 100 이상이거나 낡은 열쇠가 있을 때”

7. 결론 · 로드맵

✅ 이렇게 간다

  • 다이얼로그 = 조건 빌더 + else 체크만
  • then/else 본문 = 메인 리스트 들여쓰기
  • Condition 에 all / any / not 그룹 추가
  • 의미 조건 유지·확장 (호감, 시간, 퀘스트, 플래그)
  • AI: 자연어 → AST → 빌더 검수
  • 미리보기: 현재 세션 TRUE/FALSE + 실패 원인

❌ 이렇게 안 한다

  • 조건을 늘리자고 본문 편집을 다이얼로그로 끌어오기
  • RM 조건 종류로 표현력 후퇴
  • 문자열 조건 인터프리터
  • 미니 리스트와 메인 리스트 이중 편집 유지
  • “모던 = 창이 크고 버튼이 많음”

우선순위 제안

P0  fork 다이얼로그에서 then/else 본문 편집 제거 (요약/개수만)
     else = 체크박스 “그 외 처리”
     메인 리스트 마커 강화 (: 참일 때 / : 그 외 / : 분기 종료)

P1  Condition 그룹 (all/any/not) + 빌더 트리 UI
     세션 평가 미리보기 TRUE/FALSE

P2  AI 자연어 → condition AST 툴
     수량/퀘스트 stage/영역 조건 vocabulary 확장
🎯

최종 한 줄

모던 AI 편집기일수록 조건은 더 다양해야 한다. 다만 다양해지는 것은 Condition 엔진이지, 다이얼로그 안의 then/else 미니 편집기가 아니다. RM의 편집 리듬을 지키고, 조건 vocabulary만 미래로 밀어라.
