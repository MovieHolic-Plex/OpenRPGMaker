AI 어시스턴트가
일하는 방식

에디터 안의 AI는 말로 맵을 고치는 조수입니다. 직접 프로젝트를 덮어쓰지 않고, 도구를 빌려 써 보고 → 제안 카드로 보여 주고 → 당신이 수락할 때만 반영합니다.

한 문장으로 기억하면 됩니다.

당신 말 → 모델이 도구 고름 → 모의 시공(draft) → 제안 카드 → 수락 시에만 저장
한 턴의 흐름 두 가지 입구 계획·실행·검토 도구 골라내기 안전장치 비유 자주 묻는 점

한 턴이 흐르는 순서

채팅에 한 마디를 넣으면, 대략 아래 순서로 움직입니다.

당신이 요청한다

채팅에 자연어를 쓰거나, 맵에서 영역을 고른 뒤 “이 안에 호수 만들어 줘”처럼 지시합니다.

채팅 패널 영역 작업

컨텍스트를 챙긴다

지금 맵, 선택 영역, 타일셋, 대화 히스토리 등을 묶어 시스템 프롬프트와 함께 모델에 넘깁니다.

contextBuilder viewport

쓸 수 있는 도구만 연다

등록된 도구는 100개가 넘지만, 한 번에 전부 보이는 건 최대 40개입니다. 지금 UI 모드와 말 속 키워드로 “관련 묶음”만 고릅니다.

domain 필터 PIN + MAX 40

도구를 호출한다 (여러 번 가능)

모델이 fill_region, build_house_kit, place_npc 같은 함수를 부릅니다. 실패하면 이유를 다시 받아 스스로 고칩니다.

function calling 자가 수정 루프

진짜 저장이 아니라 draft에 쌓는다

쓰기 도구는 우선 로컬 초안(draft)에만 적용됩니다. 다음 도구 호출은 이 초안을 기준으로 “이미 벽이 있다”를 볼 수 있습니다. 실제 프로젝트 저장소는 아직 안 건드립니다.

dry-run / draft

제안 카드 → 당신이 결정

요약·미리보기가 뜬 카드에서 적용 또는 버리기를 고릅니다. 적용할 때만 에디터 프로젝트에 커밋되고, 되돌리기(undo) 체크포인트도 잡힙니다.

수락 게이트 layout 검증

요청을 넣는 두 가지 입구

같은 엔진이지만, 입구에 따라 “어디에 작업할지”와 안내문이 달라집니다.

① 채팅 패널

평소 쓰는 AI 대화창
  • 프로젝트 전반 요청 (“마을 하나 만들어 줘”)
  • 맵·이벤트·DB 등 UI 모드에 맞춰 도구 묶음 변경
  • 끝나면 제안 카드로 검토

② 영역 작업

맵에서 사각형을 고른 뒤 지시
  • 선택 영역 밖으로 나가지 못하도록 클립
  • 의도 가이드·소품 힌트가 메시지에 자동 첨부
  • 적용 전 before/after 확인 게이트

계획 → 실행 → 검토 (세 단계)

설정에 감독 모델과 라이트 모델이 나뉘어 있으면, 한 턴을 세 단계로 나눕니다. 같으면 그냥 한 모델이 끝까지 처리합니다.

Phase 1

계획 (Plan)

무엇을 어떤 순서로 지을지 설계합니다. 공간 추론·스펙 작성에 집중.

감독 모델 · model
Phase 2

실행 (Execute)

쓰기 도구를 연쇄 호출해 draft에 시공합니다. 반복 작업에 유리한 쪽.

라이트 모델 · liteModel
Phase 3

검토 (Review)

빠진 게 없는지 확인. “재실행:”이면 실행 단계 한 번 더 수리 후 최종 검토.

감독 모델 · model

영역 작업·일부 보조 모달은 처음부터 라이트 경로 비중이 큽니다.

도구를 어떻게 골라 보여 주나

모델이 “집이 필요해”라고 느껴도, 그때 열려 있지 않은 도구는 부를 수 없습니다. 그래서 노출 규칙이 품질을 좌우합니다.

전체 레지스트리~140개
→
deprecated 제외옛 이름 숨김
→
도메인 교집합map / tile / event…
→
PIN 우선 + 40개 상한핵심 도구 보장

도메인은 어디서 오나

항상 켜지는 core(요약·맵 생성·타일 조회 등) + 지금 열린 UI(타일 팔레트, 이벤트 에디터…) + 말 안의 키워드(“집”, “NPC”, “길”…) + 직전 턴에 쓴 도메인입니다.

자주 쓰는 정공법 (치트 시트)

paint_road흙길 / 모래길

왜 바로 맵이 안 바뀌나 — 안전장치

실수로 맵이 날아가지 않도록, “시공”과 “커밋”이 분리되어 있습니다.

🛡️

쓰기 = 제안, 수락 = 커밋

도구 결과는 draft에 쌓이고 제안 카드로만 보입니다. 당신이 적용을 누르기 전까지 에디터 store(실제 프로젝트)는 그대로입니다. 재료 어휘 합의·강한 클러스터 규칙 등은 자동 적용을 막고 명시 수락을 요구하기도 합니다.

🔍

적용 전 검증

배치 후 레이아웃 검증(물 위 소품, 불완전한 나무, 요청한 나무가 없는지 등)이 영역 작업 적용·채팅 제안 수락 경로에 걸려 있습니다. 통과하지 못하면 반영을 막거나 경고합니다.

📝

활동 로그

매 턴의 대화·도구 호출 요약은 브라우저 localStorage 링 버퍼에 남고, 개발 모드에서는 output/ai-activity/에도 기록됩니다. API 키는 로그에 넣지 않습니다.

한 장으로 이해하는 비유

건축 현장으로 바꿔 말하면 이렇습니다.

당신은 건축주, AI는 시공 팀

건축주가 “남쪽에 연못, 옆에 오두막 하나”라고 말하면, 감독(감독 모델)이 도면을 잡고, 현장 팀(라이트 모델)이 도구(삽·망치 = fill_region, build_house_kit…)로 목업을 쌓습니다.

목업은 아직 가설 구조물입니다. 감독이 “문 빠졌어, 재시공”이라고 하면 한 번 더 고치고, 마지막에 건축주 앞에서 제안 카드를 펼칩니다. 승인 도장을 찍기 전엔 진짜 마을 지도가 바뀌지 않습니다.

자주 궁금해하는 점

동작이 “이상해 보일 때” 참고용입니다.

왜 내가 말한 도구를 안 쓰고 다른 걸 쓰나?

그 도구가 이번 턴에 노출 목록(최대 40)에 안 들어갔을 수 있습니다. 키워드·UI 모드·PIN 우선순위에 밀리면 모델은 “열려 있는 것 중 가장 그럴듯한” 대체 경로로 갑니다.

원형 호수를 시켰는데 네모가 됐다?

fill_region 기본 shape는 사각형입니다. 원형/둥근 요청은 shape: "circle"(또는 ellipse)이어야 합니다. 시스템 프롬프트에도 이 규칙이 들어 있습니다.

“박스”를 시켰더니 보물상자나 잡소품이 나왔다?

장식용 나무/과일 박스는 place_props + 해당 재료 라벨, 열면 아이템이 나오는 보물상자는 place_chest입니다. 말만 “상자”면 혼동하기 쉬워 영역 가이드에 구분이 박혀 있습니다.

외부 AI(코딩 에이전트)가 이 채팅을 조종할 수 있나?

네. 브리지 MCP(npm run mcp:assistant)로 에디터 안의 채팅 패널에 메시지를 보내고, 사람이 화면에서 스트림·제안을 같이 볼 수 있습니다. 프로젝트 파일을 헤드리스로 직접 쓰는 MCP와는 별개입니다.

대화 기록은 프로젝트 파일에 들어가나?

아니요. 대화 히스토리는 브라우저 localStorage에만 있고, 프로젝트 JSON·플레이 세션 상태와 분리됩니다.

재료(타일)를 “합의”한다는 게 뭐지?

새 타일 조합을 앞으로 바로 쓰자고 제안하는 경우가 있습니다(propose_tile_vocabulary 또는 시공 후 목업 확인). 이때는 자동 적용되지 않고, 당신이 수락해야 “합의된 재료”로 남습니다.
