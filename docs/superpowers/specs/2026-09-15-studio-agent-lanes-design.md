## 1. 문제 — 사용자 판정 + 실측

스튜디오(`aiStudioShell.ts`, 1440×900 실측)는 **"AI가 할 수 있는 것"의 카탈로그**다. 화면의 단위가 '기능'이라 전문가가 원하는 "이번 한 수를 어디에, 무엇으로, 어디까지"를 다룰 자리가 없다. 도구 레지스트리는 오늘 **260개**(`allTools().length`, 2026-09-15 실측)이고, 덱 카드는 눌러도 입력줄에 문장을 채우는 것이 전부다. 1차 제안 목업은 `output/evidence/studio-agent-lanes/10-mock-a-workbench.png` 로 남겨 둔다.

사용자 요구는 두 문장으로 정리된다.

> "굉장히 많은 AI 들을 쓸 수 있게 해야할거같음 … 맵당 서로 다른 에이전트들을 쓸 수 있게 하고, 일을 병렬로 할 수 있게끔 해야 맞지않나."

1차 제안(A안 「작업대」: 대상 지정 · 스키마 폼 인스펙터 · 지점별 채택)은 **기각**됐다. 단위를 '도구'가 아니라 **에이전트 레인**으로 잡는 것이 이 문서의 설계다.

### 2.2 못 함 (병목, 중요한 순서)

| 못 함 | 왜 — 코드 |
|---|---|
| **레인을 따로 적용할 수 없다** | 적용 게이트가 **프로젝트 전체 내용 등가**다: `proposalContent(current) === base.content`(`applyChangesetToStore.ts:239`)가 아니면 `stale-base`("기준 프로젝트가 변경되었습니다", `:300`·`:370`). 레인 A 를 적용하면 프로젝트가 바뀌므로 레인 B 는 그 순간 거절된다. 게다가 명령 하나가 병합 하나·카드 하나다 — 병합은 `Promise.all` 이 끝난 뒤 한 번(`aiPiAgentCommand.ts:315`), 검토 카드도 하나(`:438` 주석) |
| **레인을 따로 시작·중단·재시도할 수 없다** | 명령 하나 = `surface.signal` 하나. 중단도 전체, 재시도도 전체 |
| **레인별 모델이 없다** | 명령층이 항상 전역 Deep 역할을 넘기고(`roleModels: { deep, writer }`), 팀 모드에서 팀원 `model` 은 `request.roleModels?.deep` 가 있으면 **무시된다**(`piTeamRuntime.ts:166`) — 결과적으로 한 명령의 모든 에이전트가 같은 모델 |
| **동시성 상한이 없다** | `maxConcurrent`·세마포어류가 `src/ai`·`scripts/lib` 어디에도 없다. 실제 천장은 제공자·OAuth 토큰 수명. 제공자는 둘뿐이다(`ohMyPiProviders.ts`: Google Antigravity, OpenAI Codex) |
| 맵 사이 연결이 레인 밖 | 레인 A 가 레인 B 의 맵으로 transfer 를 만들면 묶음 밖이라 spill 로 버려진다(`mapBundleSpill`) |

## 3. 설계

### 3.1 단위: 레인 = 에이전트 × 맵 묶음 × 지시 × 모델

- 병렬의 단위는 **묶음**으로 고정한다. 묶음 = `mapBundleIds` 가 주는 맵 + 그 실내 + `mapTree` 부분 트리.
- 같은 맵에 레인 둘을 동시에 붙이는 것은 지금 설계대로 **락으로 막는다**(`teamAssignments.ts` 의 in-flight 락을 레인 매니저로 승격).
- 시공 → 장식 같은 순차 작업은 같은 묶음 위에 레인을 **순서대로 세우는 파이프라인**으로 표현한다.

### 3.2 화면 — 「에이전트 운영실」

목업: `output/evidence/studio-agent-lanes/20-mock-lanes.png`

| 영역 | 지금 | 제안 |
|---|---|---|
| 좌 — **배정판** | 장면 레일(맵 이름 목록) | 맵 행마다 배정된 에이전트·모델·상태·대기열. 실내는 부모 묶음의 구성원. 「＋ 새 레인」과 「팀장에게 맡기기」가 나란히 |
| 중앙 — **모니터** | 실제 캔버스 1장 | 선택 레인 크게 + 나머지 실행 중 레인 라이브 썸네일. 레인 초안을 고스트로 겹쳐 보기 |
| 우 — **레인 인스펙터** | 조수 열(채팅) | 그 레인의 과정(툴 인자까지)·에이전트·모델·예산·묶음. 「이 레인 중단」 「지시 고쳐 다시」 「모델 바꿔 다시」. 결과가 오면 **이 레인만** 적용·버리기·검수 붙이기 |
| 하 — **레인 보드** | 도구 덱(레지스트리 260개) | 레인 표 + 에이전트 명단(지금의 `aiTeamPanel` 을 여기로) + 적용 기록 + 활동. 도구 카탈로그는 이미 있는 「모든 도구」 모달로 퇴장(`StudioShell.onUseTool` 재사용) |
| 컴포저 | 한 문장 → 전체 적용 | 「새 레인」 폼: 묶음 · 에이전트 · 모델 · 지시 · 자율성/예산 |

배정 제안 카드는 새 물건이 아니다. 지금도 있는 **Ultrabrain 읽기 전용 계획 턴**(`aiPiAgentCommand.ts:255`, `readOnly: true`)의 출력을 구조화(JSON)해 사람 승인 앞단에 세우는 것이다. 지금 `/pi team` 은 그 승인 카드 없이 팀장 LLM 이 배정을 바로 시작한다 — 행은 보드에 사후에 뜬다.

### 3.3 채팅 — 없애지 않는다. 받는 이(receiver)를 나눈다

목업: `output/evidence/studio-agent-lanes/30-mock-chat.png`

핵심 사실: **채팅은 이미 하나이고, 스튜디오는 그 하나를 재부모화해서 쓰고 있다.**

- `StudioShell.attach(panel, pieces)` 가 `historyLogMount` 와 `commandBar` 를 받아 스튜디오 격자에 꽂는다(`aiStudioShell.ts:41~55`).
- 로그 배치는 단일 상태 함수 `mountLog()` 하나가 정한다 — 슬롯은 `history`/`glass` 둘뿐이고 `panel.dataset.logSlot` 으로 노출된다(`aiChatPanel.ts:2885~2894`). 스튜디오가 열려 있으면 `history` 슬롯이다.

따라서 레인 스레드는 **새 채팅 표면이 아니라 같은 로그의 필터**다.

우측 열은 **하나**다. 받는 이가 감독이면 지금의 대화, 레인이면 그 레인의 스레드에 인스펙터(과정·지시·결과 + 에이전트·모델·예산·묶음)가 붙는다 — 목업 20(레인 인스펙터 상태)과 30(감독/레인 스레드 상태)은 **같은 열의 두 상태**다.

| 층 | 받는 이 | 무엇을 하는가 |
|---|---|---|
| ① 감독 채팅 | 감독(= 지금의 조수) | 질문 · 계획 · 배정. 로그·컴포저는 지금 그대로. 자율성 다이얼은 여기의 노브 |
| ② 레인 스레드 | 그 레인 | 보드에서 레인을 누르면 컴포저의 받는 이가 그 레인으로 바뀐다. 후속 지시 = 그 묶음 위의 이어 달리기 |
| ③ 도킹 패널(표준·초보) | 감독만 | 같은 로그·같은 컴포저. 레인 보드는 지금처럼 로그 안 카드 한 장으로 요약 |

- 「감독에게 한 말」 = 질문 / 계획 / 배정 제안. 「레인에게 한 말」 = 그 묶음 위의 후속 실행.
- 후속 실행은 **맥락을 문자열로 다시 실은 새 실행**이면 지금 워커로 된다(§2.2 마지막 행). 워커에 레인 세션을 살려 두는 진짜 다중 턴은 P2 — OAuth 토큰 잔여 수명과 함께 다뤄야 한다.
- `/pi team` 은 「감독에게 팀장 자동 배정을 켜고 말하는 것」과 같아진다(버튼으로 흡수).

### 3.4 엔진 변경 (P0, UI 없음)

1. **묶음 단위 적용.** 적용 판정을 프로젝트 전체 등가에서 **묶음 키 등가**로 내린다: 레인 출발 사본과 최신 프로젝트를 비교해 그 묶음의 키가 안 바뀌었으면 최신 프로젝트 위에 재병합(`mergeMapBundles` 의 `base` 의미론 재사용), 바뀌었으면 "이 묶음이 바뀌었다"로 재실행을 유도한다. 전역 `stale-base` 는 묶음 밖 변경에만 남긴다.
2. **레인 매니저.** 레인마다 독립 `signal`·진행·검토·적용. 오늘의 `surface.signal` 하나를 레인 단위로 쪼갠다.
3. **레인별 provider/model.** 팀원 `model` 을 존중한다 — `roleModels.deep` 이 있을 때 무시되는 `piTeamRuntime.ts:166` 의 조건을 레인 매니저에서는 뒤집는다.

## 4. 단계

1. **P0 — 엔진, UI 없음.** 위 §3.4 셋. 검증은 헤드리스 CLI 로 맵 3 · 모델 2종 · 적용 순서 뒤섞기(레인 A 적용 → 레인 B 적용)로 커밋 게이트 통과를 본다.
2. **P1 — UI.** 배정판 · 레인 보드 · 레인 인스펙터 · 새 레인 폼. 팀 모드는 버튼으로 흡수.
3. **P2 — 규모.** 제공자별 동시 상한과 대기열, 시작 전 토큰 잔여 수명 검사, 워커 쪽 한 스트림 멀티플렉스로 브라우저 연결 제한 해소, 레인별 토큰·비용 표시, 워커 세션(진짜 다중 턴).
4. **P3 — 협업.** 검수 지적 → 수정 레인 자동 생성, 맵 간 연결 레인, 팀원 명세의 프로젝트 저장.

## 5. 한계 (정직하게)

- "굉장히 많은 AI" 중 **에이전트 수**는 프롬프트·모델 조합으로 얼마든지 늘지만, **제공자 다양성**은 오늘 둘(Antigravity·Codex)이다. 다른 회사 모델을 레인에 쓰려면 제공자 추가가 별도 작업이다.
- 현실적인 동시 레인 수는 제공자 상한과 OAuth 토큰 수명 때문에 **4~6 에서 시작**해 늘려 봐야 한다. 목업의 "동시 실행 상한 4"는 **오늘 사실이 아니라 P2 에서 넣을 값**이다.
- 브라우저는 HTTP/1.1 동시 연결 6개 제한이 있어, 레인이 7개를 넘으면 스트림이 줄을 선다(팀 모드는 한 스트림이라 안 걸린다).

| 레인 보드(하) | 덱의 「레인」 탭 유지(전체 표 + 새 레인 폼) |
| 채팅은 하나 + 받는 이 | 좌 레일 「채팅」 절이 스레드 목록(감독 + 레인별)이고, 고른 스레드가 오른쪽 열에 산다. 로그·컴포저는 감추기만 하고 파괴하지 않는다 |

추가 발견과 수정:
1. **레인이 화면보다 오래 살아야 한다** — 장면 추가가 에디터 재렌더를 일으켜 스튜디오 셸이 새로 만들어지고, 셸 소유의 레인 매니저가
   함께 사라졌다(실표면에서 전체 2 → 전체 1). src/editor/panels/aiLaneSession.ts 모듈 싱글턴으로 고정.
2. **빈 프로젝트의 묶음 함정** — 맵트리 루트가 첫 맵이라 「새 장면」 이 그 맵의 자식으로 붙고, 레인 출발 뒤에 장면을 더하면
   그 레인의 묶음이 바뀐 것으로 판정되어 적용이 거절된다(가드는 옳고 순서가 문제). 적용 거절 사유는 좌 레일 조수 절에 뜬다.
3. 셸은 루트 children 을 replaceChildren(...) 로 다시 박는다 — 좌 레일을 넣을 때 그 줄도 함께 고쳐야 한다.
