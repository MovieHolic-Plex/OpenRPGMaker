Adversarial Review · Shop Core · RPG ZZU

상점은 이 에디터의 핵심이다.
그래서 더 가혹하게 뜯는다.

상점(Shop Processing)은 RPG ZZU의 유일한 양방향 경제 게이트다. 골드·인벤토리·우정 할인·계절 재고·수량을 한 번에 건드리며, 실패가 곧 "돈 복사" 혹은 "팔 수 없음"으로 직결된다. 본 리뷰는 ShopCommand 타입부터 resolveShopStock·commandCatalog·playSceneShop·commandBodyCommerce까지 데이터·에디터·런타임·경제를 관통해 적대적으로 검증했다. 전제는 하나다: 플레이어는 상점을 가장 먼저 악용한다.

Verdict — SHIP WITH GATES. 코어 흐름은 견고하다(타입·인터프리터·거래 원자성·lint). 그러나 P0 3건이 경제 무결성과 문서 정합성을 깨뜨린다: 상인 소지금 0의 "무제한" 허위 문서, 우정/계절 할인 하에서의 매입-매도 차익, 수량 입력 우회. 이 3건만 막으면 상점은 핵심 기능으로 출하 가능하다.

1. 범위 & 방법

대상은 src/project/types/events.ts의 ShopCommand / ShopStockEntry / ShopType / ShopMessageType / SocialShop, src/editor/panels/eventEditor/commandBodyCommerce.ts의 shopBody 전체, src/player/interpreter/commandCatalog.ts·interpreter/resume.ts의 shop pause/resume, src/player/playSceneShop.ts / playSceneShopDom.ts의 거래 원자성, 그리고 src/project/shopStock.ts의 resolveShopMerchantGold / resolveSocialShopPriceMultiplier / resolveShopStock이다. 비교군은 inn 커맨드(여관)이며, 검증 기준은 타입 완결성·마이그레이션·lint·reference validation·실제 DOM 렌더까지다.

가정
상점은 "신뢰된 저작자"가 배치하되 "불신된 플레이어"가 악용한다. 저작자는 실수하고, 플레이어는 집요하다.
비교
inn은 branchOnNotEnoughGold로 실패 분기를 제공한다. shop은 성공 분기(branchOnTransaction)만 있어 비대칭이다.
경제
buy price는 할인 가능, sell price는 고정 floor(price/2). 이 비대칭이 차익의 씨앗이다.

3. 데이터 모델 — 이중 기록이 부른 모호성

타입 요약

type ShopType = "normal" | "buyOnly" | "sellOnly"
type ShopMessageType = "welcome" | "business" | "direct"

type ShopCommand = {
  kind: "shop"
  itemIds: ItemId[]          // ← 레거시 단순 목록
  allowSell?: boolean        // ← 레거시 호환
  quantityMode?: "single"|"select"
  shopType?: ShopType
  messageType?: ShopMessageType
  merchantGold?: number      // 생략 시 100G
  stock?: ShopStockEntry[]   // 있으면 itemIds 대신 사용
  branchOnTransaction?: boolean
  transactionBranch?: Command[]
}
type ShopStockEntry = {
  itemId: ItemId
  seasons?: Season[]         // 비우면 사계절
  priceOverride?: number
  priceBySeason?: Partial<Record<Season,number>>
}
판정 — 이중 기록(dual source)
itemIds와 stock이 동시에 존재한다. 런타임은 stock이 있으면 그걸 쓰고, 에디터는 commitItems에서 stock을 itemIds에 맞춰 prune만 한다. 수동 JSON 편집으로 stock에 없는 id를 넣거나 itemIds 없이 stock만 두는 케이스는 에디터가 복구하지 않는다. stock의 아이템이 itemIds에 없으면 목록엔 안 보여도 Catalog에선 팔린다 — 저작자가 "왜 안 보이지?"를 겪는 경로다.

검증 현황

지점검사판정
commandReferenceValidationitemIds·stock[].itemId 존재 검사통과
projectLintreference + roundtrip통과
shapeSeason enum / price 음수 / priceBySeason 키미검증 — 값 범위는 stockEntryPrice에서 truncate만
migrationV1/V2→V3 shop 필드 기본값 주입없음 — newCommand("shop")만 기본값, 구 저장본은 shape 통과 시 보정 없음
shopType vs allowSell
shopTypeValue()는 shopType을 우선하고 allowSell은 무시한다. 에디터는 둘을 동기화해 쓰지만(withShopType), 수동 편집으로 shopType: "normal", allowSell: false 같은 모순을 만들면 타입은 normal로 동작하고 allowSell은 거짓말을 한다. lint가 잡지 않는다.
P0 예고 — merchantGold 0
패널 힌트는 "0이면 무제한"이라고 쓰지만, 런타임은 resolveShopMerchantGold(0) === 0으로 클램프하고 handleShopTransaction은 merchantGold < payout에서 그대로 차단한다. 문서는 무제한, 코드는 차단 — 둘 중 하나가 거짓말이다. 현재 코드는 차단이 맞고 문서가 고쳐져야 한다. 상점이 sellOnly인데 merchantGold 0이면 "팔 수 없는 상점"이 된다.

잘한 점
dual list + 종류/검색 필터, DB n개 카운트, 프리셋(잡화점 등), 계절 칩, 가격 오버라이드 플레이스홀더(DB 50)까지 상점 저작 동선이 완결이다. 프리셋이 matched로 DB 유무를 검증해 빈 프로젝트에서도 안전하다.

간극 3건

G1 — 0=G 무제한 허위
상인 소지금 힌트가 "0이면 무제한"이라고 쓰지만 실제는 0이 곧 예산 0이다. sellOnly 상점에 0을 넣으면 플레이어가 아무것도 팔 수 없는 함정이 된다. 문서와 코드 중 하나를 고쳐야 하며, 코드는 차단이 맞다 — 힌트를 고쳐라.
G2 — 빈 상점의 빈 껍데기
itemIds==0이면 상단 배너가 뜨지만, 런타임은 메뉴(구입/판매/취소)를 그대로 보여주고 목록엔 "No goods."만 띄운다. 플레이어는 "상점인데 왜 아무 것도 없지?"를 겪는다. 최소한 buyOnly/sellOnly 분기에서 빈 목록일 때 메뉴 자체를 비활성화하거나 안내 분기로 보내야 한다.
G3 — 실패 분기 없음
여관은 branchOnNotEnoughGold로 "돈이 없을 때"를 갈라내지만, 상점은 성공 분기(branchOnTransaction)만 있다. 골드 부족·상인 예산 부족으로 거래가 막혔을 때 저작자가 갈 길을 잃는다. shop에도 branchOnFailedTransaction 혹은 최소한 실패 메시지 오버라이드가 필요하다.
사소하지만 거슬리는 것
stockEditor의 가격 입력 플레이스홀더는 DB 가격을 보여주지만, 계절칩을 하나도 안 고르면 "사계절 판매"로 해석된다는 힌트는 작게 한 줄이다. 초보 저작자는 "계절 안 고르면 안 팔리는 줄" 안다. 칩 영역에 사계절 토글이 명시적으로 보였으면 좋겠다.

5. 런타임 — pause/resume와 원자적 거래

인터프리터 계약

catalog: pause("shop", {
  kind:"shop", itemIds, items?, shopType,
  merchantGold, branchOnTransaction
})
  where items = resolveShopStock(
    project, session, command, currentEvent)

resume: advanceResume(pending==="shop", value)
  if command.branchOnTransaction && value===true
    pushFrame(transactionBranch)
  else pc += 1

scene: playShop(step) → Promise<boolean>
  resolve(true)  // ≥1 거래 성공
  resolve(false) // 구경만 하고 닫음
견고한 점
거래 분기는 value === true일 때만 발동한다. transactionCompleted 플래그는 handleShopTransaction이 ok를 반환한 뒤에만 true가 되므로, 실패(골드 부족·상인 예산 부족·보유 부족)는 분기를 태우지 않는다. 의도대로다.

거래 원자성

handleShopTransaction(scene,item,mode,qty,merchantGold)
  qty = max(1, floor(count)||1)
  if mode==="sell"
    if owned < qty → fail (보유 부족)
    payout = sellPrice(item)*qty // floor(price/2)
    if merchantGold < payout → fail (상인 예산)
    changeItem("-=",qty) + changeGold("+=",payout)
    return {ok, merchantGold: mg - payout}
  else // buy
    cost = item.price * qty
    if session.gold < cost → fail
    changeGold("-=",cost) + changeItem("+=",qty)
    return {ok, merchantGold: mg + cost}
검증
changeGold는 Math.max(0, next)로 음수 방지, changeItem은 transitionItemState로 charge까지 갱신한다. 실패 경로는 syncRuntimeState()만 하고 상태를 건드리지 않아 원자적이다.
균열 — 수량 입력
quantity select의 ←/→는 adjustShopQuantity가 1..99로 클램프하지만, 플레이어가 input에 500을 직접 타이핑하면 currentQuantity()는 document.querySelector로 값을 읽어 parseInt만 하고 상한을 강제하지 않는다. handleShopTransaction도 Math.max(1, floor(qty))만 있어 500개 일괄 구매가 통과한다. UI의 max=99는 장식이다.

6. 경제 — 50% 매입가와 할인이 만드는 균열

상점 경제의 전부: buy: cost = price * qty, sell: payout = floor(price/2) * qty. 여기에 SocialShop.multiplier(예: 0.8)와 stock.priceOverride / priceBySeason이 buy price를 바꾼다. sell price는 바뀌지 않는다. 이 비대칭이 차익(arbitrage)을 만든다.

기본 곡선(실측)
회복약 50G, 상급 180G, 엘릭서 600G. 초원 슬라임 골드 4~6, 동굴 박쥐 8, 돌 골렘 10. 초반 1전투 1포션 수준. 할인 없이도 포션 2개면 슬라임 한 마리 값이다 — 곡선 자체는 합리적이다.
차익 임계
multiplier < 0.5 또는 priceOverride < sellPrice이면 buy→sell 무한 반복으로 돈이 생긴다. 현재 SocialShop.priceMultiplier는 0 이상이면 통과(mult < 0 ? 1 : mult)라 0.1도 허용된다. 0.4 하나면 게임 경제가 무너진다.

9. 처방 — 우선순위와 패치 스케치

F-01 — 0=G 무제한 허위

  1. 이벤트에 shop 커맨드 추가 → 상인 소지금 0 입력 (힌트 "0이면 무제한" 확인)
  2. 인벤토리에 potion 1개 넣고 게임 실행 → 상점 진입 → 판매 시도
  3. 예상(문서): 무제한 매입 / 실제: "상인의 돈이 부족합니다." 차단

F-02 — 할인 차익

  1. GameEvent에 characterId: "npc_market", socialShop: {minFriendship:0, priceMultiplier:0.4} 설정
  2. 상점에 potion(50G) 배치 → friendship 0으로 게임 시작 → 상점 buy 20G 확인
  3. sell 25G → 1회 5G 이득, 반복 시 골드 증가

F-04 — 수량 우회

  1. quantityMode: select 상점 생성 → 게임에서 상점 진입
  2. 수량 input에 500 입력 → 구입 클릭 → 500개 결제/지급 여부 확인
  3. 예상: 99 클램프 / 실제: 500 통과

F-03 — 계절가 차익

  1. 상점 stock에서 potion의 priceOverride 10 입력
  2. 게임에서 10G에 buy → 25G에 sell → 15G 차익

F-07 — 빈 상점

  1. shop 커맨드에서 itemIds 비우기 → 게임에서 상점 이벤트 실행
  2. "No goods." 목록 + 구입/판매 메뉴 노출 확인

F-05 — 이중 기록

  1. JSON에서 itemIds:["potion"]인데 stock:[{itemId:"ether"}]로 수동 편집

맺음말

상점은 "작동한다"와 "신뢰할 수 있다" 사이에 서 있다. 작동은 한다 — 타입은 닫혀 있고, 거래는 원자적이며, 에디터는 친절하다. 신뢰는 아직이다 — 문서 한 줄이 거짓말을 하고, 할인 숫자 하나가 경제를 무너뜨리며, input 하나가 상한을 무시한다. 이 셋만 고치면, 상점은 비로소 핵심이라 불릴 자격을 얻는다. 나머지는 상점을 더 좋은 상점으로 만드는 일이다.
