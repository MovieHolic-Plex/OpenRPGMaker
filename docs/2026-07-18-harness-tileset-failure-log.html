P0 옛 칩셋 이미지 기준 매핑이 코드에 잔존 해소

증상
실내 "바닥" 타일(270/271/300/301)이 실제로는 잔디, "벽"(1~3/31~33)이 연못 물 — 스탬프 실내가 시각적으로 전혀 다른 것을 그림. 던전도 동일: 옛 하네스 4그룹 중 3개가 물 타일 오답(석벽 자리 1~3/31~33 = 물웅덩이·수로).
원인
칩셋 이미지가 교체된 적이 있는데 타일 ID 매핑은 옛 이미지 기준으로 남음. 던전 그룹은 실내 것을 복붙한 흔적까지 있었음 — 이미지가 바뀌면 같은 번호가 전혀 다른 그림이 된다는 사실을 시스템이 어디서도 강제하지 않음.
해소
vision 8~14x 업스케일로 480타일 전수 감사 → 정본 시맨틱 테이블 신설(tileSemanticsInterior.ts / tileSemanticsDungeon.ts / tileSemanticsCombinedTown.ts), 하네스 그룹 재작성(던전 4→28그룹 pack v2).
교훈: 칩셋을 쓰기 전에 반드시 전수 감사부터. 타일 번호는 좌표일 뿐 의미가 아니다 — 의미의 정본은 코드 상수가 아니라 시맨틱 테이블 한 곳에만 둔다.

P0 시트 PNG 오염 — 작업 부산물이 원본을 덮음 해소

증상
실내 시트의 4타일(233/234/257/258)에 벽 오토타일 작업의 그림자 라벨이 덧그려져 있었음. 이 오염 시트로 픽셀 경계 전수 대조를 돌리는 바람에 "긴 탁자는 상단 캡이 없다" 같은 2차 오판까지 생산(234가 그림자로 덮여 있었음).
원인
렌더 실험이 소스 에셋을 직접 수정 + 그 상태로 판독 파이프라인을 돌림.
해소
git restore로 복원, 라벨 타일은 시트 픽셀을 절대 쓰지 않는 전체 쿼터 합성 규칙(INTERIOR_WALL_LABEL_TILES)으로 대체. 234=세로 긴 탁자 상단 캡으로 재판정.
교훈: 경계/배경 검사는 반드시 복원(정상) 시트에서. 배경색은 가정하지 말고 실측(실제 배경 255,103,139는 B<140이라 "B>140" 임계값이 통째로 실패했다). 에셋은 읽기 전용 — 보완 작화는 사용자 승인 후 별도 커밋.

P1 라벨 이중 소스 — 큐레이션 정본과 에디터 표기 불일치 458/480 해소

증상
에디터 DB→타일셋 라벨이 "실내 나무 바닥 72"류의 그룹명 조립 문자열 — 큐레이션 정본과 458/480 타일이 불일치.
원인
에디터는 tileset.tileMeta만 읽는데, tileMeta 시드는 하네스 그룹명 조립이었고 큐레이션 테이블은 검색 2곳에서만 소비 — 같은 지식의 소스가 두 개.
해소
시드가 큐레이션 테이블을 조회하도록 통일(+그룹 밖 타일 시드 패스, 사용자 수기 라벨만 우선). RTP 원판 결손(피아노 357 왼칸·왕좌 좌열 447/477 — 클론 오프셋 실수)은 미러 보완 작화로 채움.
교훈: 지식은 한 곳에 쓰고 나머지는 전부 파생시킬 것. "표시용 조립 문자열"이 정본을 이기는 순간 감사 결과가 증발한다.

② 오토타일 실패

P0 멤버 ≠ variantMap 출력 — 성형이 손마감 벽을 파괴 해소

증상
실내 벽(105 브러시) 옆 셀을 편집하면 손으로 마감한 트림(104)이 397로 덮여 벽이 깨짐.
원인
104/106(트림)·396/398(문 알코브)이 오토타일 멤버였는데 variantMap은 이 타일들을 절대 생성하지 않음 → 성형은 이들을 파괴만 할 수 있음. 또 connect가 바닥 72만 알아서 테마 리틴트된 바닥(돗자리 139 등)을 공허로 오판.
해소
불변식 확립: 멤버 = variantMap이 생성할 수 있는 타일만(본체·4변·4모서리). 그 외는 connect 전용 동반 타일로 강등. connect에 전 바닥 재질+러그 등록. 시드는 seed-if-missing → 계약 갱신형으로 바꿔 저장된 옛 프로젝트도 재로드 시 치유.
교훈: 오토타일 그룹의 멤버십은 "관련 있어 보이는 타일 모음"이 아니라 성형 엔진의 입출력 계약이다. connect에 가구를 열거하는 식의 거대 집합도 금물(사용자 노출 목록이자 자동 연결 후보 입력).

P0 같은 타일 ID를 3계층이 해석 — 복원 불가능 상태 해소(Option B)

증상
397이 "저장 오토타일의 edgeS"이자 "문턱"이자 "렌더 쿼터 소스"로 동시에 해석돼, 벽 편집이 서로를 되돌리는 복원 불가 상태.
원인
저장 오토타일 / 쿼터 렌더 / 주택 셸 스탬프가 같은 숫자 공간을 각자 소유.
해소
Option B: 주택 셸 = 완성 통타일 writer(저장 오토타일 폐지) · 다크월은 366만 저장 · 368/396~458은 렌더 전용 아틀라스 소스 · 233/257/258 영구 금지. paintHouseShellWalls·HOUSE_WALL_BRUSH(105)·257 등 삭제 — 되살리면 그 버그가 그대로 돌아온다.
교훈: 저장 계층의 좌표계는 하나여야 한다. "저장 타일 = 의미, 렌더 = 그 의미의 합성"으로 계층을 갈라야 안전하다. 렌더 개선은 저장 데이터 무변경으로 전 맵에 소급된다(다크월 쿼터 엔진 사례).

P1 isMass 분류 누락 → 벽 뒤 공허로 조각 누출 해소

증상
다크월 자리에 크림 회벽을 놓으면 뒤쪽 공허 칸에 벽 조각(428/368)이 흘러나옴("매우 많이 망가짐").
원인
합성 트리거(중심 게이트)와 이웃-벽 판정이 INTERIOR_DARK_MASS_TILES 한 집합에 섞여 있어, 회벽면이 "열림"으로 분류됨.
해소
INTERIOR_WALL_FACE_TILES 신설 — isMass(이웃 판정)에만 포함, 중심 게이트에는 불포함. 잔여: 벽면 바로 아래 고형 가구(화덕 하단 51, 책장) 셀 위를 편집하면 저장 성형이 여전히 깸 부분 해소.
교훈: "이 타일은 벽인가"라는 질문은 문맥이 두 개다(내가 합성을 시작하는가 / 이웃이 나를 막는가). 하나의 집합으로 두 역할을 겸하게 하면 반드시 한쪽이 틀린다.

P1 에디터 증분 리렌더가 이웃 셀을 빼먹음 — 잔상 해소

증상
430 펜으로 칠할 때 계단식 프레임 조각 잔상. 맵 데이터·스크립트 렌더는 정상(화면 전용 오염).
원인
증분 리렌더가 "칠한 셀만" 다시 그림 — 쿼터 합성(다크월 랩·9-슬라이스·호수·길)은 이웃 의존이라 이웃 셀의 낡은 조각이 남음.
해소
하위 레이어 변경 시 8방 이웃도 재렌더.
교훈: 이웃 의존 렌더에서 더티 영역은 "변경 셀 + 영향 반경"이다. 스크린샷 검증 시 데이터 버그와 화면 버그를 먼저 분리할 것.

P2 템플릿에 없는 형상 — 얇은 런·오목 대각 부분 해소

증상
폭/높이 1칸 런은 3×4 템플릿에 전용 타일이 없어 형상이 뭉개짐. 오목(inner) 코너의 대각 결손도 통짜 근사.
해소
얇은 런은 8×8 쿼터 합성(모래·흙길 전용이던 것)을 내장 11종 전체로 확장. 오목 대각의 정본 RM2K식 쿼터 4장 합성은 개선 후보로 남음.
교훈: RM2K 오토타일의 원리는 셀당 8×8 쿼터 4장 독립 합성 — 템플릿 타일이 모자라면 타일을 늘리는 게 아니라 쿼터 합성으로 푸는 게 정석.

P0 심판이 피고의 자기신고를 믿음 해소

증상
평가기의 자연 검사 전체가 builder가 직접 쓴 layoutPlan.kind에 게이팅 — builder가 안 썼다고 하면 검사 자체가 안 돎. doorFronts가 빈 배열이면 도달성 무검사 통과. settlement 레이어는 검증 없이 done. 랜드마크(호수·숲)는 실측 없이 성공 처리.
해소

교훈: 평가기는 시공기의 메타데이터가 아니라 맵 타일 실측으로 판정해야 한다. "검사할 것이 없다"는 통과가 아니라 실패다.

P0 100×100 시공 1,065초 + houseCount 무시 + 밀도 붕괴 해소(v2)

P1 지붕 침범 — 보호구역을 모르는 범용 도구들 해소

증상
스크린샷에서 "지붕 위에 길". 용마루 위 나무 밑동, 울타리가 용마루 행 침범.

⑥ 재발 방지 수칙 (요약)

  1. 정본의 위치: 타일 의미 = 시맨틱 테이블 한 곳 · 구조물 문법 = 사용자 실측 맵(캔버스) · 조립 코드는 언제나 피의자. 분석/에이전트에게 소스 신뢰 우선순위를 명시할 것.
  2. 칩셋 도입 절차: 전수 vision 감사 → 사용자 확정 → 시맨틱 테이블 → 하네스 그룹 → 오토타일 → 검증 렌더. 시트는 읽기 전용, 검사는 복원본에서, 배경색은 실측.
  3. 오토타일 불변식: 멤버 = variantMap 출력 가능 타일만 · 트리거는 멤버 한정 · connect는 사용자 노출 목록임을 기억 · 저장 좌표계는 한 계층만 소유(렌더는 합성으로).
  4. 파괴 연산: 스냅샷 기준선 + "이번 실행이 만든 것"만 삭제. 전역 초기화 금지(wipeProjectMaps를 되살리지 말 것).
  5. 평가 게이트: 실측 기반 · 하드 실패 · 통행 어휘 최신화 · 규모 불변 목표 · 폴백 의심. 게이트 도입은 빠를수록 싸다 — 게이트가 없던 기간의 버그는 게이트를 넣는 순간 한꺼번에 청구된다.
  6. 보호구역: 구조물 점유 = 그린 칸 전부(bbox 밖 용마루 포함). 범용 배치 도구 뒤에는 결정적 후처리 복원. 길/조경은 시공 전 스냅샷→침범 점검→롤백 재시도.
  7. 멀티타일 소품: 페어/세트가 배치 단위(배너 179+209, 석상, 돌기둥, 나무 수관+밑동, 울타리 둘레 세트). 자리가 문법에 안 맞으면 조용히 찍지 말고 거부.
  8. 스케일 테스트: 시공 파이프라인은 최소/기본/최대 면적을 같이 재라(1,065초·밀도 붕괴는 전부 대형에서만 드러났다). 인자는 소비 경로까지 검증.
  9. 검증 방법: 시각 증거는 손으로 그리지 말고 실제 API를 호출하는 렌더 스크립트로 재생성(inline assert 동반). 회귀 판정은 stash 왕복 기준선 대조.
  10. 부수효과 격리: 라이브 DB 쓰기는 옵트인 설정으로 분리. 배포 보고에는 projectId 명시(에디터가 다른 프로젝트를 보고 있던 혼선 사례).
