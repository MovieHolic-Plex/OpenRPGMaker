# 마을 만들기 3층 구조 (쉽게 읽기)

> **Status:** 구현 완료 (기록용). 현행 문서는 `openwiki/large-village-generation.md` 참조.

> **한 줄 요약**  
> LLM은 **무엇을 만들지 계획**만 하고,  
> 코드는 **규칙을 지키며 실제로 찍고**,  
> 마지막에 **깨진 곳이 없는지 검사**한다.  
> **시간축:** 한 방이 아니라 **체크리스트를 여러 턴에 닫는다**  
> (`run_village_session` / `advance_village_build`).  
> **순서(LLM `buildOrder`):** 호수/강이면 `water` 먼저 → `settlement`(집→길) → 숲 → critique → look.

우리가 말한 이 문장:

```text
Hierarchical plan (LLM)
  + Constraint executor (code)
  + Critique loop (reachability / lint)
```

을 **일상어**로 풀면 이렇게 됩니다.

```text
계층 계획 (LLM이 큰 그림)
  + 제약 시공기 (코드가 타일 규칙 지키며 시공)
  + 비평 루프 (도달·오류 검사 후 고치기)
```

---

## 왜 이렇게 나누나?

마을을 LLM에게 **한 방에 “맵 다 그려”** 시키면 보통 이렇게 됩니다.

| 잘함 | 못함 |
|------|------|
| 테마 느낌 (어촌, 장터) | 타일 번호·오토타일 모서리 |
| NPC 이름·대사 | 문 앞이 막히지 않게 길 연결 |
| 집 몇 채, 분위기 | 울타리 칩 조합, 통행 규칙 |

그래서:

- **창의·의도** → LLM  
- **규칙·정확도** → 코드  
- **결과 확인·수정** → 검사 + 다시 계획/시공  

이 세 층을 나눕니다.

---

## 비유: 집 짓기

| 층 | 현실 비유 | 게임에서 |
|----|-----------|----------|
| **1. 계층 계획** | 건축주 + 설계사: “어촌 마을, 남쪽 광장, 집 6채, 장터 느낌” | LLM → `plan_village` 같은 **계획서(JSON)** |
| **2. 제약 시공기** | 시공팀: 도면 보고 벽돌·배관 규칙 지키며 지음 | 코드 → `build_village` / `paint_road` / 울타리 / 소품 |
| **3. 비평 루프** | 감리: 문 앞에서 광장까지 걸어가나? 집 안 뚫렸나? | `check_reachability` / 마을 감사(audit) / lint |

설계사가 벽돌 한 장씩 쌓지 않듯,  
**LLM도 칩셋 타일을 한 칸씩 고르지 않는 편이 낫다.**

---

## 1층 — Hierarchical plan (계층 계획)

### “계층”이 뭐야?

한 번에 전부 정하지 않고, **큰 것 → 작은 것** 순으로 정한다.

```text
마을 전체
  ├─ 테마: 강가 어촌 장터
  ├─ 길: 모래
  ├─ 광장: 남쪽, 장터 스타일
  ├─ 지구: 집촌 / 물가 / 숲 가장자리
  ├─ 집 1: 흰 회벽, 마당에 과일박스·벤치, 주인 "어부"
  ├─ 집 2: …
  └─ NPC 대사들
```

### LLM이 적는 것 (의도)

- 테마 한 줄  
- 길 재질 (모래 / 흙)  
- 광장 위치·분위기  
- 집 개수, 키트, 마당 소품 태그  
- NPC 이름·대사  
- (나중) 호수·장터·묘지 같은 **역할 구역**

### LLM이 안 적는 편이 좋은 것

- 타일 번호 378, 379…  
- 오토타일 모서리 계산  
- “이 칸 upper에 울타리 레일” 같은 **시공 디테일**

### 산출물

**계획서 하나** (예: VillagePlan JSON).  
이 단계에서는 맵 타일을 **안 바꿔도 된다.**  
(“도면만 그림”)

---

## 2층 — Constraint executor (제약 시공기)

### “제약”이 뭐야?

맵을 마음대로 칠하면 게임이 깨진다.  
코드가 지키는 예시:

- 길은 이어져야 함  
- 울타리는 문 앞 게이트를 비워야 함  
- 투명 소품은 상위 레이어  
- 나무는 물·길 위에 안 올림  
- 집 키트 문·지붕 문법  

이런 규칙을 **자동으로 지키며** 계획서를 맵에 찍는 쪽이 시공기.

### 코드가 하는 일

| 계획서에 적힌 것 | 코드가 실제로 함 |
|------------------|------------------|
| “모래 길” | `paint_road(style: sand)` + 오토타일 |
| “집 6채, 광장 남쪽” | 좌표 잡고 house kit 스탬프 |
| “마당에 mailbox, flowers” | 문 앞 영역 계산 후 `place_props` |
| “울타리 on” | 필지 사각형 + 남쪽 3칸 게이트 |
| “NPC 어부” | 통행 가능 칸에 `place_npc` |

이미 우리 쪽에 있는 것들과 연결하면:

- `build_village`  
- `paint_road`  
- house kit / 울타리  
- `place_props`  
- `build_house_lots` (집 좌표를 더 세밀히 줄 때)

### 핵심 한 줄

> **계획 = 무엇 / 어디쯤 / 어떤 느낌**  
> **시공 = 규칙 지키며 타일·이벤트 확정**

## 3층 — Critique loop (비평 루프)

### 왜 필요한가?

계획이 좋아 보여도 시공 후 이런 일이 난다.

- 문 앞에서 광장까지 **길이 끊김**  
- 집이 목표 수보다 적음  
- 울타리가 길을 막음  
- 내부 맵·문 이벤트 누락  

그래서 **짓고 → 검사 → 안 되면 고침**.

### 검사 예시

| 검사 | 의미 |
|------|------|
| 도달 가능 (`check_reachability` 등) | 시작점·문 앞·광장이 걸어서 이어지나 |
| 마을 audit | 집 수, 문 연결, 길 성분, NPC 수… |
| lint / 경고 | 명세 밖 시공, 구조물 침범 등 |

### 루프가 도는 방식

```text
1. LLM이 계획 작성
2. 코드가 시공
3. 검사가 “문 2채 연결 안 됨” 보고
4. LLM(또는 코드)이 계획/시공 수정
5. 다시 2~3
   (몇 번 실패하면 안전한 기본 템플릿으로 폴백)
```

이게 **Critique loop**다.  
한 번에 완벽을 기대하지 않고, **피드백으로 고친다.**

## 전체 흐름 (그림) — 권장 확장판

지금 있는 3층에 **스펙(밑그림)** 과 **비전(눈)** 을 끼우면 이렇게 된다.

```text
사용자: "강가 어촌 마을 만들어줘"
              │
              ▼
┌─────────────────────────────────────┐
│  A) plan_village (계층 계획)        │
│     · 테마·집·마당·NPC 의도         │
│     · 맵 타일 변경 없음             │
│     · 산출: planId + 한 줄 요약     │
└─────────────────────────────────────┘
              │
              ▼
┌─────────────────────────────────────┐
│  B) set_build_spec (공간 명세)      │  ← 중간에 넣는 것
│     · plan에서 영역 박스 자동/반자동 파생 │
│     · 겹침·맵 밖·구조물 보호 검증   │
│     · “이 구역에 집/길/소품 놓는다” │
└─────────────────────────────────────┘
              │
              ▼
┌─────────────────────────────────────┐
│  C) build_village (제약 시공)       │
│     · planId 먹고 타일·이벤트 확정  │
│     · 스펙 영역 안(또는 확장 경고)  │
└─────────────────────────────────────┘
              │
              ▼
┌─────────────────────────────────────┐
│  D1) critique_village (구조 비평)   │  코드
│      · 문 연결, 도달, 집 수…        │
│  D2) 맵 스크린샷 + LLM 시각 평가   │  ← 중간에 넣는 것
│      · show_map_region / 전체 썸네일│
│      · “테마 맞나? 텅 비었나? 막혔나?”│
└─────────────────────────────────────┘
              │
        실패? ├── 구조 실패 → plan/시공 수정 후 C
              └── 시각 실패 → plan 톤 수정 후 A 또는 부분 재시공
              │
              ▼
            통과 → 사용자에게 결과
```

### 왜 스펙을 중간에 넣나?

| 구분 | VillagePlan | BuildSpec (`set_build_spec`) |
|------|-------------|------------------------------|
| 질문 | **무슨 느낌의 마을?** | **어느 칸에 뭐를 둘 예산?** |
| 예 | 어촌, 모래길, 남쪽 광장 | house@…, road@…, prop@… |
| 검사 | 태그·개수·테마 휴리스틱 | 겹침, 맵 밖, 기존 구조물 보호 |

- Plan만 있으면: “분위기”는 있는데 **영역 충돌 게이트**가 약함.  
- Spec만 있으면: 박스는 있는데 **어촌인지 광산촌인지**가 없음.  
- **둘 다**: plan → (자동) assets로 펼친 뒤 `set_build_spec` → `build_village`.

권장 구현 방향:

1. `plan_village` 성공 시 `villagePlanToBuildSpec(plan, mapSize)` 로 assets 초안 생성  
2. 세션이 그걸 `set_build_spec`에 넣거나, `build_village`가 내부에서 스펙 검증  
3. 모델이 박스를 손으로 thrash하지 않게 **파생을 기본**으로

### 왜 맵 스크린샷 LLM을 넣나?

구조 검사(`critique_village`)는 이런 것만 본다.

- 길이 이어지나?  
- 문 앞 갈 수 있나?  
- 집 수가 맞나?

**안 보는 것:**

- 광장이 허전한가?  
- 집이 한쪽에만 몰렸나?  
- 어촌인데 산골처럼 보이나?  
- 울타리·나무가 지저분한가?

그래서 시공 후:

1. **코드**가 맵 전체(또는 타일 그리드) 이미지를 만든다  
   - 이미 있는 재료: `show_map_region` (영역 타일 이미지), `renderRegionSnapshot` (썸네일 캔버스)  
2. **멀티모달 LLM**이 짧은 체크리스트로 평가한다  

예시 체크리스트 (JSON으로 받게):

```json
{
  "ok": false,
  "score": 0.55,
  "themeMatch": "weak",
  "issues": [
    "광장이 비어 장터 느낌이 약함",
    "북쪽 가장자리만 나무가 빽빽함"
  ],
  "fixes": [
    { "kind": "plazaDecor", "hint": "벤치·과일박스 추가" },
    { "kind": "rebalanceTrees", "hint": "남쪽 가장자리에도 나무" }
  ]
}
```

- `ok: true` → 끝  
- `ok: false` + 구조 이슈 없음 → **계획 미세조정** 또는 **부분 시공**(소품만 다시)  
- 구조 이슈 있음 → 먼저 `critique_village` 쪽 수정

주의:

- 50×50 전체를 매번 고해상도로 넣으면 **토큰·비용**이 큼 → 전체는 저해상 썸네일 + 문제 구역만 `show_map_region` 확대  
- 비전 LLM은 **미학 판정**, 코드 비평은 **통과/실패 게이트** — 역할을 섞지 말 것  
- 자동 재시도는 **최대 1~2회** (비전 thrash 방지)

### 검사 2종류 정리

| 종류 | 누가 | 질문 | 실패 시 |
|------|------|------|---------|
| 구조 비평 | 코드 | 걸어가나? 숫자 맞나? | plan/시공 재실행 |
| 시각 비평 | LLM+이미지 | 테마·밀도·균형 괜찮나? | plan 톤 수정 또는 부분 꾸밈 |

월드 쪽과 같은 리듬:

| 월드 | 마을 (목표 그림) |
|------|------------------|
| `plan_world` | `plan_village` (계획) |
| (영역 예산) | `set_build_spec` ← plan에서 파생 |
| `build_world` | `build_village` (시공) |
| `lint_world` | `critique_village` + **맵 비전 평가** |

## 지금 우리 프로젝트 위치

| 층 | 툴 | 상태 |
|----|-----|------|
| 계획 | `plan_village` | ✅ + **쿼리 상식 스펙** (`requirements`: 강/숲/장터…) |
| 스펙 | `materialize_village_spec` (+ 세션 `set_build_spec`) | ✅ plan→BuildSpec (필수 강/숲 영역 포함) |
| 시공 | `build_village({ planId })` | ✅ 주거 + **랜드마크(강·호수·숲)** |
| 구조 비평 | `critique_village` | ✅ |
| 룩 게이트 | `evaluate_village_look` | ✅ 휴리스틱 + **requirementsMet** (강/숲 존재 필수) |
| 피드백 개정 | `revise_village_plan` | ✅ fixes→plan 패치 |
| 원큐 | `run_village_pipeline` | ✅ 실패 시 최대 N회 재시공 |

**상식 계약:** 사용자가 「강촌마을」이라고 하면 plan에 `river`+`forest`+주거가 들어가고, 시공이 수역·숲을 깔며, 게이트가 없으면 탈락시킨다.

피드백 루프: 게이트 실패 → `feedbackForLlm`을 다음 관찰로 → `revise_village_plan` → 맵 wipe → `build_village` 재실행.

코드: `villagePlan.ts`, `villageEvaluate.ts`, `villageBuilder.ts`  
재현: `npx tsx scripts/plan-build-village.mts`  
나중: `show_map_region` 멀티모달로 look report 보강, district/랜드마크.

## 하지 말아야 할 것

1. LLM에게 **타일 id 나열로 맵 전체 그리기**  
2. 계획 없이 **빈 `build_village()`만** 돌려 “창의적 마을” 기대  
3. 검사 없이 “한 번에 끝” 가정  
4. `set_build_spec`(영역 박스 게이트)과 마을 **미학 계획**을 한 덩어리로 섞어 버리기  
   - 영역 게이트는 유지해도 됨  
   - 하지만 “어촌 장터 느낌” 같은 내용은 **VillagePlan** 쪽이 맞음

## 초단기 기억용 카드

```text
1. PLAN   — LLM: 뭐 만들지 (테마·구역·집·NPC)
2. BUILD  — CODE: 규칙 지키며 찍기
3. CHECK  — 걸어가나? 깨졌나? → 안 되면 1 또는 2로
```

이 세 박자가  
**Hierarchical plan + Constraint executor + Critique loop** 전부다.
