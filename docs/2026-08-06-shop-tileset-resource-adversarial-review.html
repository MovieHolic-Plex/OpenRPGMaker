P0 — 숨은 경제

merchantGold / 시즌 / 소셜 할인이 미리보기가 없다

  • 상인 소지금 DEFAULT 100G — resolveShopMerchantGold 가 NaN→100, 음수→0, 소수→floor 로 클램프. handleShopTransaction 에서 매입 시 merchantGold < sellPrice*qty 면 “상인의 돈이 부족합니다.” 로 차단, 구매 시 merchantGold += cost 로 예산이 늘어난다. 에디터엔 이 숫자를 보는 칸이 없다.
  • 계절 재고 — ShopStockEntry.seasons/priceBySeason 가 있으면 resolveBaseShopStock 이 project.system.timeSystem.enabled 일 때만 필터링. 에디터에서 “봄에만 보이는 포션”을 테스트하려면 게임 시간을 바꿔야 한다.
  • 소셜 할인 — resolveSocialShopPriceMultiplier 가 characterId + socialShop.minFriendship + priceMultiplier 로 buy 가격만 스케일. priceMultiplier 0 이면 무료가 된다(0 클램프 없음). 미리보기·경고 없음.
P1 — UX 맹점

quantityMode / branchOnTransaction 이 설명 없이 숨어 있다

  • quantityMode: single(기본) vs select — select면 shopItemList 에 input[type=number, 1..99] 가 붙고, 커서 ←→ 로 adjustShopQuantity 가 동작한다. 버튼에 힌트가 없다. 숫자 입력이 있다는 걸 모르면 1개씩만 산다.
  • shopType: normal/buyOnly/sellOnly + messageType: welcome/business/direct — playSceneShopDom.ts:shopType/messageLine 에서 분기하지만, 에디터 폼엔 라벨·미리보기 문장이 짧게만 뜬다.

인터프리터·검증 경계

인터프리터 핸드오프

interpreter.ts: createInterpreter → executeCommand → pause(shop) — shop은 블로킹 StepResult { kind:"shop", items, merchantGold, branchOnTransaction … } 를 던지고 resume(boolean) 으로 재개한다. 상점 안에서 인벤토리·골드가 바뀌어도 scene.syncRuntimeState() 가 매 거래마다 호출돼 세션이 즉시 반영된다. 이 부분은 견고하다.

좋은 점 — 매입 실패 시 owned < qty → “You do not have enough.”, merchantGold < payout → “상인의 돈이 부족합니다.” 로 언어가 갈라진다. 테스트가 blocked → ok 두 경로를 모두 잡는다(shopMerchantGold.test.ts:31-49).

검증 구멍 2개

  • itemIds vs stock 이중 기록 — shop 커맨드는 레거시 itemIds: string[] 와 신형 stock: ShopStockEntry[] 를 둘 다 가진다. resolveBaseShopStock 은 stock 이 있으면 itemIds 를 무시한다. 에디터에서 두 곳을 따로 편집하면 “stock엔 있는데 itemIds엔 없는” 괴리가 생긴다. 검증은 둘 다 reference.item.missing 를 돌지만, 어느 쪽이 런타임에 쓰이는지 알려주지 않는다.
  • 가격 0 허용 — stockEntryPrice 는 priceOverride/priceBySeason 를 Math.max(0, trunc) 로만 클램프. 0원 상점은 에러가 아니다. 소셜 할인으로 0원이 된 경우도 마찬가지. 의도한 무료 나눔인지 실수인지 구분 불가.

P1 — 계약 밖 칩셋

업로드 칩셋은 하네스가 없다

isCombinedTownTileset / isThemePackTileset 가 번들 tex_* 만 인식한다. 사용자가 올린 480×256 칩셋은 ensureTilesetHarnesses 에서 그대로 통과 — tileGroups 0, tileMeta 빈칸, passability 기본값, priority 기본값 으로 남는다. 나무·물·벽 라벨, 오토타일, 투명 우선순위 모두 없다. resourceSearch.ts:bundledTileSemantics 도 같은 분기로 커스텀 칩셋을 COMBINED_TOWN_TILE_SEMANTICS 로 때운다 — 인덱스 의미가 다른데 라벨을 덮어씌운다.

재현: 새 프로젝트 → 칩셋 업로드(480×256, 나무 2칸 포함) → 팔레트에서 “나무” 검색 → combinedTown 라벨이 붙어 엉뚱한 타일이 하이라이트된다. 같은 나무를 하위 레이어에 칠하면 enforceTransparentOverlayPriority 가 동작하지 않아 검은 배경이 보인다.
P0 — 조용한 graft 실패

graft는 실패해도 조용하다

  • isValidTileGraft — 음수·비정수·빈 문자열만 거른다. 존재하지 않는 sourceChipset 은 통과.
  • createGraftedTilesetCanvas — resolveSourceImage(key) == null 이면 warn 후 continue. 캔버스는 빈칸으로 남는다. 에러·검증 이슈 없음.
  • tileGraftImageCache.ts:scheduleGraftImageBake — loadChipsetSourceImage 가 bundledChipsetPath 에서 못 찾으면 동일하게 warn+skip. 커스텀 소스 전체가 이 경로로 막힌다.
  • tileGraftsTextureSuffix — djb2 → (hash>>>0).toString(16) 32비트. 이론상 충돌 시 다른 graft 구성인데 같은 텍스처 키를 쓴다. 캐시 키는 baseUrl|count|suffix 3요소뿐이라 충돌 확률이 0이 아니다.

레이어 강제 — 의도는 좋고, 설명은 없다

enforceTransparentOverlayPriority 가 투명 칩을 전부 priority=upper 로 승격한다. 예외는 isUserRuntimeMeta(meta) && defaultLayer=="lower" 일 때, 그리고 TREE_TRUNK 뿐. 사용자가 “이 벤치를 바닥에 깔고 싶다”고 lower로 고정하지 않으면, 하네스가 매 로드마다 upper로 되돌린다. 팔레트엔 “상위 전용”이라는 문구만 있고, 왜 하위에서 검게 보이는지(투명 배경)는 툴팁 한 줄로 끝나서 초보가 이해하기 어렵다.

나무 수관(260-263) upper★ + 밑동(290-293) lower solid — 겹치면 숲이 되는 건 잘 설계됐다.

행 단위 확장 — 캔버스가 자란다

tileCountWithGrafts = max(count, rowAlignedTileCount(maxTarget+1, tilesPerRow)) — targetTile=500 이면 ceil(501/30)*30 = 510, 즉 17행이 필요해 캔버스 높이가 max(baseHeight, 17*16=272) 로 늘어난다. 베이스 256보다 16px 커진다. 그 아래 20칸은 비어 있다. 빈칸을 칠하면 투명으로 남고, 저장 시 count=510 이 된다. 이후 이 이미지를 다시 업로드하면 validateResourceDimensions 가 480×256 고정 이 아니라서 통과하지만, 다른 툴은 510을 모른다.

P1 — 캐시 사각

Supabase 캐시는 base64만 안다

supabaseResourceCache.ts:BASE64_DATA_URL = /^data:([^;,]+);base64,([A-Za-z0-9+/=]+)$/ — parseBase64DataUrl 가 이 정규식에 안 맞으면 skipped: not-base64-data-url 로 버린다. 외부 URL 업로드, blob URL, plain text dataUrl은 전부 스킵. cacheStorage == undefined 면 cache-api-unavailable 로 전량 스킵. 리포트 { cached, skipped } 는 반환되지만, 어디에도 경고 토스트가 없다. 오프라인/배포 시 리소스가 조용히 빠진다.

추가로 SUPABASE_RESOURCE_CACHE_NAME = "…-v1" 이 하드코딩. 프로젝트가 바뀌어도 같은 캐시 이름이라 오래된 리소스가 남는다. 무효화 키가 없다.

수집·해결은 넓다

collectResourceIds 가 8개 소스를 합친다 — sprites, uploaded, resourceProfiles, tilesets, promoted plan, builtin ids, EasyRPG/CC0/Scarloxy/Farming. generatedAssetResourceResolver.ts 는 BUILTIN_GENERATED_RESOURCE_URLS 100+개와 LEGACY_PACKAGED_RESOURCE_URLS 를 분리하고, 404를 correctFaceGridOnLoad onerror 로 방어한다. resourceSearch.ts:charsetDerivedTags 가 people→ 마을/사람 같은 한영 동의어를 보강한 것도 실측 로그(LLM은 영문 질의 우선)에서 나온 좋은 패치다.

P1 — 슬라이싱 맹점

규격 검사가 graft 확장을 모른다

resourceProfiles.ts:validateResourceDimensions 는 chipset 480×256, charset 288×256… 고정 규격을 엄격히 본다. 그런데 graft로 count 510 이 된 칩셋을 이미지로 내보내 다시 업로드하면, 그 이미지는 480×272(17행)라 규격에 안 맞는다. 현재 코드는 이 이미지를 chipset 으로 재검증하지 않으므로 통과하지만, 나중에 누군가 “칩셋 규격 검사”를 강화하면 graft 지도가 전부 에러가 된다. 또한 music/sound 는 media=="audio" 라 무조건 ok:true — 깨진 오디오도 검증이 안 잡는다.

4. 교차 실패 — 세 축이 함께 깨지는 지점

P0

X1 · AI 상점 + 타일 + 리소스 동시 실패

AI가 build_village 로 마을을 깔고 place_npc(상점 주인) 으로 상인을 꽂으면 — 상점은 비어 있고(1장), 상인 스프라이트는 charset:people1 같은 번들 키라 리소스는 통과하지만, 상점이 선 자리의 타일은 WOOD_EDGE 같은 데크 가장자리일 수 있다. 그 타일은 4방향 차단이라 플레이어가 카운터에 접근 못한다. 세 축이 각자 “성공”인데 합치면 막힌 상점이 된다.

P1

X2 · 에디터 미리보기 vs 런타임 진실

에디터는 데크를 타일 색으로 보여준다. 런타임은 passability × priority 로 걷는다. 투명 타일의 검은 배경, 상인 소지금 부족, 시즌 필터링, 소셜 할인은 에디터에서 안 보인다. “보이는 대로 도는” 계약이 4곳에서 깨진다.

P1

X3 · 마이그레이션 빚

하네스 라벨 우선순위가 “bundled-default를 태그로 강등, user만 우선”으로 바뀐 건 좋은데, 구 프로젝트는 이미 source: bundled-default 라벨로 저장돼 있다. 재저장 전까지 구 라벨이 검색 상단에 뜬다. graft count 510 지도도 구 버전 툴은 480으로만 안다.

그림 5 — 삼축 교차 실패 매트릭스. 세로로 읽으면 각 축의 P0→P1→P2, 가로로 읽으면 같은 심각도끼리 묶인다. 빨간 행이 “조용히 틀리는” 것들이다.

5. 증거 — 어디를 뜯었나

정적 코드 감사 + 테스트 독해 + 빌드 산출물 대조. 브라우저 스냅샷은 이 리뷰의 재현 단계에 포함하지 않았다 — 상점은 1장 데모 맵이라 스냅샷보다 코드 경로가 더 정직하다.

재현 레시피 (수동, 5분)

R1 — 빈 점포 재현

  1. AI 패널에 “상점 주인 1명 추가해줘”
  2. 생성된 이벤트 열기 → 상점 커맨드의 재고가 비어 있음 확인
  3. DraftValidator 패널에서 shop.items.empty 에러 확인
  4. 그런데 AI 로그는 “place_npc 성공”으로 찍힘 — 메시지 갈림 확인

R2 — 커스텀 칩셋 검은 배경

  1. 480×256 칩셋 업로드 (투명 배경 벤치 포함)
  2. 그 칩셋으로 새 맵 생성 → 벤치를 하위 레이어에 배치
  3. 런타임에서 벤치 배경이 검게 보임 — isCombinedTownTileset==false 라 upper 강제 안 됨
  4. 같은 타일을 상위로 옮기면 정상 — 하네스 밖 증거

R3 — 검증 우회 404

  1. 아이템 하나에 iconResourceId="generated-enemy-typo" 지정
  2. 검증 패널: 에러 없음 (접두사 예외)
  3. 게임 실행 → 콘솔 404, 아이콘 미표시 — 검증이 못 잡은 증거

R4 — 상인 돈 부족 첫 경험

  1. 상점 merchantGold=10 으로 저장, 가격 100짜리 아이템 1개 판매 시도
  2. 런타임 상점에서 “판매” → “상인의 돈이 부족합니다.” 첫 노출
  3. 에디터엔 이 예산을 미리 보는 UI 없음 — 플레이어가 처음 본다

6. 처방전 — 고치는 순서대로

작게, 검증 가능하게, 한 번에 하나씩. “전면 리팩터”는 이 문서가 반대한다.
