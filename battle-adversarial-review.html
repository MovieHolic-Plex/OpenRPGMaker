CHAPTER 01 — HOSTILE VERDICT

총평: 무엇이 깨지고, 무엇은 의외로 단단한가

5명의 적대적 리뷰어가 각자 다른 각도에서 같은 코드를 찔렀다. 겹치는 지적만 남겼다.

치명 플레이어가 체감하지 못하는 성장

  • power + floor(stat/2) - floor(def/2) — stat 2 올려야 +1 피해. 장비 +3 공격이 체감 1.5에 불과.
  • 방어는 분모가 아니라 뺄셈: 고방어 보스가 아니라면 방어 투자는 늘 손해.
  • variance 0 / critical 0 기본값으로 모든 전투가 결정론적 탁구.
src/battle/battleDamage.ts:64-88 power + floor(atk/2) → ×element → ±variance → ×crit(×3) → -floor(def/2) → defending/2 → max(1)

견고 의외로 잘 막아둔 것

  • 예측/실제 단일 권위자 분리: usesMagicalDefense()가 runtime/predict 공통 — 패리티 붕괴 방지.
  • 스냅샷·타임라인 append-only, RNG 주입(mulberry32) — 재현·리플레이 가능.
  • 레벨업 다중 레벨·클래스 곡선·스킬 습득 일원화 — 마이그레이션 내성.

CHAPTER 02 — DAMAGE FORMULA FORENSICS

데미지 공식 해부: 왜 때려도 안 아픈가

공식은 단순하다. 단순해서 문제다. 한 줄마다 플레이어 체감을 갉아먹는 트레이드오프가 숨어 있다.

공식 원문 (실측)

let m = power + floor(stat/2) m = round(m * element) // 0=무효, 음수=흡수(그대로) m = applyVariance(m) // ±variance% (기본 0) if (roll(critRate)) m = round(m*critMult) // 기본 0%, 기본 ×3 m -= floor((def * defMult)/2) // ← 뺄셈! if (defending) m = floor(m/2) return max(1, m) if m>0 else m

출처: src/battle/battleDamage.ts:computeMagnitude. stat은 attack/mind 중 하나, def는 defense/mind 택1.

적대 포인트 1 — 뺄셈 방어: 방어 40→80(+40)이 피해 -20에 불과. 같은 투자로 공격 40→80이면 피해 +20. 즉 방어는 공격의 절반 효율. 탱커는 늘 손해 보는 장사.

시뮬레이션: 같은 자원으로 공격 vs 방어 투자 시 피해 변화

power 30, 상대 방어 40 기준 — 공격 +40과 방어 +40의 비대칭

공격 투자   방어 투자   상쇄 — “둘 다 키우면 제자리”

교훈: 이 공식은 둘 다 키우면 성장이 사라진다. 레벨 곡선이 공격·방어를 같이 올리므로(§4), 후반 체감은 필연적으로 평탄화.

균열 A floor/2 계단 — 1 올려도 0

floor(stat/2), floor(def/2) 때문에 스탯 1 증가가 피해 0인 구간이 50%. 플레이어는 “장비 바꿨는데 왜 그대로지?”를 반복 경험.

atk 45 → floor 22, atk 46 → floor 23 (+1) atk 44 → floor 22, atk 45 → floor 22 (+0) — 절반은 공기

장비 보너스 +3이 체감 +1~2로 뭉개지는 이유.

균열 B variance/crit 기본 0 — 전투가 주사위를 잃음

기본 variance 0, criticalRate 0이면 모든 타격이 고정값. RM2K3 감성은 좋지만, 2026 플레이어는 “같은 버튼 30번”을 지루해한다.

  • 분산 0 → 오버킬 표기(applyDamage가 원본 피해 반환)만으로 타격감 보정 — 실제 긴장은 없음.
  • 크리 ×3은 터지면 너무 세고, 기본 0이라 밸런스 테스트에서 한 번도 안 터짐 → 실전 밸런스 사각지대.

균열 C 마법 방어 게이트 — gen1에서만 살아나는 mind

주석이 솔직하다: usesMagicalDefense()는 battleModel==="gen1"에서만 mind로 라우팅. 기본 rm2k3에선 화염·냉기·번개가 모두 defense로 깎인다.

// battleDamage.ts:11-20 — 게이트 없으면 기존 RM2K3 저장소가 전부 깨진다. // normalizeElementKind 폴백이 "magical"이고 17개 중 13개가 magical. if (project.system.battleModel !== "gen1") return false;

결과: mind 스탯은 gen1을 켜기 전까지 장식. 마법사·힐러의 방어 투자가 무의미. 켜는 순간 기존 프로젝트 피해가 마이그레이션 없이 바뀜 — 둘 다 나쁜 선택. 게이트는 필요했지만, 그 자체가負債를 증명한다.

모델마법 피해 감소플레이어 오해
rm2k3(기본)defense“마법 방어 올렸는데 왜 그대로?”
gen1mind (magical kind만)“왜 갑자기 불 데미지가 달라졌지?”

패리티 붕괴 예측은 장비 보너스를 모른다

battlePredict.battlerStats()는 parameterValueAtLevel(curve, level)만 보고, battleBattlers.totalEquipmentBonuses()의 +attack/+defense를 무시.

predict: curve[level] 만 runtime: curve[level] + equipmentBonuses + paramBonuses

장비 바꿔 끼면 예측 피해는 그대로, 실제 피해는 달라짐 — UI 신뢰도 하락. STAB·속성 배율은 맞췄으면서 정작 스탯에서 틀린다.

흡수/무효 분기 — 음수 배율의 함정

코드: if (elementMultiplier===0) return 0 / if (<0) return magnitude — 흡수는 그대로 힐로 뒤집히며, 방어 계산을 안 탄다. 흡수 몬스터가 방어 버프를 받아도 의미 없음.

CHAPTER 03 — RUNTIME & TURN GAUGE DISSECTION

런타임/턴 게이지/상태: 결정적이지만, 상태가 게임을 멈춘다

상태기계는 깔끔하다. 그러나 상태이상 하나가 전체 게임을 무승부로 몰고, 연출이 로직을 멈춘다.

ATB 게이지 — 민첩이 이렇게 무력할 줄이야

chargeRate = max(0.02, agi × 0.1/43) · timeToReady = (100-gauge)/rate

chargeRate   기준점   민첩 8 이하는 체감 0

비판: 민첩 43(기본값)에서 100까지 올려도 대기시간 430ms→230ms 차이. 2배 투자에 0.2초. 게다가 FLOOR 0.02로 슬로우 상태가 사실상 무의미. 상태가 민첩을 안 건드려서, 둔화/가속 버프를 넣을 자리도 없다.

상태기계 — 잘한 것과 못한 것

잘함왜
append-only timelinesequence 단조증가, 재생·검증 가능
RNG 주입전투·예측·시뮬이 같은 시드 공유
배틀이벤트 분리battleEvents.ts가 조건·커맨드 일원화
그러나 — 연출이 로직을 멈춘다: battleEventState.wait(ms)가 pendingWaitMs를 적립하고, tick()이 그 시간을 먼저 소진. 배틀이벤트 wait 2초면 2초간 게이지·턴 전부 정지. 플레이어는 “왜 ATB가 멈췄지?”를 이해할 수 없다. 연출과 로직의 결합도가 너무 높다.
runtime.ts: pendingWaitMs -= min(pendingWaitMs, deltaMs); deltaMs -= consumed; // 남은 시간만 charge

상태이상 — 문자열을 파싱하는 전투

stateBehavior()가 record.runtimeEffects 없으면 hpTurn 문자열에서 /-?\d+%/ 를 정규식으로 뽑는다. DB가 한글로 바뀌거나 “매 턴 -6%” 표현이 달라지면 지속피해가 0이 된다.

hpDamagePercentFrom(hpTurn: string) /(-?)\s*(\d+)\s*%/ → 있으면 그 값 /^\s*(-?\d+)\s*$/ → 절댓값 else 0

하드코딩 분기도 산재: state_sleep은 무조건 행동불가, state_attack_up은 ×2, state_poison은 전투종료 유지. 새 상태 추가 시 코드 수정이 필요 — 데이터 드리븐이 아니다.

독·수면 = 무승부 공장

독 틱: tick = floor(maxHp*%/100), min 1, cap hp-1 — HP를 1 미만으로 안 떨어뜨림. 수면: restrictsAction=true로 행동 완전 봉쇄. 둘 다 자연회복은 확률.

if (tick>0 && battler.hp>1) hp -= min(tick, hp-1) canBattlerAct = !stateIds.some(restrictsAction)

전원이 수면 + 독이면: 아무도 행동 못 함 + 독은 죽이지 못 함 = 영원한 전투. 이를 STRICT_MAX_ROUNDS=200에서 강제 탈출(escape)로 봉합. 플레이어에겐 “왜 갑자기 도망쳤지?”로 보인다.

상태 배율 중첩 — 곱하기로 터지는 공격력

attackMultiplierForStates = ∏ behavior.attackMultiplier defenseMultiplierForStates = ∏ behavior.defenseMultiplier // battleStates.ts: attack ×2 가 2개면 ×4

가산이 아니라 곱샘. 공격업 상태 2개 + 장비 효과가 겹치면 피해가 기하급수로 뛴다. 반대로 방어다운 0.5 두 개면 방어 0.25 — 보스가 녹는다. 상한/하한 캡이 없다.

이중 RNG 소모: equipmentResistsState()가 상태 저항 판정 전에 또 rng()를 굴린다. 같은 시드라도 장비 유무에 따라 이후 모든 판정(명중·분산·크리) 순서가 밀린다. 재현성은 유지되지만, “장비 끼면 크리율이 달라지는 것처럼 보이는” 디버깅 함정.

전투가 멈추는 시나리오 (실제 코드 경로)

수면 파티 전원 — canBattlerAct=false → 명령 불가 → strictCurrentRoundActions에 빈 액션만 쌓임 · tick은 battleFlow==="strict"에서 early return이라 회복 틱도 안 돎
독만 남은 경우 — runStateUpkeep은 매 턴 돌지만 hp-1 캡으로 절대 죽지 않음 → 라운드만 증가
200R 도달 — STRICT_MAX_ROUNDS 초과 시 escape로 강제 종료 · 로그는 남지만 플레이어는 원인 불명
CHAPTER 04 — BALANCE / REWARDS / PROGRESSION

성장·보상: 레벨업은 단단한데, 보상이 재미를 갉는다

레벨 곡선 자체는 잘 설계됐다. 문제는 그 주변 — 드랍, 경험치 페널티, 시뮬 밸런스가 체류 동기를 꺾는다.

견고 레벨업 — 다중 레벨·클래스 곡선 일원화

computeActorLevelUp()이 누적 경험치 vs totalExpForLevel()로 while 루프 다중 레벨업을 처리. 클래스 오버라이드 시 parameterCurves 교체, 스킬은 합집합.

while (level < max && exp >= totalExp(level+1)) level++ gain = curve[level] - curve[fromLevel] learned = actorSkills ∪ classSkills

마이그레이션 내성도 확보: normalizeActorRecord가 레벨·커브 기본값을 메운다. 이 부분은 적대 리뷰에서도 흠 잡기 어렵다.

레벨 곡선이 주는 성장 체감 — 왜 후반이 밋밋한가

레벨 20→30에서 공격 +38, 레벨 70→80에서 +42 — 50레벨 동안 기울기 거의 동일. 플레이어는 “후반엔 더 빨리 세져야” 기대하지만, 곡선은 그 기대를 안 준다.

갭 패널티 — 귀환을 처벌한다

expForRewardActor(): 적 레벨보다 5 높으면 50% 컷, 10 높으면 90% 컷.

gap = actorLv - enemyLv if gap>=10 return floor(exp*0.1) if gap>=5 return floor(exp*0.5)

의도: 고렙 사냥 방지. 결과: 뒤로 가서 도우려는 신규 유저 동행, 도감 채우기, 아이템 파밍이 전부 손해. 오픈월드·마을 상점·우정 시스템(openwiki 다수)과 충돌 — “돌아다니는 재미”를 경험치로 처벌.

드랍 — 독립시행의 잔인함

collectBattleRewards()는 적마다 rng()*100 < dropRate 독립시행. 5% 드랍을 20번 잡아도 기대 1개, 실제 0개인 확률 36%.

items = enemies.flatMap(e => rng()*100 < dropRate ? [dropId] : [])

천장·보정·묶음 드랍 없음. 플레이어는 “20번 잡았는데 왜 안 주냐”를 시스템 탓이 아니라 운 탓으로만 듣는다. 보상 예측 가능성 0.

  • hidden/captured 적은 보상 제외 — 포획과 드랍이 배타적이라 “잡을까 죽일까” 선택이 생기지만, 설명이 없다.
  • enemyLevel = max(enemy.level) — 트룹 내 최고 레벨만 경험치 갭 계산에 사용, 평균이 아님.

시뮬레이터 — 밸런스 테스트의 빛과 그림자

src/battle/simulate.ts는 RNG 고정·몬스터 파티·엄격 스크립트로 N회 전투를 돌려 승률/평균턴/포션/잔여HP를 뽑는다. 체스처럼 밸런스를 돌려볼 수 있는 건 큰 장점.

runSingleBattle: mulberry32(seed) 고정 AI: hp<=30%면 potionItemId 사용, 아니면 평타

그림자: AI가 너무 단순 — 평타만으로 승률을 재니, 스킬·속성·상태를 쓰는 실제 전투와 괴리. “시뮬 승률 70%”가 실전 70%가 아니다. 회복 AI도 단일 아이템·30% 단일 임계값이라, 두 가지 물약·상태해제 전략은 평가 불가.

AUTO — 친절하지만 멍청한 동료

battleAuto.chooseAutoBattleCommand() 우선순위: 강제교체 → 회복 → 공격스킬 → 평타 → 방어. 아이템은 안 씀.

  • 회복 점수: hpDanger=(0.4 - hp%)×100 — 40% 이하에서만 점수 발생, 41%는 0점. 경계에서 회복 안 함.
  • 공격 점수: 피해+치명타 보정 1000점 — 잡을 수 있으면 무조건 그 대상. 합리적이지만, 광역·디버프 가치는 0점.
  • 동점만 RNG — 그 외엔 결정론적이라 매번 같은 선택.

결과: AUTO는 “죽기 직전에 힐하고, 잡을 수 있으면 잡는다”만 한다. 버프·디버프·광역 판단이 없어, 후반 보스전에서 AUTO는 평타 기계.
